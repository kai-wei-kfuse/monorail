# ADR 0001：私有 GitHub 更新与安装前收尾

- 状态：Accepted
- 日期：2026-10-27
- 授权：用户要求接入检查更新、测试原地升级，并上传 GitHub 私有仓库。

## 问题与决定

当前应用只有 NSIS 安装包，没有更新客户端。GitHub 私有 Release 的清单和安装资产均需认证，公开静态下载地址不能满足当前仓库可见性要求。

采用 Tauri 2 官方 updater 验证签名、下载和运行 NSIS。原生端从本机已登录的 GitHub CLI 读取凭据，调用 GitHub REST 定位 Release 中的 latest.json，并向 updater 提供带认证的资产 API 地址。令牌不传入前端、不写入配置、不打包、不记录日志。缺少 gh 或未登录时明确报错；不降级到匿名下载。私有开发版的每台机器需先安装 gh 并登录可访问仓库的账号。

私有更新配置只包含仓库名称及可选固定 Release 标签。正式配置读取最新正式 Release；验收配置固定测试 Release，以便隔离测试资产。GitHub API 和资产 URL 必须指向配置的仓库，避免将凭据发送到任意地址。HTTPS 客户端保留跨域重定向去除敏感请求头的默认行为。

## 边界与不变量

- platform 封装版本、检查、下载进度和安装 IPC；应用组装层连接状态与界面，业务模块不引用具体更新实现。
- 版本以 package.json 为发布输入，由脚本同步 Cargo 及锁文件；Tauri 读取 package.json，界面读取真实应用元数据。
- 安装前同步封口主窗口提交队列，并等待此前已入队的事务全部完成；部分提交故障必须阻止安装。
- 定时和电源触发的事务等待封口解除，不把安装失败变成丢失日界或休眠结算。
- 快速记录的附件和记录保存视为一次会话。安装前有正在保存或未保存草稿时明确拒绝安装，保留输入，让用户完成后重试。
- 收尾成功后原生端保存 last_alive，再调用官方 updater 安装。失败必须解除封口并显示原因；不关闭用户任务、不改计时规则。
- 更新签名私钥保存在仓库外及 GitHub Secrets；只有公钥进入应用。

## 发布与验收

Windows 发版执行测试、类型检查、lint、签名构建。先上传 exe 和 sig，按资产 ID 生成含签名内容的 latest.json，再发布完整 Release。正式 tag 与 package.json 版本一致；同一 tag 的资产不覆盖。

用独立产品名「单轨更新验收」、identifier local.pixelrecord.update-test 和独立安装/数据目录安装 0.1.1，再由应用内真实下载与安装 0.1.2。两次均为生产构建，不启用 verify feature。证明安装路径相同、版本更新、记录与计时状态、目录授权持续可用。原本正在运行的「像素记录」不参与此验收，不宣称旧产品名迁移已验证。

## 影响

当前阶段 M4 增加更新、发版与真实升级验收；不改变领域模型及数据格式。GitHub CLI 认证适合当前私有开发范围。面向无需开发工具的用户分发时，应另做认证设计，而不是内置共享令牌。
