## 3. 目标模块与迁移范围

建议目录（按职责实施，若局部命名调整，应记录真实路径）：

```text
src/shared/application.ts          应用方法、输入输出 schema 与类型映射
src/shared/appError.ts             既有共享错误，不复制
src/shared/operation.ts            既有回执与操作定义，不复制
src/app/applicationController.ts   桌面应用请求分派（从 mcpController 迁移）
src/app/applicationBridge.ts       Tauri 消息接线（从 mcpBridge 迁移）
client/
  applicationClient.ts            类型化调用、结果验证
  pipe.ts                         Windows 连接/配置/后台启动（从 mcp/pipe 迁移）
  types.ts                        仅确有需要时放 transport 接口，不建导出镜像
cli/
  main.ts                         薄进程入口，注入 IO 与客户端
  commands.ts                     子命令/flags 映射
  execute.ts                      上下文获取、重试技术字段恢复
  output.ts                       人类文本/JSON/退出码
mcp/
  server.ts                       工具元信息与 MCP 封装
  main.ts、http.ts                 标准传输入口
```

不要求每个文件机械拆分；以上是职责边界。schema 规模大可按确切业务域拆文件，但只能有一个被双方引用的权威定义。

### 3.1 公共契约

以现有 15 个方法为准，保留 wire 方法名与已确定字段。公共 contract registry 将方法名关联输入/成功输出 schema；类型从该定义推导，不能另写第二份手工请求/返回映射。

可使用类似接口（签名是目标，不是强制逐字实现）：

```ts
call<M extends ApplicationMethod>(
  method: M,
  input: ApplicationInput<M>,
  options?: { signal?: AbortSignal }
): Promise<ApplicationOutput<M>>;
```

运行时边界仍要校验。对公共调用者返回经过验证的成功值；失败抛 ApplicationError，保持 code/category/next_step/latest_context。仅 raw transport 允许 unknown。若 SDK 要 JSON Schema，从同一权威 schema 导出。

SDK 的工具输入校验与桌面入口校验分别位于外部边界，可以都保留；两边必须引用同一契约，而不是两套规则。`outputSchema` 仍包含成功/错误联合，保留旧客户端兼容修复。

公共契约不得导入 MCP SDK、node:*、Tauri 或桌面 store。客户端不得导入 services/domain/data/app；它只能读连接配置，不直接读写业务 Markdown。

### 3.2 ApplicationController

从现已修复的 handleMcp 迁移为中性的 handleApplicationRequest。继续共用 recordService/homeService、完整 snapshot、runOperation/readOperation。Rust 的 pipe/事件/权限名称不要求本轮一并改名。

删除过时直接引用，更新 bootstrap、桥接、测试、原生证据脚本和 lint。不要创建 handleCli 分支复制 switch；不要为 CLI 单独初始化 Ctx 写磁盘。

### 3.3 MCP 适配器

保持 15 个工具和语义；工具名称、描述、annotations 留在 MCP 内。业务输入输出和错误校验下沉公共客户端。MCP 只将已验证成功/错误映射到 content/structuredContent/isError，继续支持 2025/2026 两代 stdio/HTTP。

## 4. CLI 命令契约

统一使用 `monorail` 作为用户命令名称；源码执行可为 `node cli/main.ts`，发行基准为 `node <安装资源>/monorail-cli.mjs`。可提供同目录 launcher，但不能依赖用户仓库 cwd，也不默默更改系统 PATH。

| CLI | 应用方法 | 参数 |
|---|---|---|
| `context` | get_context | 可选重复 `--section timer/pending_actions/options` |
| `idea add <text>` | save_idea | 可选 `--needs` |
| `todo add <text>` | capture_todo | 可选 `--task-id`、`--due-at`、`--blocking` |
| `find [query]` | find_items | `--kind idea/todo_card/task/all`、`--include-archived` |
| `time summary` | get_time_summary | `--day today/yesterday/this_week/YYYY-MM-DD`、`--day-mode activity/calendar` |
| `time entries` | list_time_entries | 必填 `--from`、`--to`，带时区 ISO |
| `time add <description>` | add_time_entry | 必填 `--start`、`--end`；可选 `--project`、重复 `--tag` |
| `timer start <description>` | start_timer | 可选 `--project`、重复 `--tag` |
| `timer start-item <card-id>` | start_task_item | 必须提供查询得到的精确 ID |
| `timer pause/resume/stop` | 对应三个控制方法 | 默认读取最新上下文后调用，仍由服务核验 |
| `break start <activity>` | start_break | 名称或既有预设 ID；保持原语义 |
| `break return` | return_from_break | 与 pause/resume 分开 |
| `operation get <id>` | get_operation_result | 查询已有操作，不写入 |

通用：`--help`、`--version`、`--json`。未知命令、未知 flags、互斥参数、重复单值参数均明确报 usage error，不忽略。布尔开关约定明确，不把字符串 "false" 当真值。

正文输入支持三选一：位置参数、`--text-file <path>`、`--stdin`；后两者用于多行/中文/包含 shell 特殊字符的内容。缺少明确输入时不无故等待 stdin。只对需要 text/description 的命令启用，互斥冲突在调用应用前拒绝。文件只作为用户明确指定的内容来源，不允许因此跳过现有业务校验。

内部执行一律参数化调用，不拼 shell 命令。CLI 不通过子进程运行 MCP，不给用户文本套 shell `eval`。帮助必须列出最小示例、JSON 方式及如何核对结果未知的操作。

## 5. CLI 状态、幂等与重试

### 5.1 新操作
写命令缺少 --operation-id 时，调用 get_context 签发 ID；计时控制同时取得 expected_state。允许自动化显式传 `--operation-id` 与 `--expected-state`，已有值不静默覆盖。只读命令不额外签发写 ID。

上下文读取与写入之间仍可能被其他入口改变状态：服务在事务内检查，STATE_CHANGED 返回最新上下文和下一步；CLI 不自动刷新令牌后重放。用户可明确再发一次新意图。

### 5.2 同一操作重试（必须实现并测试）

当前 timer receipt 的规范化 input 含 expected_state。不能只拿旧 --operation-id 加新上下文调用，否则已成功的重试会产生 OPERATION_CONFLICT。

建议通过公开的 get_operation_result 在已有 receipt 上额外返回 `request: { method, arguments }`，arguments 为该次**实际规范化输入**（不从 data 推测原请求，不新增存储来源）。该结果字段与 schema 要同步测试并说明兼容扩展。

有显式 --operation-id 的写命令：
1. 查询该 ID。若未找到，再按缺失字段取上下文；若查询失败/未知，不猜测成功或失败。
2. 若已提交且用户没有给 --expected-state，恢复 receipt 中的原状态令牌。命令名和用户本次正文/目标/时间等仍取本次 CLI 输入，不能一律复制历史业务参数。
3. 调用同一应用命令，让已有 runOperation 比对规范化请求。相同请求返回原结果，任何业务参数变化仍冲突。显式传了不同 expected-state 也不能被 CLI 偷改。
4. 如果只有旧 receipt 的错误/缺字段而无法可靠恢复，明确说明不能重建重试，提供 operation get；不能凭最新状态替代。

测试两个并发进程同 operation ID，保证只执行一次或清楚返回冲突，绝不能重复写。自动化调用方希望跨进程确定幂等时应显式保留 --operation-id。

### 5.3 输出与退出码

`--json`：stdout 恰好一个完整 JSON 结果，错误也为 JSON；诊断只能到 stderr。普通模式 stdout 显示简洁业务结果，错误到 stderr。两种模式均带关键 ID/提交状态；写入结果未知时必须保留原 operation_id，给出核对命令。

建议统一 CLI 外层 envelope：成功 `{status:"ok", method, result}`；失败 `{status:"error", method?, operation_id?, error: ApplicationFailure}`。内层应用结果不改名、删字段或把 warning 改成失败。help/version 的 --json 分别返回明确结构。

| 退出码 | 意义 |
|---|---|
| 0 | 调用成功，含 committed+warnings 或已确认 noop；warnings 仍展示 |
| 2 | CLI 用法/本地参数错误，尚未调用业务 |
| 3 | 应用明确拒绝且未执行，如 STATE_CHANGED/OPERATION_CONFLICT/非法目标 |
| 4 | 连接/配置/就绪等环境错误且确认尚未发送业务 |
| 5 | 结果未知，须核对原操作 ID；不得当作未写入 |
| 130 | 用户取消且确认发生在发送前 |

若发送后取消可能已经提交，使用 5，并保留 CANCELLED_AFTER_SEND 原因；不能仅凭收到 SIGINT 就宣称未执行。不要自己添加固定生成期限、重试循环、回执淘汰上限或静默截断。

## 8. 验收矩阵

### 公共客户端
输入验证失败不发请求；返回成功 schema 不符时保持结果未知；ApplicationError 不丢 code/category/latest_context；AbortSignal 保持原语义。编译期验证方法与输入/结果匹配，但不以纯类型镜像测试代替行为。

### CLI 行为
15 项能力可达；同名候选不盲选；中文、多行、引号、`&`/`|`/反引号/`$()` 作为普通数据处理；无输入、重复 flags、错误时区、非法日期、文件读取失败明确失败；help/version 无后台；JSON stdout 无日志污染；退出码符合 §5.3。

### 混合入口
- MCP 保存 → CLI 查找/核对；CLI 捕捉待办 → MCP 查找/开始指定卡片。
- CLI 开始 → MCP 暂停 → CLI 停止，卡片与返回目标保持正确。
- 同一 operation_id 先在 MCP 提交，再由 CLI 同参数重放；反向同样通过；修改正文/目标必须冲突。
- CLI 首次自动取状态后发生 UI/MCP 状态变化，写入拒绝，不悄悄重试。
- 查询遇 journal 中间态只读完整已提交 snapshot，失败后明确拒绝；继承 R1–R3/D1/D2 全部回归。
- 发送后断开/取消保留操作 ID 和结果未知；排队前取消不落盘；committed+warning 仍返回成功与可见警告。

### 分发/平台
未启动、托盘、前台三态；并发冷启动单实例；旧版/未初始化/配置损坏/权限/busy 明确区分；干净目录两包双向调用；Windows debug build、资源路径核对。不改用户日常数据或窗口，用独立 identifier 与临时目录。

测试顺序：定向行为 → 类型/lint → 受影响构建 → 最小真实原生/CLI/MCP 冒烟。后端测试进程 60 秒期限沿用项目规则，不在产品调用上复制该期限。
