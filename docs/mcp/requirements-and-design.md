## 1. 用户体验与产品边界

用户通过 AI 完成保存想法、捕捉待办、寻找记录、分析时间、控制活动计时等日常操作。AI 负责理解意图和解释结果；单轨负责实体定位、业务规则、时间计算、并发检查和可靠提交。

可以在支持 MCP 的不同客户端调用同一组能力。默认本机 stdio，可选 Streamable HTTP。协议兼容、客户端具体支持、网络可达性分别验收。

“不打开单轨”定为：完成首次安装和数据目录选择后，无须用户手动打开主窗口；进程未运行时允许 MCP 启动后台实例。托盘/进程存在不等于出现主窗口。不是在电脑关机时仍执行本地代码，也不是保证手机系统允许永久后台进程。

## 2. 未打开窗口时如何执行

### 2.1 第一阶段：按需启动现有应用的后台模式

```text
AI 客户端 → MCP 适配器 → 连接已有单轨后台
                          └─ 明确未运行 → 启动已安装单轨 --background
                                                ↓
                        恢复 journal / 迁移 / 建立业务上下文
                                                ↓ ready
                        原服务执行 → 提交并返回 → 稍后打开 UI 可见
```

现有基础：`src-tauri/src/windows.rs` 关闭窗口只 hide；`tray.rs` 的退出才结束进程。`lib.rs` 已注册 single-instance，但第二次启动目前会 show/focus 主窗口。`bootstrap.ts` 在主 WebView 中创建业务上下文。官方 Tauri single-instance 提供启动参数，窗口配置支持 create/visible，足以支持这条演进路线，尚未实现或验收新模式。

实施要求：
- 新增明确的 `--background` 启动意图；在创建窗口之前决定可见性，避免先闪窗再 hide。普通双击依旧显示窗口；第二个后台请求不抢焦点。
- 同一用户/数据目录只有一个写入者；并发启动由单实例机制收敛，启动器重连已有服务。只把“未运行”当作启动条件，权限错误、协议不匹配、损坏配置不自动当未运行。
- 可执行文件路径来自安装/配置入口；不扫描猜路径，不让模型传任意执行命令。首次未配置返回 SETUP_REQUIRED；让用户完成一次 UI 初始化。
- 区分 starting、recovering、migrating、ready、failed。观察真实 ready/退出事件，不以固定 sleep 假装就绪；保持取消能力，不添加无证据的硬启动期限。
- 后台应用持有业务状态。MCP 客户端关闭不结束正在计时的后台；用户明确退出才结束。之后新的授权工具调用可以再次按需启动。
- 起始时刻以后台 ready 后正式接纳该命令的时间为准，返回 effective_at。冷启动前的等待不偷偷记成活动时间；历史起点使用补录能力。
- 启动恢复可能产生离线追问等 notices；MCP 必须返回可见的 pending_actions，不能在隐藏窗口里无人处理，更不能自动编造离线活动。只有实际阻碍操作的领域状态才拒绝。

这仍然运行隐藏 WebView，不能称为不依赖 UI 运行时的 headless 服务。资源占用以冷启动与常驻测量为准，不承诺更轻。

### 2.2 后续独立后台与移动端

业务契约、纯领域函数与用例不得依赖 DOM、Tauri window 或 named pipe；原生能力保持注入。当前后台模式利用已有结构，未来如需独立服务，将事务/调度的唯一所有者从 WebView 移出，而不是桌面、手机各写一份业务规则。

远程 Agent 首先需要运行中的可达后台及授权。电脑关机时还要保存/计时，则必须有其他在线权威端（服务端或可运行的设备），这属于移动/同步阶段，不能靠“远程 MCP 地址”自动实现。

## 3. 按现有功能选择的 MCP 能力

### 3.1 首个可用版本：核心功能组

| 用户说法 | 工具候选 | 现有依据与明确语义 |
|---|---|---|
| 帮我记下这个想法 | save_idea | recordService/createRecord；进入想法池，不建任务 |
| 帮我记个待办 | capture_todo | 记录条待办 + reconcile 规则；缺省单事项支线，不改变当前计时；记录、卡/任务与回执同事务 |
| 找一下我说过的那个点子/待办 | find_items | 从现有记录、任务、卡片投影查询；指定 kind + query，返回显示名、ID、状态；关键词精确搜索先行，不假装语义搜索 |
| 现在在做什么/有哪些可以操作 | get_context | 一次已提交快照；当前活动、状态、允许操作、相关目标、操作 ID 与状态令牌；按 section 请求，默认仅当前状态，不倾倒全部历史 |
| 今天时间都花在哪里了 | get_time_summary | 确定性统计；活动日/自然日、待机、离线、重叠和真实空档分别说明 |
| 看一下某段时间的记录 | list_time_entries | 返回原始边界和区间内时长，供核对，不截断合法结果 |
| 开始写代码 | start_timer | 普通活动的开始/切换，复用 homeService；项目缺省未分类 |
| 暂停/继续/结束这件事 | pause_timer / resume_timer / stop_timer | 分别表达意图；修复共用服务的暂停态停止语义，不做 MCP 特例 |
| 开始做这个待办 | start_task_item | 查询后使用明确 card ID，走 homeService.startCard；不将显示名称当唯一键 |
| 我去吃饭，回来继续 | start_break / return_from_break | 对应现有临时插入与“回来”；保留原返回目标；不等同于降级休息 state.rest |
| 刚才 14:00–14:30 在看书，补记一下 | add_time_entry | 手动补录；带时区的起止时间；复用 place/manual 与现有并行语义；报告重叠，不覆盖其他普通记录 |
| 刚才那次保存到底成功了吗 | get_operation_result | 按稳定 operation_id 查询 receipt，区分 committed/not_found/unavailable |

以上是优先实现范围，不是已有能力清单。工具名称在 schema 冻结时最终确定；不额外保留含糊同义工具。

### 3.2 第二批：任务整理与回顾支持

这些能力纳入需求目录，以单独里程碑交付，不把“本轮可以选择”解释成必须在一个版本塞完所有 UI 操作。

| 能力 | 选择理由与规则 |
|---|---|
| 编辑想法正文/需求 | `create_idea` / `get_idea_details` / `update_idea`（0.3.3 已交付，见 ADR 0026 / ADR 0029）；必须命中明确目标与 `record_revision`，避免覆盖用户刚编辑的内容 |
| 建任务并添加事项 | `create_task`（0.3.3 已交付，见 ADR 0029）；主线/支线及容量遵循现有规则；满了返回 `TASK_CAPACITY_FULL` / `MAIN_TASK_ITEMS_FULL`，不自动放弃旧任务腾位 |
| 把想法转成待办/拆分任务 | `convert_idea_to_task`（0.3.3 已交付，见 ADR 0029）；明确目标（指定现有 `task_id` 或新建主/支线任务）与 `record_revision` 才执行，保留原想法完整 Markdown 详情与关联 |
| 完成指定事项并记录进展 | cardService.checkComplete/complete；时间盒不足、非当前卡等遵循领域规则；不能静默替用户选 keepGoing、跳过 note 或触发额外行为 |
| 创建计时项目、保存常用活动 | presetService；明确用户意图时新增；start_timer 不因模型猜出名称而自动改设置 |
| 获取周回顾素材 | 只读周区间统计、完成事项和想法（`get_recap` 0.3.2 已交付）；AI 帮用户整理，但不自动把单轨的回顾状态机标为完成 |

暂不开放批量删除、重置数据、改数据目录、安装更新、任意文件读写、自动放弃/冷藏任务、擂台淘汰和替用户更换主线。这是当前产品范围选择，并非 MCP 协议的限制。

## 4. 面向低成本模型的工具设计

GPT-6 LUNA 作为目标测试模型之一，不预先断言任何模型能达到成功率。MCP 客户端选择模型，单轨 Server 不硬编码模型或把规则外包给昂贵模型。

- 一个工具对应一个清楚的用户意图，输入用扁平字段、少量语义枚举；避免 `execute(command, payload)`、复杂嵌套 union 和“开始/暂停/删除都放一个 action”大工具。
- 工具描述明确“何时用、会改变什么、不能替代哪个工具”，给一个最小输入示例。无需依赖某客户端专用 system prompt，也不依赖支持可选 MCP prompts 才能正确使用。
- 模型只复制服务给出的 ID/令牌，不计算 hash、不生成 UUID、不拼 Windows 路径、不手动计算时间总和。名称重名返回候选，不采用第一个搜索结果偷偷执行。
- `get_context` 首次提供一个服务器生成的 `operation_id` 和 `expected_state`；每次成功写入返回新的可用 operation_id。重试沿用旧 ID。模型只复制字符串。它不是授权 token，不替代登录。
- 第一次冷调用通常“get_context → 写工具”两步；已有上下文时直接写。暂停/停止使用明确目标，状态改变时返回最新上下文及合法下一步。不要求用户回答技术性的 ID 问题。
- operation_id 在正式写契约中必填；已有原型无此字段尚未发布，升级需同步示例/测试。优先用工具签发 ID；存储文件名使用服务端固定编码/散列，不把模型给的 key 直接拼路径。不规定无依据的 128 字符等任意上限。
- 时间输入提供 `today`、`yesterday`、`this_week` 等明确语义入口，由服务按设备/账户时区解析；仍允许显式时间区间，模糊“下午两点”由 AI 根据返回的时区/日期澄清。
- 结果结构统一：status、简短 summary、data、必要时 allowed_actions/next_step。错误明确指出“未执行”“已提交但提醒失败”“结果未知”，而不是只给 Rust 堆栈或一句失败。
- 普通、已授权的单步保存不增加确认弹窗。只有实际重名、目标变化、用户未表达的影响或现有领域要求需选择时才询问。模型不能自行把 confirmation=true 视为人的同意。
- 不依赖动态隐藏工具才可用；默认通用列表和简单 schema，专业工具可按实际成本实测再提供配置组。

### 模型验收

建立按用户原话编写的任务集：一句记想法、聊天提炼、重名任务、暂停后停止、临时离开后回来、02:30 的“今天”、并行记录、模糊补记、应用未启动、断线重试、过期状态、服务错误。正常/歧义/故障分别计分。

实际使用目标低价模型与一个对照模型，记录工具选择正确率、参数有效率、最终状态、误写/重复写、调用轮次、输入输出 tokens、延迟；费用只按实际模型计费记录计算，不使用猜测价格。固定提示与数据，重复运行检验波动。关键场景要求无未授权更改、无重复提交、无假成功；正常任务完成率以测试集逐条验收报告，不用自评分替代结果。

本文初稿阶段没有调用目标模型；现已完成 GPT-6 LUNA 与 GPT-6.1 SOL 同题目/种子各两轮实测，记录在 M9 最终报告与 `evidence/m9-suite/`，不将有限样本外推为普遍成功率。

## 5. coder-3 首轮审核的处理决定

审核对象为 v1；原文保留在 `evidence/mcp-execution-plan-review.md`。以下是方案修正，不代表代码问题已修完。

### B1：回执、幂等与提交结果
采纳独立 ReceiptRepo + 同 journal 原子提交；提取共用 InTx 用例；在现有串行队列内、加载/修改事务之前检查回执命中，命中不写 state、不增加 revision、不发布投影。get_operation_result 明列为工具。

已提交后提醒失败返回 committed + warning，并保留可查询的提交结果；日志和应用错误状态继续显式上报。publish 失败也必须与持久化提交区分，不能把已落盘结果说成未保存。此为有界的 post-commit 错误处理，不吞事务异常。

回执在独立目录，不塞进 state.yaml。审核中“z.object 默认严格拒绝额外字段”不准确：本地验证当前 Zod 会去除额外字段；所以把回执塞进 state 仍可能丢失数据，但不是必然抛解析错误。

不采用无依据的“500 条/30 天自动删回执”。这会使旧操作重试重新执行。先按 ID 直接索引，不每次全目录扫描；清理/归档需有测量和明确幂等保留契约，不能把 expired 与从未存在混为 not_found。

### B2：桥接生命周期
采纳监听器启动幂等、WebView 世代标识、明确 ready、旧回复隔离与读写 admission 区分。不得仅因 oneshot 被丢弃就解除仍在执行的原生写入保护；旧 WebView 发出的文件 IPC 可能未结束。

第一阶段保守方案：宿主丢失时停止接纳新写入，向请求端报告结果未知；确认旧写执行环境结束后由完整进程重启、journal 恢复和 receipt 核对恢复服务。若要在进程内热重载，则必须实现并测试原生 IO 排空/世代隔离，不能靠 sender.clear() 宣称已安全。更新准备期应复用单一协调状态，避免复制前端/原生两套门控。

### B3：时间口径
一次 snapshot + 一个真实 as_of。返回 resolved_day/timezone/day_boundary，采用有效区间裁切；未来日期返回尚未发生的零时长，不产生负数，非法日期显式拒绝。时钟倒退明确报告 CLOCK_INCONSISTENT，不静默把现在推到未来。

分别返回非待机覆盖 non_idle_covered_ms、待机 idle_ms（含暂停）、真实空档 untracked_ms；恒等式 interval_elapsed_ms = 三者之和。非待机记录累计 non_idle_recorded_ms 与 coverage 的差才是 overlap_excess_ms。非待机含睡眠/离线，绝不命名为“有效工作时间”。保留各系统项目独立统计。

### B4：状态转换
固定顺序：幂等回执 → expected_state → 领域前置条件 → 单事务执行。普通控制遇 pending/rest 明确说明；临时活动由新加入的 start_break/return_from_break 处理，不混用普通 resume。

暂停后停止必须清除返回目标并对齐卡片，在共用 timerService/homeService 修复并覆盖桌面回归；不能让 MCP 绕过 bug 后 UI 仍错。已经暂停/待机返回未更改的实际状态，不能说“刚执行成功”。未知/系统保留项目由公共规则校验，普通 start_timer 不自动建项目或伪造离线条目；需要睡眠等专门语义时另加明确用例。

### B5：协议与分发
P0 验证 v2 官方工厂形式同时覆盖 stdio/HTTP 与 2025/2026 两代协议；无参 schema 显式空对象。所用 API 以锁定版本实际编译和互操作为准，不凭抓取代码里的格式噪声实现。

本机 HTTP 显式启用，回环绑定、Host 校验、Origin 明确白名单（不自动信任 null/任意 localhost）；云端使用独立 HTTPS/授权方案。默认不承诺旧双端点 HTTP+SSE。发行物先定为打包依赖的 monorail-mcp.mjs + Node 24，随单轨安装版本提供定位配置，不依赖源码仓库；无需 Node 的独立可执行文件以后按用户安装体验决定。mcp 静态检查纳入统一 check。

### 5.4 v2 复审实施建议（v2.1）

- N1 / M5：Rust setup 阶段建立可查询的生命周期入口，前端报告 setup_required/recovering/ready/failed；不让启动器以“管道不存在”猜测首次配置或恢复失败。监听开始与业务 ready 分开。
- N2 / M6：pending_actions 读取累积未消除通知，通过 app 适配接口获取；不能只取 ctx.snapshot().notices，因为它只包含最新一次事务通知。当前 appStore 的 appendNotices 已保存累积状态，不再建第二份通知列表。
- N3 / M7：return_from_break 要求当前为插入活动，但允许 resume_entry_id=null 并正常退回待机；resume_timer 要求真正可恢复的暂停状态。start_task_item 与 start_timer 共用 rest/插入/pending 检查，不直接调用会清除这些状态的内部函数。
- N4 / M6–M7：capture_todo 如支持指定 task_id，须在事务内校验任务在背包和容量；缺省单事项支线遵循已有 E4 规则。add_time_entry 拒绝系统保留项目；补录改变当前待机边界时返回新的 expected_state。

## 6. 手机端与可扩展性约束


手机端将是业务系统的另一个入口，不要求把桌面 MCP Server 原样塞进手机。MCP、Windows UI、未来移动 UI 均围绕相同的操作语义和返回契约。

当前只做必要边界：稳定实体 ID、操作 ID、明确时区/起止时间、结构化业务错误、平台能力注入、按能力定义契约。Windows 路径/pipe/安装目录不进入业务 schema；不现在搭建未使用的同步框架或万能插件系统。

移动/同步阶段必须另定：账户/设备归属、哪端是权威数据源、离线操作队列、同步冲突和删除、两台设备同时开始计时的规则。当前的“一台桌面串行队列”不能当成多设备一致性方案。MCP 接口本身不负责自动同步数据，也不保证手机后台常驻。

## 7. 修订后的执行里程碑

| 阶段 | 当前范围 | 验收 |
|---|---|---|
| M4 / P0 | SDK 双时代、stdio/HTTP 工厂与协议契约 | 两代客户端的发现/调用/错误均通过 |
| M5 / P1 | 保存可靠性、共用事务回执、生命周期、按需后台启动 | 完全退出后不弹窗启动；并发调用单实例；恢复/迁移/未配置/中途退出无假成功；幂等重试无新副作用 |
| M6 / P2 | get_context、查找/待办捕捉、时间查询 | 准确候选、不猜目标；记录转换原子性；统计恒等式/跨日/DST通过 |
| M7 / P3 | 普通计时、指定待办、临时离开与回来、补录 | 共享状态机与桌面一致；暂停停止缺陷回归；不擅自认领 pending 或覆盖原记录 |
| M8 / P4 | 双传输产品入口、安装定位、自包含包 | 干净环境不依赖源码目录；后台运行/重连/退出策略明确 |
| M9 / P5 | 多客户端 + 低价模型行为验收 | 真客户端调用；真实低价模型任务集；误写/重复/假成功等关键场景通过 |
| 后续 A | 任务整理/想法编辑转换/周回顾素材 | 每项契约简单且复用规则，不模拟点击 UI 对话框 |
| 后续 B / P6 | 异机个人 Agent、手机与同步设计 | 远程可达/授权撤销/设备离线语义；手机按独立平台计划交付 |

先闭合 M4–M9；第二批与移动/远程并非在本轮自动实现。当前 stage 的 M0–M3 原型事实继续保留。每阶段记录关键决策与证据，最终整理新 session 解读材料。

## 8. 新增验收场景

- 未启动单轨、仅托盘运行、前台运行，三种情况下结果相同；后台启动不闪窗/抢焦点。
- 两客户端同时冷启动、用户同时双击图标，不产生两个数据写入者。
- 首次安装未选目录、更新/迁移失败、管道权限错误有不同的机器可读结果。
- MCP 客户端结束后计时继续；用户退出应用后再调用按约定重新启动并处理离线区间。
- 低价模型能区分想法/待办/计时项目/任务事项；不会用自由计时替代指定卡片计时。
- 同名结果、上下文过期、上次结果未知时，能沿返回指引完成或澄清，不自行猜 ID。
- 记待办不开始计时；开始指定待办保留卡片关联；临时活动回来恢复正确目标。
- 两个设备同时计时的测试留到同步阶段，当前不标为已支持。
