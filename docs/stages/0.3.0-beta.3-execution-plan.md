### E5 D4 小窗会话世代

根因（已核对）：小窗的修订号来自每个 Ctx 的 `queue.version`（`src/services/commit.ts:75` 初始化为 0，`:213` 每次提交 +1）；主窗口重载会重建 Ctx，计数从头开始，而小窗 `src/platform/windowBus.ts:63-67` 闭包里还留着旧的高修订号，把新快照和心跳全部丢掉，3 秒后显示「主窗口未响应」。另一个隐患：旧会话的编辑命令可能碰巧带着与新会话相同的修订号，被新主窗口误接受。

1. **可比较的会话世代**（审核 G3）：随机 UUID 分不出新旧。连续重载 A → B → C 时，如果 C 的快照先到、从没见过的 B 后到，「当前会话 + 已退役集合」会把 B 当成新会话接纳、反把 C 退役，之后 C 的心跳全被丢弃。改为由 Rust 进程发放单调递增的世代号：
   - 新增 Rust 命令 `begin_main_session()`：进程内 `AtomicU64` 加一后返回（先例：`mcp_bridge.rs` 的 `generation`、`mini_visibility.rs` 的 `REVISION`）。前端重载不会重置它；Rust 进程重启时小窗也随之重建，从头计数没有问题。在 `lib.rs` 注册，capability 只开放给 `main` 窗口。
   - 主窗口 `bootstrap()` 在创建 Ctx 前调用一次，结果作为 `Ctx.mainEpoch`（E0.5 定义），与 `queue.version` 同生同灭。
2. `MiniSnapshot`（`windowBus.ts:24-33`）加 `epoch`；`connectMini.push`（`miniController.ts:13`）填入。
3. 命令 `base` schema（`windowBus.ts:8`）加 `epoch`，所有命令都带（schema 是 `.strict()`）。
4. 小窗过滤（`windowBus.ts:62-69`）按 `(epoch, revision)` 字典序比较：`epoch` 更大 → 接受并以它为新基准；`epoch` 更小 → 丢弃；`epoch` 相同 → 丢弃更小的 `revision`（心跳的相同修订仍接受）。首次订阅接受任意快照。不再需要退役集合。
5. 小窗界面（审核 G4）：
   - 收到更大 `epoch` 的快照时：清掉 `MiniApp` 的名称编辑、提示和报错；**按 `epoch` 重建读数编辑组件**（`TimeField` 加 `key={epoch}`，它自己保存了 draft / target 和确认回调，`TimeField.tsx:34,40,46`），旧草稿随之丢弃；等待中的回复全部以「主窗口已重新载入」结束。
   - 所有异步完成回调（回复、确认、`onNote`）在改界面前先核对「发起时的 `epoch` 等于当前 `epoch`」，不符就丢弃，防止旧回调晚到后把错误或确认写回新界面。
   - `send`（`:82-88`）用编辑**开始时**的 `epoch` 盖章，不用最新快照的值，这样旧编辑不会被盖上新世代变成合法命令。
6. 主窗口拒绝（`miniController.ts` `receive`）：`command.epoch !== ctx.mainEpoch` 时回错误并推送最新快照，不写入。`dispatchMiniCommand` 与其测试不变。不把「回复里没有 epoch」单独当成错误：`requestId` 唯一、等待表在世代切换时清空，已经挡住旧回复。
7. 同步修改 `src/app/dev/MiniPreview.tsx:15,21`（预览里用固定世代）和所有测试里的快照 / 命令字面量。
8. 不拦截 F5（用户要求保留）。

### E6 D7a 回看聚合

现状：`src/services/reviewProjection.ts` 的 `recap()` 只在有进行中的回顾时计算（完成后返回 null），且每次提交都随投影重算；只有按项目一种维度，待机和睡眠没有排除。

1. 纯函数（不含卡片、任务）放 `src/domain/timeline/recap.ts`：
   - 周期解析：7 种周期 → `[from, to)` 时间范围；「本次回顾周期」需要上次完成回顾的时刻作为参数；「自定义」由调用方给起止日期。
   - 上一期：紧接本期之前、同样天数；「本月」对比上月同期（不超过上月末）；早于最早记录时返回「不可比」。
   - 裁切与分日：先按时刻用 `clipEntriesInRange`（`stats.ts:134` 起）裁到周期内，**之后一律用它返回的 `clipped_start` / `clipped_end`**，原 `started_at` / `ended_at` 没有被替换（审核 G6）；再按活动日边界分日。不使用原型里按开始日过滤的简化做法。
   - **先修 `splitAtDays` 的夏令时错误**（审核 G6，第三轮已在 `TZ=America/New_York`、日界 2 点下复现）：`day.ts:13-17` 在同一个 `Date` 上先 `setHours(boundaryHour)` 再 `setDate(+1)`，跳时那天 02:00 不存在被规范成 03:00，次日也被带成 03:00，错一小时。改为按目标日历日期分别构造当天日界（`new Date(y, m, d, boundaryHour)`），不把被规范化的小时带到下一天。`activityDayTotals` 等现有调用方一并受益。用户所在时区没有夏令时，但修正后结果在任何时区都对。
   - 时区口径：一律用「当前本地时区 + 当前 `dayBoundaryHour`」重算回看；周期与上一期按日历日推进（`shared/time.ts` 的日历日函数），不用固定 24 小时。操作历史里已保存的 `day` 是写入时的分组键，回看不用它。
   - 系统项：默认排除「待机」「睡眠」，开关打开时计入。
   - 维度：项目；标签（多标签按 1/n 平均分摊，条数按出现次数计）；具体活动（按描述合并）。
   - 分桶：≤ 16 天按日，17–100 天按 ISO 周，> 100 天按月。
   - 并行记录（R1，用户 2026-11-04 定为**实际占用时间**）：「有效投入」是去掉待机 / 睡眠后的实际占用时长，同一时刻有几条记录并行也只算一次（与 `get_time_summary` 的覆盖时长口径一致）。算法按以下顺序，顺序不能换（审核 P5）：
     1. **先过滤**：开关关闭时，先剔除「待机」「睡眠」条目；否则与睡眠重叠的补录会被睡眠分走一半，再隐藏睡眠就会少算。
     2. **再切原子区间**：把剩下条目裁切后的 `[start, end)` 端点排序，切成互不重叠的小段；某一段被 k 条记录覆盖，每条分得 Δt / k。
     3. **再分日、分桶**：小段按活动日边界和桶边界切开后再分配，保证每根柱子之和等于当天 / 当周 / 当月的有效投入。
     4. **最后按维度累加**：每条记录分得的时长全额计入项目 / 来源 / 活动维度对应的组；标签维度再按该条的标签数 1/n 分摊（无标签归「无标签」）。
     精度（审核 G7）：内部一律用整数毫秒，不用浮点。每次「把 Δt 分给 k 份」（原子区间分给 k 条记录、一条记录的份额分给 n 个标签）都用**确定次序的余数分配**：每份先得 ⌊Δt / k⌋，余下的 r 毫秒按固定顺序（条目 ID、标签名排序）各补 1 毫秒。不在每条、每段各自四舍五入后相加。这样结果与输入顺序无关，任何层级的合计都严格相等。
     显示：时长各自格式化（HH:MM），不保证各行显示值之和等于总数的显示值，界面不做这种承诺；占比用最大余数法分配到 0.1%，保证合计显示 100.0%。图表、列表、主线卡共用同一份分配结果。
     任意开关、任意维度下，各组合计 = 柱状图各段之和 = 有效投入（整数毫秒，严格相等）。上一期对比、主线投入用同一函数。卡片的「用时」只看这张卡自己的条目，按实际占用时长算。界面在有效投入旁注明「同一时间并行的记录只算一次」。测试覆盖：与睡眠重叠的补录、三条部分重叠、跨日的并行段、多标签、1 毫秒段、1000 毫秒分 3 条、同一组输入换顺序结果相同；夏令时春季跳时与秋季重复小时、23 / 25 小时的日子、周 / 月桶边界、运行中改 `dayBoundaryHour` 后重查。
