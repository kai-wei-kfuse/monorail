### E5 D4 小窗会话标识

根因（已核对）：小窗的修订号来自每个 Ctx 的 `queue.version`（`src/services/commit.ts:75` 初始化为 0，`:213` 每次提交 +1）；主窗口重载会重建 Ctx，计数从头开始，而小窗 `src/platform/windowBus.ts:63-67` 闭包里还留着旧的高修订号，把新快照和心跳全部丢掉，3 秒后显示「主窗口未响应」。另一个隐患：旧会话的编辑命令可能碰巧带着与新会话相同的修订号，被新主窗口误接受。

1. 会话标识放在 Ctx 上：`createContext`（`commit.ts:57`）生成 `session = crypto.randomUUID()`，只读暴露。放 Ctx 而不是 `connectMini`，是为了让修订号与会话同生同灭，也避免开发模式下重复挂载产生两个会话。
2. `MiniSnapshot`（`windowBus.ts:24-33`）加 `session`；`projectMini` 或 `connectMini.push`（`miniController.ts:13`）填入。
3. 命令 `base` schema（`windowBus.ts:8`）加 `session`，所有命令都带（schema 是 `.strict()`，必须显式加）。
4. 小窗过滤（`windowBus.ts:62-69`）：保存当前 `{ session, revision }` 和已退役会话集合。退役会话的事件丢弃（防旧主窗口迟到的事件）；新会话：旧会话入退役集、修订基准重置为新快照的修订号并接受；同一会话仍丢弃更小的修订号。
5. 小窗界面（`src/app/MiniApp.tsx:35`）：收到不同会话的快照时，清掉进行中的编辑、提示和报错，把等待中的回复全部以「主窗口已重新载入」结束（不再等 5 秒超时）；`send`（`:82-88`）用当前会话盖章，编辑基准属于旧会话时不发送。
6. 主窗口拒绝（`miniController.ts` `receive`）：在调用 `dispatchMiniCommand` 前检查 `command.session === ctx.session`，不符则回错误并推送最新快照，不写入。服务层的 `dispatchMiniCommand` 与其测试不变。
7. 同步修改 `src/app/dev/MiniPreview.tsx:15,21` 和所有测试里的快照 / 命令字面量。
8. 不拦截 F5（用户要求保留）。

测试：`src/platform/windowBus.test.ts` 增加「同会话更小修订丢弃」「新会话更小修订接受」「旧会话迟到事件丢弃」；`src/services/mini.test.ts` 增加「会话不符的命令回错误、推送、无写入」。真窗口：主窗口按 F5 与更换数据目录各一次，小窗 3 秒内恢复正常（E9）。

### E6 D7a 回看聚合

现状：`src/services/reviewProjection.ts` 的 `recap()` 只在有进行中的回顾时计算（完成后返回 null），且每次提交都随投影重算；只有按项目一种维度，待机和睡眠没有排除。

1. 纯函数（不含卡片、任务）放 `src/domain/timeline/recap.ts`：
   - 周期解析：7 种周期 → `[from, to)` 时间范围；「本次回顾周期」需要上次完成回顾的时刻作为参数；「自定义」由调用方给起止日期。
   - 上一期：紧接本期之前、同样天数；「本月」对比上月同期（不超过上月末）；早于最早记录时返回「不可比」。
   - 裁切与分日：先按时刻用 `clipEntriesInRange`（`stats.ts:132-175`）裁到周期内，再用 `splitAtDays`（`day.ts:9-20`）按活动日边界分日；不使用原型里按开始日过滤的简化做法。
   - 系统项：默认排除「待机」「睡眠」，开关打开时计入。
   - 维度：项目；标签（多标签按 1/n 平均分摊，条数按出现次数计）；具体活动（按描述合并）。
   - 分桶：≤ 16 天按日，17–100 天按 ISO 周，> 100 天按月。
   - 并行记录（R1，用户 2026-11-04 定为**实际占用时间**）：「有效投入」是去掉待机 / 睡眠后的实际占用时长，同一时刻有几条记录并行也只算一次（与 `get_time_summary` 的覆盖时长口径一致）。算法按以下顺序，顺序不能换（审核 P5）：
     1. **先过滤**：开关关闭时，先剔除「待机」「睡眠」条目；否则与睡眠重叠的补录会被睡眠分走一半，再隐藏睡眠就会少算。
     2. **再切原子区间**：把剩下条目裁切后的 `[start, end)` 端点排序，切成互不重叠的小段；某一段被 k 条记录覆盖，每条分得 Δt / k。
     3. **再分日、分桶**：小段按活动日边界和桶边界切开后再分配，保证每根柱子之和等于当天 / 当周 / 当月的有效投入。
     4. **最后按维度累加**：每条记录分得的时长全额计入项目 / 来源 / 活动维度对应的组；标签维度再按该条的标签数 1/n 分摊（无标签归「无标签」）。
     任意开关、任意维度下，各组合计 = 柱状图各段之和 = 有效投入。上一期对比、主线投入用同一函数。卡片的「用时」只看这张卡自己的条目，按实际占用时长算。界面在有效投入旁注明「同一时间并行的记录只算一次」。测试覆盖：与睡眠重叠的补录、三条部分重叠、跨日的并行段、多标签。
2. 需要卡片、任务的部分放 `src/domain/review/recap.ts`（src/domain/review 可以引用 timeline、card、task）：
   - 「任务来源」维度：条目 `card_id` → 卡片 → 任务。已完成卡用 `completed_track`；未完成卡用当前 `trackOf(task_id, tasks)`；无卡为「自由活动」；`kind === '插入'` 为「临时离开」。
   - 完成的卡：`completed_at` 在周期内；用时为周期内该卡条目的裁切后时长。
   - 做到哪了：`progress_noted_at`（缺省用 `completed_at`）在周期内的卡。**每张卡只保存最新一条笔记**（`progress_note` 会被覆盖），同一张卡早先的笔记查不到；这是现有数据模型的限制，本版不改。
   - 主线投入：主线任务时长 / 有效投入；与上一期的百分点差。
3. 服务 `src/services/recapService.ts`：`query(ctx, { period, from?, to?, dim, includeIdle })` 从内存中的计时索引读取（`timelogV2Repo` 启动时已全部载入），**不做** `queryRange` 那样的 `structuredClone`，聚合函数不修改输入。
   - 上次完成回顾的时刻：回顾完成后 `ReviewSlice` 为 `null`（`reviewProjection.ts:52-55`），挂不了字段；`Snapshot`（`commit.ts:25-28`）也没有 `reviews`。因此在 `Snapshot` 加 `reviews: Review[]`（提交时已在内存载入，与 `cards`、`tasks`、`records` 一致），`recapService.query` 用 `ctx.snapshot()` 的 `reviews`、`state.first_used_day`、`settings.dayBoundaryHour` 调 `recapStart` 算出，不改 `ReviewSlice` 的 `null` 语义（审核 P6）。
4. 移除 `projectReview()` 里每次提交都算的 `recap()`，`RecapData`（`src/pages/review/Recap.tsx:5-9` 与 `src/store/reviewSlice.ts:3-7` 两处重复）改为新的查询结果类型，放 `src/shared`。同步改 `src/app/dev/M3Preview.tsx:21-48`（它依赖 `ReviewData.recap`）。

**E8a 基础设施（逻辑线）**

1. `src/shared/history.ts`：记录 schema（`version: 1`）、动作 ID 联合类型与中文名表、来源类型、调用方显示名对照表。
2. `src/data/historyRepo.ts`（审核 P2、P7）：
   - 路径生成与校验：`history/<day>/<HHmmssSSS>-<id>.json`，经 `safeRelative`。
   - `write(record)`：生成新文件的 write（`before = null`），同时返回落盘文本 `rawText` 与路径，供设置合并使用。
   - `rewrite(prev, next)`：设置合并用。**沿用上一条的原路径** `prev.path`，`before` 传上一条**实际落盘的原文** `prev.rawText`，即 `createWrite(prev.path, nextRawText, prev.rawText)`；`Journal.run` 会逐字节核对 `before`（`journal.ts:24,34`），不一致会抛 `External edit` 并让提交队列进入故障状态。
   - 列表与清理都只调**一次** `fs.list('history', true)`，在内存里按路径中的 `<day>` 过滤：`listDays(fromDay, toDay)` 只读命中的文件，坏文件计数返回；`removeDaysBefore(cutoff)` 逐个文件 `fs.remove`（不经 journal）。不按目录名调 `remove`：`MemoryFs.remove` 只认文件（`memoryFs.ts:15-17`），`tauriFs.remove` 不带 `recursive`（`fs.ts:91`），删非空目录会失败。

4. `src/services/commit.ts`：

   - 设置合并（审核 P2）：在 Ctx 内存中保存上一条设置历史 `{ path, rawText, record, committedAtMs, settingKey, sourceKey, day }`。同时满足以下条件才合并，否则写新文件：同一设置项、同一来源、活动日未变、本次改的不是 `dayBoundaryHour`、距上一条 ≤ 60 秒。合并时用 `historyRepo.rewrite` 原地改写（更新 `at`、改后值与 `merged`，保留首次的改前值）。只在 `transact` 成功后才更新内存中的 `rawText`；提交失败或重载后指针清空，下一次写新文件。
