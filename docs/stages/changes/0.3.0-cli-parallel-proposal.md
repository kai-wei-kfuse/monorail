## Stage Change Proposal

状态：Accepted v1.1 · 2026-11-03。用户明确要求 0.3.0 完成统一接口层、MCP、CLI，制定方案后交 coder-3 执行。当前实施依据为 `docs/application/0.3.0-execution-plan.md`、ADR 0014 与 0.3.0 Current Plan v1.9。

### Problem

当前 0.3.0 已实现并修复 MCP 核心能力，但没有 CLI。可复用边界已有 DesktopClient 与应用请求分派，契约仍称 McpRequest/shared/mcp，Node 客户端位于 mcp/，输出验证和错误到 MCP 响应的映射仍在适配器内。需要确认它们是真正可共用的应用接口，而不是让 CLI 依赖 MCP 协议。

用户提出的选项 1“两个一起开发”与选项 3“一起做好统一层和 CLI”交付目标基本相同。关键在于交付范围和内部顺序，而不是两条代码线必须同时开写。

### Why It Matters

CLI 是已经明确的第二个消费者，能够实际检验接口层是否有 MCP 专用假设。仅抽象公共层而不实现 CLI，无法验证终端输入、自动化输出、状态令牌和错误处理是否好用。

现有业务、journal、回执、后台启动与验证资产应保留；新 CLI 不得建立第二个写入者或重复业务判断。未来手机端属于不同平台/同步课题，不据此提前建设万能跨端框架。

### Options

| 选择 | 内容 | 判断 |
|---|---|---|
| MCP 内继续包含通用客户端，CLI 经 MCP 或调用 CLI 子进程 | 少做目录调整 | 不符合并列入口目标，也增加协议/进程转换 |
| 0.3.0 仅整理公共层与 MCP，CLI 延后 | 当前交付较小 | 可用，但公共接口缺第二消费者验证 |
| 本版交付公共应用接口 + 现有 MCP + 最小 CLI | 用真实 CLI 验证公共层，保留现有实现 | 推荐；范围仅覆盖已经确定的核心能力 |

### Decision

采用第三项：**0.3.0 两个入口一起交付，内部先统一接口，再实现 CLI，最后交叉验收。** 不需要重写已验证的业务，也不要求先完整开发 CLI 再做 MCP。

公共接口不是 HTTP/stdio/named pipe 之一。它是应用命令、输入输出、错误与提交语义；通信方式是可替换的适配实现。

推荐职责：

```text
MCP adapter ─┐
             ├─ 公共应用客户端 ─ 本机连接 ─ 单轨应用请求入口 ─ 业务服务/commit/journal
CLI adapter ─┘
```

### Impact

1. 公共契约：将业务命令与 schema 从 shared/mcp 明确归入传输无关的 application 契约；包含请求、成功/错误结果、operation_id、状态令牌。MCP 工具描述/annotations 留在 MCP adapter。
2. 公共客户端：承接 DesktopClient、pipe/后台连接、结果验证和共享错误，提供可确定输入/输出类型的调用接口；不以 Promise<unknown> 作为最终公共 API。不要再复制一套 validation。
3. 桌面请求入口：将 handleMcp 的应用请求分派职责明确为 Application API，继续依赖原服务与同一事务队列。Node CLI 不直接导入并初始化桌面 service context 写文件。
4. MCP adapter：保持已发布/已确定的工具名字和语义，只负责协议工具注册和响应格式；继续支持新旧协议。
5. CLI adapter：解析 flags/subcommands，调用公共客户端，默认人类可读，--json 提供稳定机器结果；诊断到 stderr，退出码有明确契约。结果和错误不能伪造成功。

目录位置以实际边界和 lint 规则决定；不是简单重命名，也不新增一层与现服务平行的业务实现。

### CLI 首版范围

- 想法保存、待办捕捉、查找。
- 当前状态、今天/指定日期/本周时间摘要、显式区间明细。
- 普通/指定待办计时、暂停/继续/停止、临时离开与回来、补录。
- 操作结果核对。

对应现有核心业务能力。命令形式可为 `monorail idea add`、`monorail todo add`、`monorail timer start/pause/resume/stop`、`monorail time today`，不要求与 MCP 工具数量一一对应。

CLI 默认自动取得上下文/状态令牌，不让终端用户手抄 UUID。自动化写操作允许传入稳定的 --operation-id；同一次重试沿用 ID，不自动换新 ID。结果未知时输出原 ID 和可核对命令。自动获得上下文与实际写入之间仍需服务端事务内校验；冲突时不偷偷刷新后强行执行。

不增加第二批复杂任务整理、批量删除、账户/手机同步、云部署、交互式 TUI 或自动补全等附加范围。
