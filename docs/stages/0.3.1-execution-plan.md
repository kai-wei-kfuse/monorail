## 2. 做法要点

### G1 兼容锁定
- 冻结：把当前 `schemas.ts` 里的 `cardSchema / recordSchema / taskSchema / settingsSchema`、`stateRepo.ts` 里的 `stateSchema`、`historyRepo.ts` 的记录 schema 拷到 `src/data/migrations/v030/`（文件头注明来源 tag `v0.3.0`、提交 `23d6240`，以后不改），同 `migrations/v1/` 的做法。当前 `src/` 与 tag `v0.3.0` 相同（`git diff --stat v0.3.0 HEAD -- src mcp cli` 为空），所以拷当前文件即可。
- 测试 `src/data/migrations/v030/compat.test.ts`：
  1. 拆分后的 `today`（改了内容和时长）、`rest`（`shrunk_from` 指向非 `已缩小` 卡、带 `split_note`）过 0.3.0 `cardSchema`，`split_note` 在解析结果里保留；照抄 0.3.0 `restoreInTx` 的判断（`cardService.ts:22-27`）完成 `rest`，父卡不变。
  2. 「待机 / 插入」条目 + `resume_entry_id` 指向带 `card_id` 的普通条目，过 0.3.0 的 `entrySchema` 和 `stateSchema`，`assertEntries` 不抛。
  3. 带四个新键的设置文件过 0.3.0 `settingsSchema`、写回仍带这些键。
  4. 板子改动记成 `type: card / state` 的历史记录过 0.3.0 历史 schema。
  5. 0.3.0 的 `shrinkCard`（照抄进 `v030/`，纯函数）处理带 `split_note` 的 `rest` 卡：子卡带着 `split_note`、父卡变 `已缩小`（ADR 第 4 条的提示规则靠这一点区分）。
- 锁定失败就先改 ADR 0021，后面不开工。

### G2 今日任务板数据与换日
- **`CLAUDE.md` 方向表先补**（公共文件，交接里说明）：`dealService` 读 `planService`（只读）；`homeService` / `cardService` 调 `planService` 的 InTx（开始卡时清 `skip_until_planned`、缩小改量、接着做不动）；`newDay()` 调 `planService.rolloverInTx`；`planService` 只依赖 domain 和 tracking/api 的只读查询（今天已计），不调别的 service。卡离开背包不写板子（ADR 第 1 条派生过滤），所以没有 `backpack / review → plan`。
- `domain/plan/plan.ts`（纯函数）：`minutesToday(entries, cardId, day, boundary, at)`（按活动日切，用已修好夏令时的 `splitAtDays`）、`achieved(item, card, minutesToday)`、`visibleItems(plan, cards, tasks)`、`candidates(...)`、`carryFrom(source, today, cards, tasks, minutesToday, running)`、`dueOn(card, day)`（只标那天到期，已定 16）。
- `planService`：`add / remove / edit / skipToday / skipCard / confirmCarry`（根动作 + InTx）；`rolloverInTx`；`dropMissingInTx` 不做（派生过滤）。
- `Transaction` 建立时预读今天的板子（`tx.todayPlan`），明天和更早的 `await tx.plan(day)` 懒读（ADR 第 1 条）。
- `newDay()`（`bootstrap.ts:84-89`）：`expireInTx` → 0.3.0 `state.rest` 一次性处理 → `rolloverInTx` → `refreshInTx`。启动和 `scheduler` 换日都走这里；`rolloverInTx` 靠 `plans/` 的 `rolled_over` 每个活动日只做一次，在计的卡、插入中结束原任务只在开着的那一条开始于今天活动日起点之前时做（ADR 第 6 条，第 2 轮 B2）。带过去记在 `system.dayChange` 这一条历史里。
- 单测：同一天第二次 `newDay()` 什么都不改；前一晚排了明天，第二天带过去照样执行一次；从抽屉直接开始一张没排的卡、同一天重启，不被加进板子。
- `planProjection`：今天、明天两块板子的行（MAIN/SIDE、名字、优先级、今天已计 / 今天的量、达成、到期标红、正在计、带过来待确认）；提交后整块重算，心跳只更新正在计那一行（R5）。
- 历史：`shared/history.ts` 登记 ADR 第 11 条的动作；`historyCapture` 加 `plans` 前后比较，输出 `card` / `state` 类型的改动。
- 保留期：`historyService.maintain` 的清理加 `plans/`，同 180 天。

### G6b 宽松 / 紧凑模式（已定 58、59，ADR 第 13 条）
- 数据不变：任何时刻有且只有一条在计时，待机照记。
- `homeProjection`：宽松模式下，开着的是 `待机`（含暂停）时输出 `idle: true`，首页读数不走、写「没在计时」，标题栏状态灯灰。
- 日历、列表（`TimeScreens.tsx:51` 的 `showIdle`）：宽松模式下恒为 false。回看（`recapService` / `domain/review/recap.ts`）：宽松模式下待机不计，「含待机 / 睡眠」开关只剩睡眠。
- 离线结算 `settleOfflineInTx`（`timerService.ts:61-67`、`homeService.ts:102-108`）：宽松模式下这段记成 `待机`、不推 `offlineAsk` 通知；紧凑模式不变。
- 空闲追问（紧凑模式）：开始下一件事的事务里，如果刚结束的那条是待机或暂停、且长于 `idleAskMinutes`，推一条新通知 `idleAsk`（`widgets/notices/` 照 `OfflineAsk.tsx` 做），填了就 `timeEditService.patch` 把那段待机改成这项，历史 `home.answerIdle`；忽略不写盘。
- 单测：两种模式的投影、日历 / 回看过滤、离线结算、追问阈值（刚好等于、短于、长于）、切换模式不改数据。
- 宽松模式首页空闲的样子和空闲追问通知没有原型：G7 前用 gallery 截图给用户确认。
