# 版本开发流程

给新开的会话用：接手单轨的下一个版本时，先读这一份。路径相对 `app/`，`../` 是上级目录 `1026(4)/`。

## 1. 开工先读

1. `CLAUDE.md`：分层、事务方向、术语、验证约定。必须遵守。
2. `../架构设计.md`、`../像素记录系统 设计文档 v0.3.md`：系统结构和产品规则。
3. `../UI风格规范.md`、`../原型/原型说明.md`：界面规格。原型页面在 `../原型/页面/`，测试在 `../原型/测试/`。
4. 当前版本的计划和分工文档（例如 `../二期开发计划 0.2.0.md`、`../二期分工-Astra.md`），以及上一版的 `evidence/<阶段>-summary.md`：看还有哪些没做、没测。
5. `docs/updates.md`：版本号、CI 和发版。
6. `git status`、`git log --oneline -10`：确认工作区状态。`evidence/journal-real.json` 常有别人的改动或测试写入，不要提交，也不要回退。

`../归档/` 里是一期设计和早期审查，只在追溯历史时看。

## 2. 版本类型

| 类型 | 例子 | 内容 | 发版前要求 |
|---|---|---|---|
| 补丁版 | 0.2.1 | 只修 bug，不改数据格式 | `npm run check`，相关冒烟条目 |
| 小版本 | 0.3.0 | 新功能 | 完整收尾（第 6 节） |
| 带迁移的版本 | 改 `schemaVersion` | 数据格式变化 | 加做迁移演练和回退说明（第 5 节） |

补丁版可以直接从第 4 节做起，修完就走第 7 节发版，不必等功能攒齐。

例外：0.3.1 按用户决定（2026-11-05）放任务卡 RPG 化，有新功能和新数据目录 `plans/`（不改 `schemaVersion`），版本号用 0.3.1，但按小版本的要求做完整收尾。最初安排先发 Beta，用户 2026-11-06 改定直接正式版 0.3.1（当前计划已定 70）。见 `docs/stages/0.3.1.md`。

## 3. 规划（小版本和带迁移的版本）

1. 写计划 `../<期数>开发计划 <版本>.md`。每一项写清：做什么、怎么算做完、归哪条线、依赖哪项。计划按阶段编号（N1、N2…），后面的提交和 evidence 都用这个编号。
2. 交互有变化的，先改原型和 `UI风格规范.md`，用户看过截图同意后再写代码。截图放 `../UI参考截图/`，文件名带版本前缀，例如 `v0.3-01-…`；过时的移进子目录，不要删。
3. 两条线分工，写进交接文档 `../<期数>分工-<名字>.md`：
   - 逻辑线：`src/domain`、`src/services`、`src/data`（含迁移）、`src/store`、`src/platform`、`src-tauri`。
   - UI 线：`src/pages`、`src/ui`、`src/widgets`、`src/app`。
   - 两条线先在交接文档里约定好 service 接口和 store 投影，再各自实现。改公共文件（`src/shared`、`package.json`、CI、`CLAUDE.md`）前，先在交接文档里说明。
4. 版本号在开工时就改：`npm run version:set -- <版本>`。

## 4. 每项改动

1. 一个功能或一个修复一个提交。提交信息格式 `feat(n4): …` / `fix(n3): …` / `docs(n7): …`。
2. 逻辑改动带单测（Vitest，node 环境，只测逻辑）。不写类型镜像测试，不写导出列表测试。
3. UI 用 `gallery.html?page=live`：内存数据加真 service。配无头浏览器截图，和原型截图对照。不要反复开真程序，除非这一项只能在真窗口里验证；只能真窗口验证的，记进收尾清单。
4. 提交前跑 `npm run check`（tsc → eslint 分层与无环 → vitest），失败不提交。
5. 只暂存自己负责的文件：`git add <路径>`，不用 `git add -A`。

## 5. 数据格式变化

1. 迁移写在 `src/data/migrations/`。旧版读法冻结在旧版本目录里，以后不再改动。
2. 迁移前先备份到 `backup/v<旧>-<UTC时间>-<编号>/`，逐个读回比对，然后用一份 journal 切换。参照 v2 的实现。
3. 演练：把用户真实数据目录拷进内存或临时目录，用当前代码迁移，再核对任务、卡、条目的数量和内容。全程只读真实目录。结果写进 evidence。
4. 写 `docs/releases/<版本>-回退.md`：备份在哪、回退会丢什么、手动回退步骤、实际验证到哪一步。
5. 发版前要用旧版安装包做一次应用内更新到新版，冒烟测试的第 9 条就是测这个。

## 6. 收尾

1. 写 `evidence/<阶段>-summary.md`：检查结果、构建结果、迁移演练、UI 对照、冒烟测试表、没做的事。**没实测的写「未测」，不能写成通过。**
2. 构建：`npm run tauri -- build --debug --no-bundle`，日志存进 evidence。
3. Windows 冒烟测试（`../架构设计.md` §8 的 12 条）：**在发版前做完**，至少把这一版改到的条目测过。0.2.0 是先发版再补测，这次不要这样。
4. 写发版说明 `docs/releases/<版本>.md`，给用户看：说做了什么，不讲实现。这份文字会出现在应用内的更新说明里。

## 7. 发版

照 `docs/updates.md` 做，要点：

1. `npm run version:check`、`npm run check`。
2. 从 master 的最新提交打 tag `v<版本>`，先推 master，再推 tag。CI（`.github/workflows/release.yml`）会检查、签名构建并发布。
3. **打 tag 时，tag 指向的提交里的 `release.yml` 必须和默认分支上的一致**，否则发布这一步会被 GitHub 拒绝（`403 Resource not accessible by integration`，见 `evidence/release-0.2.0/ci-recovery.md`）。改 CI 的提交要先推到 master，再在它之后打 tag。
4. CI 失败时先查日志。不要覆盖或删除已有的 tag 和 Release。只是工作流环境问题、源码不用改的，按 `docs/updates.md` 用 `workflow_dispatch` 加原 tag 重跑；发布被拒的，用 `publish=false` 只构建，再用本机 gh 登录发布。
5. 核对 Release：有安装包、`.sig` 和 `latest.json`；`latest.json` 里的版本号正确；不是草稿，也不是预发布。
6. 在本机设置 → 关于 → 检查更新，确认能更新到新版。结果记进 `evidence/release-<版本>/`。

## 8. 交接

会话结束或换人时，把以下几项写进交接文档：做到哪一步、哪些没测、哪些文件有未提交改动及其归属。下一个会话从第 1 节开始读。
