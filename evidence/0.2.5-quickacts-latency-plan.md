## 1. 根因定位与精确调用链计数（按首审校正）

点击快捷活动（`QuickActs` -> `actions.startPreset(id, at)` -> `homeService.startPreset` -> `commit.run`）出现约 1 秒卡顿感，由 **UI 层硬编码 650ms 延迟** 与 **事务提交前仓库层的逐文件串行读取/解析及路径 IPC 往返** 两部分共同组成，两者职责与边界严格区分如下：

### 根因 A（已由 UI 方案 A 修复）：`QuickActs.tsx` 硬编码了 `650ms` 弹层关闭定时器
- **位置**：`src/app/shell/QuickActs.tsx:40, 49`
- **现象与影响**：
  1. 原代码 `const pick = (fn: () => void) => { fn(); setTimeout(() => setOpen(false), 650); };` 强制让弹层在点击后至少等待 **650ms** 才调用 `setOpen(false)`，且快速重开弹层时会被未清理的旧 timer 意外关闭。
  2. 移除该 `650ms` 定时器（`const pick = (fn: () => void) => { setOpen(false); fn(); };`）已直接消除弹层关闭的人为等待；但**右上角临时活动抽屉（`AwayDrawer`）与底栏活动名仍由真实事务提交后更新的 `appStore` 投影驱动**，不使用未提交的业务状态假装已开始。

### 根因 B（v1.2 已完成）：每次 `commit.run()` 内各 `MdRepo.list()` 内部逐文件串行读取/解析，且 `tauriFs` 路径处理触发多余 IPC
1. **四类实体目录并行、但每个目录内部逐文件串行（`src/services/commit.ts:97`、`src/data/mdRepo.ts:21-28`）**：
   - `commit.ts:97` 已使用 `Promise.all([cards.list(), tasks.list(), reviews.list(), records.list()])` 并行发起四个目录的读取（四个目录之间并行，非四目录串行）。
   - 但在每个 `MdRepo.list()` 内部，代码使用 `for (const path of ...) { ... await this.get(id); }` **逐个 `.md` 文件串行等待**磁盘读取，并对每个文件无条件执行 `frontmatter.decode`（YAML 解析）与 `this.schema.parse`（Zod 校验）。
2. **`tauriFs.read` 的真实 IPC 调用数与依赖阶段（`src/data/fs.ts:18-26`）**：
   - 已核对安装的 `@tauri-apps/api/path`（`path.js:731-733, 745-747`）：`join` 与 `dirname` 均通过 `invoke('plugin:path|...')` 调用原生端，不是纯前端字符串函数。
   - 当前读取一个**已存在**的文件共发生 **4 次 IPC 调用、4 个串行依赖阶段**：
     1. `await resolve(path)` -> `invoke('plugin:path|join')`
     2. `await fs.exists(full)` -> `invoke('plugin:fs|exists')`
     3. `await fs.stat(full)` -> `invoke('plugin:fs|stat')`
     4. `await fs.readTextFile(full)` -> `invoke('plugin:fs|read_text_file')`
   - 拟用本地路径函数替换 `join` 并对已存在文件并行执行 `Promise.all([fs.stat(full), fs.readTextFile(full)])` 后，单次读取已存在文件将变为 **3 次 IPC 调用（`exists`、`stat`、`readTextFile`）、2 个依赖阶段（阶段 1：`exists`；阶段 2：`stat` 与 `readTextFile` 并行）**；`atomicWrite` 则消除 `join` 与 `dirname` 2 次路径 IPC。
   - *注：v1.0 中提到的“60 个实体、240+ 次调用、400–800ms”仅作为说明规模效应的算例假设，不能替代实测数据；且四个目录本身并行，并行化 `MdRepo.list()` 缩短的是每个目录内部的串行 I/O 等待链，JS 主线程上的 YAML/Zod 解析与缓存命中时的 `structuredClone` 仍各自有 CPU 开销，需通过第 3 节的分阶段实测验证。*

## 2. 修订后的低层优化方案（对应 [ADR 0007](../docs/adr/0007-mdrepo-parse-cache-and-local-path-resolution.md)）

### 2.1 UI 层：`src/app/shell/QuickActs.tsx`（已完成实现与测试）
- 采用主审决定的 **方案 A**：将 `pick` 改为 `const pick = (fn: () => void) => { setOpen(false); fn(); };`，覆盖活动磁贴点击、数字键 `1–9`、「睡觉」磁贴与 `TempRow` 临时活动表单提交。
- 不引入 `120ms` 新定时器，不在 `appStore` 放未提交乐观状态，保留点击时刻 `at = new Date().toISOString()`，事务失败继续通过既有 `report` 报错。

### 2.2 平台文件层：`src/data/fs.ts`（Windows/POSIX 根路径等价的本地路径函数 + 2 阶段读取）

针对首审指出的 v1.0 `cleanRoot/parentOf` 在 Windows 盘符根（`C:\`、`C:/`）与扩展盘符根（`\\?\C:\`）下丢失根分隔符退化为 `C:` / `\\?\C:` 的反例，重新定义 `src/data/fs.ts` 内的本地路径辅助函数契约（只服务当前数据层，不引入外部路径框架，不静默回退原生 IPC）：

v1.2 实施采用以下源码；v1.1 候选片段由 Accepted ADR 0007 修订替代。相对盘符根显式拒绝，并保留扩展卷前缀。

```ts
interface RootSplit { root: string; rest: string; sep: '/' | '\\' }

/** Configured data directories are absolute, as required by save_config. Keep volume roots intact. */
function splitRoot(path: string): RootSplit {
  const sep = path.includes('\\') ? '\\' : '/';
  let match: RegExpExecArray | null;
  if ((match = /^([\\/]{2}[?.][\\/]UNC[\\/][^\\/]+[\\/][^\\/]+)(?:[\\/](.*))?$/i.exec(path))) {
    return { root: match[1].replace(/[\\/]/g, sep), rest: match[2] ?? '', sep };
  }
  if ((match = /^([\\/]{2}[?.][\\/][A-Za-z]:[\\/])(.*)$/.exec(path))) {
    return { root: match[1].replace(/[\\/]/g, sep), rest: match[2], sep };
  }
  // Extended volume paths need their namespace prefix even when they have no drive letter.
  if ((match = /^([\\/]{2}[?.][\\/][^\\/]+[\\/])(.*)$/.exec(path))) {
    return { root: match[1].replace(/[\\/]/g, sep), rest: match[2], sep };
  }
  if ((match = /^([\\/]{2}(?![?.][\\/])[^\\/]+[\\/][^\\/]+)(?:[\\/](.*))?$/.exec(path))) {
    return { root: match[1].replace(/[\\/]/g, sep), rest: match[2] ?? '', sep };
  }
  if ((match = /^([A-Za-z]:[\\/])(.*)$/.exec(path))) {
    return { root: match[1].replace(/[\\/]/g, sep), rest: match[2], sep };
  }
  if ((match = /^\/+(.*)$/.exec(path))) return { root: '/', rest: match[1], sep: '/' };
  throw new Error(`Data directory must be absolute: ${path}`);
}

function buildPath({ root, sep }: RootSplit, segments: string[]): string {
  if (!segments.length) return root;
  return `${root}${root.endsWith(sep) ? '' : sep}${segments.join(sep)}`;
}

export function resolveLocal(base: string, relative: string): string {
  safeRelative(relative);
  const parts = splitRoot(base);
  return buildPath(parts, [...parts.rest.split(/[\\/]+/).filter(Boolean), ...relative.split('/').filter(Boolean)]);
}

export function parentLocal(path: string): string {
  const parts = splitRoot(path), segments = parts.rest.split(/[\\/]+/).filter(Boolean);
  segments.pop();
  return buildPath(parts, segments);
}
```

- **契约与边界验证**：
  1. `safeRelative(path)` 边界完全保持不变；`resolveLocal(baseRoot, relative)` 始终先校验 `safeRelative(relative)`。
  2. 当 `baseRoot` 为 `'C:\\'`、`'C:/'` 或 `'\\\\?\\C:\\'` 且 `relative` 为 `'settings.yaml'` 时，`parentLocal(resolveLocal(baseRoot, relative))` 分别返回 `'C:\\'`、`'C:/'` 与 `'\\\\?\\C:\\'`（均为 `win32.isAbsolute === true` 且与 `win32.dirname` 归一化结果完全一致）。
  3. 已通过只读验证脚本 [quickacts-path-v2-check.mjs](quickacts-path-v2-check.mjs) 核验 42 组 Windows/UNC/扩展盘符/POSIX/Unicode/空格路径与非法相对路径拦截，日志见 [0.2.5-quickacts-path-v2-check.log](0.2.5-quickacts-path-v2-check.log)，退出码 `0`。
  4. `tauriFs.read(path)` 在 `if (!await fs.exists(full)) return null;` 之后执行 `const [info, text] = await Promise.all([fs.stat(full), fs.readTextFile(full)]);`。明确声明：`stat` 与 `readTextFile` 并行不是操作系统级原子快照（原串行实现亦非原子快照），若读取期间文件消失或任一调用失败，按原样抛出错误，外部修改仍由 `version`（`mtime:size`）与 `Journal.before` 校验保障。

### 2.3 仓库层：`src/data/mdRepo.ts` 与 `src/data/timelogV2Repo.ts`（缓存双重隔离与 5 条生命周期不变量）

1. **`MdRepo` 实例级解析缓存契约（详见 [ADR 0007](../docs/adr/0007-mdrepo-parse-cache-and-local-path-resolution.md) §2）**：
   - **每次必读盘**：`get(id)` 始终先调 `const file = await this.fs.read(path)`。
   - **缺失即清理**：若 `!file`，立即 `this.cache.delete(id)` 并返回 `null`。
   - **命中返回深拷贝**：若 `cached && cached.version === file.version && cached.text === file.text`，返回 `{ ...cached, value: structuredClone(cached.value) }`。
   - **首次解析同样深拷贝隔离**：若未命中或 `(version, text)` 变化，执行 `decode(file.text, path)` 与 `this.schema.parse(parsed.meta)`；成功后将 `{ value: structuredClone(parsedValue), body: parsed.body, ...file }` 存入 `this.cache`，并向调用方返回本次独占的新解析值 `{ value: parsedValue, body: parsed.body, ...file }`，确保**首次调用方修改返回对象（含 `.passthrough()` 嵌套未知字段）也绝不污染缓存**。
   - **异常清理与原样传播**：若 `decode` 或 `this.schema.parse` 失败，先 `this.cache.delete(id)` 再抛出 `${path}: invalid entity`，绝不返回旧缓存；若 `this.fs.read` 抛错同样原样抛出。
   - **`list()` 并行读取与陈旧键清理**：枚举当前目录 `.md` 文件后，先删除 `this.cache` 中不在当前目录列表内的键；再用 `Promise.all(paths.map(...))` 按原序并行调用 `this.get(id)`，若任一文件返回 `null` 则抛出 `Entity disappeared: ${path}`（不用 `allSettled` 吞错）。
   - **未提交 `write`/`remove` 不触碰缓存**：`write()` 与 `remove()` 只做 `mtime` 校验并生成待提交 `Write`，不预写或失效缓存。
2. **`TimelogV2Repo.writes()` 局部分组 `push`**：
   - 在 `writes()` 内部仅对新建的局部 `groups` `Map` 桶数组执行 `push(entry)`，不修改输入 `entries`，不修改已提交 `this.index`，保持条目顺序与变化日比较逻辑不变。

### 3.2 分阶段性能基线与对比方案
为严格区分「删除 650ms 定时器」与「底层事务提交提速」，在独立测试数据副本 / 验证入口（**绝不操作或重启用户正在手测的隔离窗口，不读取或修改日常数据，不拿合成 sleep 冒充真实 Tauri IPC**）采集以下指标：
1. **记录数据规模**：测试副本中的 `cards`、`tasks`、`reviews`、`records` 文件数及 `timelog` 天数/总条目数。
2. **记录文件/IPC 调用计数**：单次 `startPreset` 事务中 `fs.list`、`fs.read`（含 `exists`/`stat`/`readTextFile`）、`fs.atomicWrite`、`decode`/`schema.parse` 的实际调用次数（优化前 vs 优化后）。
3. **记录冷启动首轮（Cold）与热缓存次轮（Warm）的 5 个分阶段耗时**：
   - `stage1_clickToTrayCloseMs`：原计划测量点击至可见帧；实际 DOM 回归证明移除 650ms 定时器等待，不声称屏幕绘制耗时为 0ms；
   - `stage2_commitQueueWaitMs`：进入 `commit.run` 互斥队列的排队等待耗时；
   - `stage3_repoReadAndParseMs`：实际记录 state 读取与四类实体列表读取/解析；每次事务使用 ctx.settings，不额外重读 settings；
   - `stage4_timelogAndJournalWriteMs`：`timelog.writes()` + `journal.run()` 原子落盘耗时；
   - `stage5_publishToDrawerVisibleMs`：`ctx.publish()` 更新 `appStore` 到右上角 `AwayDrawer` 渲染可见耗时。

v1.2 验证完成：实际 driver 将写计划、Journal、投影至 publish 分开记录；没有挂载 UI，因此 publish→可见帧未测，不能把计划指标写成通过。18/180 实体热轮次中位事务耗时 347.9→207.2ms / 1942.4→767.8ms，计数与分阶段原始数据见最终审核。当前计划 v1.22，P2d 已完成，桌面手测由用户继续。
