# 0.3.3 存储评估（只读）

日期：2026-11-08。仓库 `app`，版本事实来自已发布 0.3.2 源码。未读用户数据目录，下面没有真实正文。不设字数上限，不引入同步框架。这不是执行方案。

## 当前事实

### 文件格式

一条想法或待办是一个文件：`records/<id>.md`（`src/services/operation.test.ts:35`，`src/data/repos.ts:62`）。YAML frontmatter 加可选正文。解码用第一个顶格 `---` 结束 frontmatter；结束线之后再出现 `---` 仍算正文（`src/data/frontmatter.ts:6-14`，`src/data/frontmatter.test.ts:6-8`）。

记录 schema 的可见字段是 `text`、`kind`（待办/想法）、标签、附件路径、想法池状态、`needs`。没有标题字段，也没有详情字段（`src/data/schemas.ts:12-16`）。卡片是 `cards/<id>.md`，标题在 frontmatter 的 `content`。任务是 `tasks/<id>.md`，标题在 `name`。这两类写入没有把字段抄进正文的回调（`src/services/commit.ts:285`）。

### 正文现在不是空的，也不是独立详情

快速记录条把整条记录编码成文件，正文参数就是 `value.text`（`src/app/QuickBarApp.tsx:18-20`）。服务端提交时，新建记录或 `text` 变了，正文写成 `record.text`；`text` 没变则保留原正文（`src/services/commit.ts:287-288`）。`editIdea` 改 `text` 后，正文变成新的 `text`（`src/services/ideaService.test.ts:94-105`）。只改池状态、需要这类元数据时，已有正文会留下。

所以现有文件是同一段话存两遍：YAML 的 `text`，以及 frontmatter 后面的正文。不是「正文空着，可以随便拿来当详情」。若以后把详情放进正文，必须改掉这两处抄写，否则改标题会把详情盖成标题。

当前 `yaml` 的 `stringify` 把多行 `text` 写成缩进块标量。用 `para\n---\nmore` 试编码，缩进后的 `---` 没有被 `frontmatter.ts` 的顶格规则截断。这只说明今天的序列化碰巧避开了解码器的结束线。解码器本身不认识 Markdown。长文放在结束线之后，走的是 `frontmatter.test.ts` 已经覆盖的路径。

链接没有单独字段。写在 `text` 里就是普通字符。附件是文件，路径必须在 `attachments/` 下（`src/data/schemas.ts:8-15`）。快速记录先写附件再写记录；中间崩溃会留下没有记录指向的附件，不会留下指向空文件的记录（`src/app/QuickBarApp.tsx:25-35`，`src-tauri/src/lib.rs:104-111`）。

### 加载

每次提交都 `list()` 全部卡片、任务、回顾、记录（`src/services/commit.ts:284`）。`MdRepo.list` 读目录里每个 `.md` 的全文，缓存按文件版本和全文命中（`src/data/mdRepo.ts:8-40`）。提交后的内存快照保住全部 `RecordEntry`，其中有 `text`，没有正文（`src/services/commit.ts:392-396`）。背包投影再抄一份想法的 `text`：活跃池和已转任务、全部已完成、冷库里最旧的两条（`src/services/backpackProjection.ts:82-90`，`src/domain/idea/pool.ts:55-58`）。

计时日志不在这条路径上。启动时 `scan` 进内存，之后提交用内存快照（`src/app/bootstrap.ts:28`，`src/services/commit.ts:283`）。

`find_items` 只读已提交快照，匹配想法的 `text`、标签、`needs`，不读正文（`src/app/applicationController.ts:289-314`、`:620` 一带）。

活跃想法池按条数，不按字数：默认 10，设置范围 3–50（`src/shared/settings.ts:21`）。到期默认 60 天进冷库，文件仍在（`src/shared/settings.ts:22`，`src/domain/idea/pool.ts:51-53`）。历史性能测试写过 2000 条想法，那是测量用量，不是产品上限（`src/services/history.perf.test.ts:18-21`）。

界面上的「一行」：快速记录条 Enter 保存，Shift+Enter 换行，最高约 10 行（`src/pages/quickbar/QuickBar.tsx:15`、`:41-45`）。回顾里的新想法是单行框（`src/pages/review/NewIdeas.tsx:12`）。契约 `save_idea` 的 `text` 写明支持多行，没有最大长度（`src/shared/application.ts:20-24`）。`capture_todo` 同样只有一个 `text`（`:42-48`）。

### CLI / MCP

`monorail idea add` → `save_idea`，正文三选一：位置参数、`--text-file`、`--stdin`，另有 `--needs`（`src/cli/commands.ts:801-816`，`docs/application/README.md:44`）。`monorail todo add` → `capture_todo`（`src/cli/commands.ts:819-848`）。应用契约里没有改已有想法的方法。`ideaService.editIdea` 只在服务层（`src/services/ideaService.ts:60-64`）。`docs/mcp/requirements-and-design.md:82` 把「编辑想法正文/需求」记成尚未接到公共 API 的服务。

### journal、回执、历史、备份

journal 是提交中的计划：每个写入带改前全文和改后全文，应用后删除该 json（`src/data/journal.ts:29-39`）。它不随天数堆积。崩溃时留下一份，启动 `recover()`（`src/app/bootstrap.ts:25`）。外部改过文件会报恢复冲突。

回执 `receipts/<operation_id>.json` 只增不删，内容是整份规范化输入（`src/data/receiptRepo.ts:7-21`，`src/services/commit.ts:351-354`）。没有保留期。`save_idea` 的输入今天就是 `{ text, needs }`。长文若放进这个输入，会在回执里永久再存一份。

操作历史把记录「内容」截到 60 字（`src/domain/history/compare.ts:30`、`:65-66`）。自动化调用的参数超过 8KB 才截断，并标 `truncated`（`src/shared/history.ts:168`，`src/services/historyCapture.ts:83-87`）。历史和今日任务板保留含今天的 180 个活动日（`src/services/historyService.ts:27-36`）。

备份只出现在 v1→v2 迁移：拷到 `backup/v1-<时间>-<id>/`，并读回核对（`src/data/migrations/v2.ts:18-32`）。没有日常全库备份。

### 主线不只有「写死一个」

`mainTasks` 默认 1，允许 1–3（`src/shared/settings.ts:4`，`src/data/schemas.ts:81-82`）。这个键没有 `defaultWhenMissing`。已有 `settings.yaml` 里写着的数字不会因为改代码默认值而变；缺文件的新目录才用默认（`src/data/settingsRepo.ts:15-18`）。

入背包时，进行中的主线数达到 `mainTasks` 就拒绝（`src/domain/task/backpack.ts:8-12`）。把设置调低不会赶走已有任务；腾位之后仍然超过新上限，整次创建回滚（`src/services/backpackService.test.ts:42-52`）。界面显示 `主线任务 n / mainMax`，满了不再给新建格（`src/pages/home/drawer/BagDrawer.tsx:187-188`）。设置文案是「同时押注的主线任务数」（`src/pages/settings/sections.ts:21`）。

这和「每个主线下面最多几项」是两件事。`mainItems` 默认 5，最多 10（`src/shared/settings.ts:6`）。往一个已满的主线捕捉待办会报 `MAIN_TASK_FULL`（`src/services/recordService.ts:38-40`）。支线事项个数不设这个上限（`src/domain/task/pool.ts:19-20`）。

主线还有押注到期，只在放进主线槽时写入（`src/domain/task/backpack.ts:16-17`）。槽号是主线和支线合用的最小空号，不是主线单独编号（同函数 `:13-17`，`src/services/backpackService.test.ts:21-30`）。一条卡算不算主线，看它的任务是否正在背包的主线槽里（`src/domain/task/task.ts:26-28`）。回顾里的「主线任务」时间用的是这个判断。

在现有设置里，用户已经可以把同时主线从 1 调到 2 或 3，不必改文件格式。超过 3 才要放宽 `settings.ts` 的 `max` 和对应 zod。现有任务文件不用改字段。

## 长详情和大量想法的实际瓶颈

条数已经有池上限和冷库。字数没有上限。变长之后，贵的不是「想法池列表多了几十字」，而是：

1. 每次提交 `list()` 读进每条记录的全文，并留在 `MdRepo` 缓存里。详情若放在正文，快照里的 `records[].text` 可以仍是短标题，但缓存和当次事务仍拿着全文。
2. 快照里的 `text` 今天就是整段内容。背包会把活跃、已转任务和全部已完成想法的 `text` 再放进投影。长文继续放在 `text` 里，列表和查找都会带着全文。
3. 回执永久保存操作输入。这是不随 180 天历史清理消失的那份副本。
4. 单次 journal 在落盘完成前持有改前、改后两份全文。正常结束后删除，不是持续增长。

数据完整性上，真正要守的是：详情不要再被 `commit.ts:287-288` 和 `QuickBarApp.tsx:20` 写成 `text` 的副本；改标题不要通过 `editIdea` 把正文换成标题。查找今天看不见正文。外部直接改 md 会在下次写入时因 mtime 不一致失败（`src/data/mdRepo.ts:42-44`）。

## 若要标题加详情，需要改的不变量

这些是现有行为，不是新需求清单。方案若要「标题一行、详情在 Markdown 正文」，下面几条会不再成立：

- 正文等于 `text`。创建和修改 `text` 都会这样写。
- 公共 API 只有一个 `text`。没有详情参数，也没有改已有想法的应用方法。
- `find_items`、想法池、已完成列表只看 `text`。
- 回执输入等于当时保存的整段 `text`。详情若放进操作输入，会永久留在 `receipts/`。
- 待办卡的可见内容是 `content` 一个字段。卡片正文目前不承担详情。
- 主线同时个数的上限是设置 `mainTasks`（1–3），不是任务文件里的标志。每个主线的待做项上限是 `mainItems`。

已有文件不必为了「正文槽已经存在」而升 schema：正文本来就在 frontmatter 之外。需要的是读规则。今天正文和 `text` 相同，不能把正文直接显示成详情，否则标题会显示两遍。

主线条数：只改默认值影响新数据目录，不影响已经写着 `mainTasks: 1` 的 `settings.yaml`。放到 3 以上才改设置上限。任务 Markdown 没有「只能一条主线」的字段。

## 迁移与验证建议

不在这里定产品默认几条主线，也不定详情多长。验证时建议覆盖：

- 旧文件：正文与 `text` 相同。打开后标题只出现一次；用户没写详情时，正文不再被当成另一篇详情。
- 新文件：标题留在 `text`，详情只在结束线之后。文件里出现顶格 `---` 的 Markdown 仍能整篇读回（沿 `frontmatter.test.ts` 的例子）。
- 只改池状态或 `needs` 时详情还在（现有测试已覆盖「元数据编辑保留正文」）。改标题后详情仍在（这是今天 `editIdea` 做不到的）。
- 同一 `operation_id`、同一规范化输入重放不写第二份。输入若含详情，换详情必须 `OPERATION_CONFLICT`。
- `find_items` 在方案选定「只搜标题」或「也搜详情」之后，用一份短标题加长正文的记录核对，避免详情只存在磁盘上、快照里永远看不见。
- 回执与历史：历史「内容」仍可截断；回执不要在无保留期的情况下意外再存一份正文，除非方案明确接受。
- 主线：`mainTasks` 为 2 时可以同时有两条进行中主线；调回 1 时已有两条还在，不能再加第三条。待办项上限仍按 `mainItems` 拒绝，不跟主线条数混在一个错误里。
- 快速记录条的窄写入和 `save_idea` 写完的文件，用同一套解码读，避免一边正文等于标题、一边正文为空。
