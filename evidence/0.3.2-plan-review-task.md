只审 P1–P3 的实现可行性。只读：没有改 ADR / 执行方案 / 代码 / 版本。代码位置以当前 `master` `95fd8f3` 为准。兼容结论分开写：**schema 能 parse** 和 **旧版实际写回仍保留字段** 不是同一件事。

## 结论

大方向可行：任务内字段级快照、不改 schemaVersion / 枚举、不靠 180 天历史重建前态、GUI 与 InTx 共用、满格走现有 makeRoom，对着代码都站得住（见文末「已核对属实」）。没有发现「按原文实现会和已定规则冲突或状态表达不了」的阻塞。有 **5 条应改**要在 P1/P2 写进方案，否则会做成和 ADR 相反的行为，或把「schema 可读」当成「旧版写回证据」。另有 4 条建议。

## 应改

### S1 重新打开不能直接调用现在的 `putInBackpack`：它会重开押注周期

- ADR 第 3 条同时写了「复用 putInBackpack 分配空格」和「保留完成前仍在任务上的 bet_ends_at，不隐式重开一个新的押注周期」。
- 代码 `domain/task/backpack.ts:16-17`：主线每次 `putInBackpack` 都用 `tx.at + betWeeks` 写成新的 `bet_ends_at`。`restoreTaskInTx`（`backpackService.ts:53-58`）也是这条路径。
- 执行方案 P2 只写「恢复押注时间与格号规则按 ADR0022 明确执行」，没有点出这个函数冲突。
- 要定的：重新打开只复用它的格号分配 / 满格拒绝，**不要**原样调用；或给 `putInBackpack` 加「沿用已有押注」参数。P2 加一条：主线完成前押注 11.20，重新打开后仍是 11.20，不是新周期。

### S2 完成整张任务不能走 `leaveBackpack`

- ADR 第 2 条第 6 点：`status=已完成`、`slot_index=null`，**保留** `slot` 与原 `bet_ends_at`。
- 代码 `leaveBackpack`（`backpack.ts:20-21`）把 `bet_ends_at` 清成 `null`。冷藏 / 放弃可以；完成不行。
- P2 写明 `completeTaskInTx` 自己改这三个字段，不调用 `leaveBackpack`。测：主线完成后天仍在、押注还在、格号空、`inBackpack` 为假。

### S3 写卡的 `completed_track` 必须在 `task.status` 变成已完成之前

- `trackOf`（`task.ts:7-8`）只在 `inBackpack && slot===主线` 时返回主线。`inBackpack` 等价于 `status==='进行中'`。
- 若先把任务标成已完成再批量完成卡，主线会被记成 `completed_track: 支线`。ADR 第 2 条顺序是对的（先卡后任务），P1 领域函数和 P2 事务要写成硬顺序，并测主线批量完成的 `completed_track`。
- 单卡 `cardService.complete` 现在是先 `completeCard(..., trackOf(...))` 再 `afterItem`，任务此时还是进行中，所以旧路径没这个问题。新的整任务路径没有这个现成顺序，要自己锁。

### S4 「schema 可读」不是「旧版写回仍保留」。P1 要拆成两类证据

ADR 第 1、4 条和第 13 行已经写了对：`passthrough` + 不加跨状态 refine；「不能通过字段存在就默认数据兼容」。执行方案 P1 把「新完成对象可读」和「未知嵌套字段写后保留」写在同一句，容易做成只跑 `oldSchema.parse(newTask)`。

对着代码，两件事不是同一个机制：

| 种类 | 代码实际做什么 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| schema 可读 | 现行 `taskSchema` / 冻结的 0.3.1·0.3.0 `taskSchema` 都是 `.passthrough()`（`schemas.ts:35-39`，`migrations/v030/schemas.ts:36-40`） | 旧 schema **parse 新任务文件不抛** | 旧版改一个已知字段再保存后，`completion` 还在 |
| 实际写回 | `MdRepo.write`（`mdRepo.ts:45-48`）是 `{ ...decode(original.text).meta, ...value }`，再 `schema.parse(meta)` | 旧版 **读入 → 改已知字段 → write** 之后，嵌套 `completion.cards[].before` 仍在 YAML 里 | 只 parse、只看 TypeScript 类型、只 `passthrough` 注释 |

P1 验收要分开签字：

1. 冻结 tag `v0.3.1`（及兼容表里的 0.3.0 / 0.2.5）的 **schema.parse** 新任务 / 新完成卡，不抛。这是可读。
2. 用冻结的 **write 路径**（或隔离旧 exe）改名称 / 冷藏等已知字段后，文件里的 `completed_at` 与 `completion` 嵌套还在。这是写回。
3. 旧版把成员改掉（删卡、换 `task_id`、再完成）交回新版，重新打开拒绝 `TASK_COMPLETION_CHANGED`，不覆盖。这是冲突，不是「字段还在」。

`AUDITED_COMPATIBLE_STABLE_VERSIONS` 目前是 `0.2.5` 与 `0.3.0`（`private_release.rs:17`）。本 ADR 明确不提前承诺继续兼容；P1 冻结 + P7 源码/隔离往返之后再改表。未做隔离 exe 的，evidence 写「未测」，不要写「兼容」。

### S5 批量完成不能复用 `completeCard` 的「必须进行中 + 写入 progress_note」

- `transitions.ts:8-10`：只有 `进行中` 能完成，而且总会写 `progress_note`。
- ADR：待做也要能批量完成；保留已有进度笔记，只改 status / 完成时间 / 活动日 / 轨道；不逐项弹时间盒未计满；不造零长度条目。
- 单卡入口继续 `requireCurrent` + 只完成当前卡，这点 ADR 有。P1 要新纯函数（或给 `completeCard` 可选 note 且允许待做），**整任务路径禁止循环 `cardService.complete`**（会 `restoreParent`、会停错计时、会改 current_card）。
- 测：待做卡完成后天 `progress_note` 仍是原值；进行中卡撤销后是待做，不是进行中。

## 建议

### N1 P2 矩阵补「自由计时中完成无关任务」

§3.4 写了当前卡 / 卡暂停 / 插入原任务 / 另一个任务在计。ADR 第 2 条第 3 点还有**自由活动**不停。现在 `alignInTx` 会把「不是当前引用」的进行中卡放回待做；若完成路径先 `stopRef` 再 `alignInTx`，可能把无关的自由条目或另一张卡一起停掉。应用例锁：自由计时开着，完成抽屉里另一件任务，开着的那条描述和 `ended_at` 不变。

### N2 插入中只禁用「正在等待的那张原任务」的〔完成〕，不要灰掉所有任务

ADR：仅当本任务是插入中 / 插入暂停的原任务时拒绝 `IN_AWAY_ACTIVITY`；无关任务没有计时门槛。P3 写「插入状态禁用原因验证」，请写成：原任务按钮灰、说明先回到任务或结束原任务；其他任务的〔完成〕仍可点。待确认同理：只在 `current_card` 属于本任务且 `pending_id` 非空时拒绝（pending 本身没有 card_id，见 `state.pending_id` / `pending_at`）。MCP 现有 `checkNormalPreconditions`（`homeService.ts:298`）是全局 PENDING，那是 P4/P5 的事，GUI 不要照抄成全局禁用。

### N3 自动完成支线：补 `completed_at` 时一并清 `slot_index`，并写明 task_only 的界面后果

`afterItem`（`pool.ts:14-15`）只改 `status`，不清格号、不写时间。P2「统一自动 afterItem 完成时间」是对的。建议同时 `slot_index=null`，避免已完成任务带着旧格号参与 `orderedTasks` 排序。无快照重新打开是 `task_only`：子项保持已完成，用户只能再添加事项——P3 文案已经要求清楚，gallery 要真的展示这条，避免做成「撤销却全部变待做」。

### N4 历史比较不要把 `completion` 整包打出来

`compare.ts` 的 TASK 字段是白名单（名称 / 状态 / 槽位 / 押注 / 默认项目），未知字段本来不会出现。P2 加完成时间即可；**不要**把 `completion` 加进 `TASK` 字段表，否则 `text()` 会 `JSON.stringify` 整份快照（`compare.ts:45`）。卡侧现有「状态」已经能反映本批完成。

## 已核对属实

- `Task.status` 已有 `已完成`；没有完成时间 / 快照。`afterItem` 只结束没有活跃项的支线；`doneSides` 只有支线名字，主线完成了也不会出现（`backpackProjection.ts:46`）。换成 `doneTasks` 覆盖主线是第 1 条 GUI 能看见完成列表的前提。
- `cardService.complete` 是根事务 + `requireCurrent` + `restoreInTx`（缩小父卡）。整任务完成不能循环调用它。ADR 不调用 `restoreParent` 与现有缩小恢复（`cardService.ts:21-26`）一致。
- `makeRoomInTx` / `putInBackpack` 已拒绝满格、自身腾位、不同槽；与 ADR 满格语义一致。取消不写取决于 GUI 不调用；同事务腾位+恢复走现有 `run` / journal，失败不部分提交。
- `taskSchema` / `cardSchema` 均为 passthrough；`MdRepo.write` 合并原始 frontmatter。TypeScript 类型不会在运行时删多余键。旧版**实际写回**仍要测（见 S4）。
- 单卡 `completeCard` 不允许待做；批量需要另一条转换（见 S5）。
- 计划文件不因完成而写盘：与 ADR 0021「卡离开背包不写板子、读时过滤」一致。
- `restoreTaskInTx` 今天对已完成等于直接 `putInBackpack`（无快照校验）。P2「已完成走共用 reopen」必须关掉这条旁路；当前 GUI 冷藏列表不含已完成，旁路主要防未来入口。
- 快照只存本次从待做/进行中改掉的字段差量；原已完成 / 已放弃 / 已缩小不进恢复集；进行中恢复成待做、不重开计时。这些与「不能默认全部变待做」的需求约束一致。无快照 `task_only` 覆盖旧自动完成支线。
- 兼容表不因本 ADR 自动扩大；未测往返写未测。

## 补充（同日，ADR / 方案已写入「task 领域不改 card」）

主线程补充：`domain/task/complete` 只做 Task 元数据、快照校验与核验 ID；卡完成/恢复纯转换留 `domain/card/transitions`，由 `backpackService` 组合；不要在 task 纯函数里批量改卡，也不要让 backpack 反向调用 `cardService`。

与上文 S5 相合，不是新冲突：

- 允许待做的完成、进行中→待做的恢复，都加在 `card/transitions`，单卡 `cardService.complete` 仍 `requireCurrent` + 只进行中。
- `backpackService` 用 task 域给出的核验 ID 去调卡转换并 `saveCard`；不循环 `cardService.complete`（那会 `restoreParent`）。
- `task/complete.ts` 不要 import `card/transitions`。`task/pool.ts` 已只读 Card 类型；`task/create.ts` 已依赖 `card/edit` 建卡，本约束是 complete 路径不要再让 task 改卡。
- eslint 层方向允许 domain 互引（除 history / tracking）；`import/no-cycle` 仍禁止 card↔task 环。卡转换留在 card 侧可避免环。

未改结论：仍无阻塞；S1–S5 仍要在方案里写死。未改 ADR / 执行方案 / 代码 / 版本。
