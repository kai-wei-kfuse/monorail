## 4 个重点的回答

### 1. B1「停了还在等 = 待机 / 插入」在 0.3.0 下的表现：可以接受
逐处核对过 0.3.0 读到「开着 `待机 / 插入`、`resume_entry_id` 指向卡那一条」时的行为：
- 卡状态：`activeRefInTx`（`tracking/api.ts:94-98`）发现开着的条目不是 `普通`，就用 `resume_entry_id` 找卡，所以卡保持 `进行中`，`alignInTx` 不会把它放回待做。
- 首页：`timerView.ts:17-19` 看到 `kind === '插入'`，就把底层显示成原来那张卡；`AwayDrawer` 显示一条名为 `idleName`（默认「待机」）的临时活动；〔回来〕走 `homeService.resumeInTx`（`homeService.ts:83-89`），回到原来那张卡。
- MCP：`applicationController.ts:96-98` 进 `away`，`return_from_break` 可用（`homeService.ts:289` 只看 `kind`）。
- 停止：0.3.0 的 `stopInTx`（`timerService.ts:31-36`）对它不会当成什么都不做，而是清掉回到目标、开一条 `待机 / 普通`，卡放回待做。结果和 0.3.1 的〔结束原任务〕一样。
- 回看：`recap.ts:86,144` 先按项目名判断待机，所以这段算「待机」，不算「临时离开」。
- 条目校验：`assertEntries`（`entry.ts:24-25`）只要求待机不和别的条目重叠，和 `kind` 无关。

只有一处小毛病：0.3.0 的 `AwayDrawer` 允许改这条的描述（`AwayDrawer.tsx:31`），用户可能把「待机」改名。数据不会坏，不用处理。

### 2. B3 抽卡只读、`state.seen` 不再用：读写方只有两处，都已经在方案里
`grep` 全仓，只有 `cardService.ts:121`（`redraw`）和 `dealService.ts:20-22`（`drawInTx`）读写 `state.seen`，方案都删了。`state.yaml` 里留着旧值，0.3.0 照读，没有影响。但「只读」和「新一轮清空 `seen`」两句自相矛盾，见应改 S1。

### 3. `split_note` 之后不变量的措辞：执行方案准确，ADR 还有一处没改；0.3.0 会把它复制到别的卡上
见应改 S3。

### 4. `newDay()` 的顺序：顺序本身没问题，但每一步缺少「是不是真的跨日」的判断
「过期 → 旧降级休息 → 带过去 → refresh」之间没有数据依赖，问题都出在带过去这一步，见阻塞 B2。另外 `refresh` 这一步删多了，见阻塞 B1。

## 阻塞

### B1 G3 精简 `refreshInTx` 会丢掉 `first_used_day` 和回顾进度的写入，新数据目录里每周回顾进不去
- 方案 G3：`refreshInTx` 只保留「当前卡不再是待做 / 进行中就清空」和把旧 `home_mode` 归一到 `blank`。
- 代码：`first_used_day ??= day` 和 `reviewUpdates`（取代过期的回顾、建本周的回顾行）**只在** `drawInTx` / `refreshInTx` 里调用（`dealService.ts:13-14,30-31`）。0.3.1 把 `drawInTx` 删掉、`refreshInTx` 精简以后，就没有地方写它们了。
- 后果：
  - 新数据目录的 `first_used_day` 永远是 null。`reviewProjection.ts:30` 在它为 null 时返回 null，顶栏「回顾」里没有可进的回顾。`homeProjection.ts:43` 的 `review` 也一样。`recapService.ts:26` 回看的起点也算不出来。
  - 老数据目录：过期没做完的回顾不再被标成「已被取代」，`currentReview` 可能一直停在旧的那一周。
- 改法：G3 写明 `refreshInTx` 保留 `first_used_day ??= day` 和 `reviewUpdates` 这两行，只删出卡相关的部分。ADR 第 2 条第 8 点同步。单测补一条「新目录启动后 `first_used_day` 已写」。

### B2 `newDay()` 在启动时也会跑：带过去会误加没排的卡、误结束插入，而且「今天的文件不存在」不能用来判断换日
- `newDay()` 在每次启动时调用一次（`bootstrap.ts:89`），换日时由调度器再调用（第 91 行）。ADR 第 6 条的每一步都没有写「只在真的换了活动日时才做」：
  - **还在计的卡直接加进今天**：同一天重启时，正在计的卡会被加进板子。从抽屉直接开始一张没排的卡，再重启，它就被悄悄加进了今天，和已定 49 提议 4（直接开始没排的卡，不加进板子）、已定 11（不悄悄加进今天）冲突。
  - **插入中先结束原任务**：同一天重启时，正在插入的会被结束原任务，用户回不去了。
  - **「今天的文件不存在就建」**：前一晚排过「明天」，第二天 `plans/<今天>.yaml` 已经存在，所以「文件不存在」等于「刚换日」这个判断不成立。
  - **`carried_from` 为空才带**：来源里没有可带的项时，`carried_from` 一直是 null，每次启动都会再扫一遍。来源那天的计时被日历改过以后，已经达成的项可能又变成没达成，被补带过来。
- 改法：
  1. `plans/` 的 schema 是自己的，可以随便加字段。今天的文件加 `rolled_over: true`（或者 `rolled_at`），带过去这一步只在它为 false 时做一次，做完就写上，不管有没有带到项。这样「明天的文件已经存在」也能正确处理。
  2. 「还在计的卡加进今天」和「插入中先结束原任务」再加一个条件：开着的那一条（插入中时看原来那一条），开始时间早于今天活动日的起点，也就是确实跨过了换日时间。同一天重启时这两条都不成立。
  3. 单测补「同一天第二次 `newDay()` 什么都不改」「前一晚排了明天，第二天带过去照样执行一次」。

### B3 插入的入口没有处理待确认起点：做卡时在计时框里写新事件，会卡在「待确认」
- 这是已定 22 最常用的一条路：做卡时点计时框的「＋ / 写别的」→ `beginPendingInTx` 写 `pending_id` / `pending_at`（`homeService.ts:52-54`，`useEntry.tsx:34,65`），用户也可能把起点往前拨（`commitReadoutInTx` 的 pending 分支，`homeService.ts:137-156`）→ 输入 → 开始。
- 现在的 `startFreeInTx`、`startPresetInTx`（切换分支）、`continueEntryInTx` 都是 `from = pending_at ?? at`，再 `clearPending`（`homeService.ts:37,63,119`）。`insertInTx`（`timerService.ts:37-41`）既不接收 `from`，也不清待确认。
- 方案把这几个入口在做卡时都改成走插入，却没写待确认怎么办。照现在的 `insertInTx` 去做：插入从点击那一刻开始，用户往前拨的起点丢了；`pending_id` 留在 `state.yaml` 里，首页一直显示待确认，MCP 的每个计时方法都报 `PENDING_CONFIRMATION`（`homeService.ts:218`）。
- 改法：`insertInTx` 加一个 `from` 参数（同 `startInTx`）；插入和替换这两个分支同样取 `from = pending_at ?? at`，并 `clearPending`。卡那一条在 `from` 处截断，交给 `place` 处理（同现在的切换）。`entryAction` 的表驱动单测，每个入口都加一行「带待确认起点」。

## 应改

### S1 `drawFromPlan` 只读，但「`seen` 空了开新一轮」要写盘
- ADR 第 2 条第 3 点：候选为空但 `seen` 不为空时，「清空 `seen` 开新一轮」。第 6 点又说抽卡是 `readSerial` 只读，不写盘。只读的抽卡清不了 `seen`。
- 改法：`pickFromPlan` 在计算时，如果去掉 `seen` 以后候选为空，就在不排除 `seen` 的候选里抽，并返回 `resetRound: true`。真正的清空放进〔换一张〕的写事务：`planService.skipCard` 遇到 `resetRound` 时，写入 `seen = [这张]`，不再往原来的列表里追加。只是关掉翻卡就不写盘，和现在一致。

### S2 入口表里「暂停中的卡」和「继续这一条是原来那张卡」两格
- **卡暂停时**：入口表把「待机 / 暂停」归为「直接开始」。卡暂停时，开着的条目是 `待机 / 暂停`，`resume_entry_id` 指向卡，卡还是 `进行中`（`activeRefInTx`）。照表格「直接开始」，`startInTx(普通)` 会清掉回到目标（`timerService.ts:16`），卡被放回待做。可是现在的 `insertInTx` 遇到暂停条目时本来就保留回到目标（第 39 行只在 `普通` 时才改），也就是说，按插入做反而是现成的。用户的说法是「我换了东西之后，自动暂停……我可以选择返回」，暂停的卡更像「还在做卡」。这一格要定下来，建议把「卡暂停中」并进「一张卡」那一行（按插入处理），没在做卡时的暂停仍然直接开始。
- **插入中「继续这一条」继续的是原来那张卡的条目**：表格写「替换插入的事」，但 `continueEntryInTx` 遇到卡的条目会去调 `startCardInTx`（`homeService.ts:120`），G4 又让 `startCardInTx` 在插入中抛 `IN_AWAY_ACTIVITY`。建议：如果继续的正是原来那张卡，就等于〔回到任务〕；是别的卡就照 B2 拒绝。小窗的 `startCard` 命令（`homeService.ts:200-203`）同理。
- **`homeService.resumeInTx` 本身也调 `startCardInTx`**（第 87 行）：它是先清掉 `resume_entry_id` 再调用，所以 `insertState` 必须以「`resume_entry_id` 不为空」为前提，才不会把〔回到任务〕自己拦掉。建议在 `insertState` 的注释和单测里锁定这一点。

### S3 `split_note`：ADR 第 1 条的旧说法没改；0.3.0 缩小 `rest` 卡时会把它复制给子卡
- ADR 第 1 条「为什么不写进卡」还写着「卡、记录、任务的 schema 一个字段都不加，退回 0.3.0 时这些文件和 0.3.0 自己写的一样」，和第 4 条的 `split_note` 矛盾。请改成和执行方案第 0 节一样的说法：「不加 0.3.0 会拒绝的字段或枚举值，卡上只有可选的 `split_note`」。第 8 条表里 `cards` 那一行已经写对了。
- 0.3.0 的 `shrinkCard` 生成子卡时用的是 `{ ...card, ... }`（`shrink.ts:11-14`），会把 `split_note` 一起复制过去。在 0.3.0 里缩小一张 `rest` 卡，子卡就带着父卡的 `split_note`。回到 0.3.1 以后，鼠标提示会写成「从〔祖父卡的内容〕缩小来的」。`editCard` 这类编辑也是展开整张卡，同样会保留，这没问题。
- 改法：鼠标提示只在 `shrunk_from` 指向的卡**不是** `已缩小` 时才读 `split_note`。0.3.0 缩小时会把父卡改成 `已缩小`，正好可以用来区分。G1 的锁定测试补一条：0.3.0 的 `shrinkCard` 处理带 `split_note` 的卡，确认子卡带着它、父卡是 `已缩小`。

### S4 完成对话框：拆过的卡都不能接着做，现在的说明文字也不对了
- `CompleteDialog.tsx:16,24` 对 `shrunk_from` 不为空的卡（`HomePage.tsx:241` 的 `isShrinkCard`）不显示「还要接着做」，因为 0.3.0 的续卡不能接在缩小链上（`transitions.ts:18`）。0.3.1 拆分以后，`rest` 和再拆出来的卡都带 `shrunk_from`，照现在的界面，这些卡都不能接着做。
- 现在的说明是「生成一张同内容的新卡放到队尾，带上这次的『做到哪了』」（第 25 行）。0.3.1 的行为是同一张卡回到待做，所以 G7 写的「开关文案不变」不对。
- 改法：G7 去掉 `isShrinkCard` 这个判断，说明改成「这张卡回到待做，进度和『做到哪了』留着」（具体文字给用户看一眼）。G5 的 `transitions.ts:18` 随 `continueCard` 一起不再使用。

### S5 `drawInTx` 和写 `home_mode` 的其他地方没有列全
- G3 只写了 `complete` 和 `redraw`。还有：`cardService.pass` 末尾的 `drawInTx`（`cardService.ts:137`）；`homeService.draw`（第 75-78 行，会先开待确认，再抽卡）；`degradeService.returnFromRest` 写 `review` / `guide`（`degradeService.ts:43`），它要留给 `state.rest` 的一次性处理用，按 ADR 第 2 条第 8 点，这里只能写 `blank` / `task`。
- 改法：G3 写一句「删掉所有 `drawInTx` 调用（`complete`、`pass`、`redraw`、`homeService.draw`）」，并在测试里 grep 断言没有地方再写 `review`、`guide` 或 `rest` 这几个 `home_mode`。

### S6 MCP `get_context` 列快捷活动时也看 `mode`
- ADR 第 3 条只改了 `homeService.ts:277` 的 `start_break` 找预设（第 1 轮写的第 271 行，HEAD 上在第 277 行）。`applicationController.ts:342` 的 `options.break_presets` 也是 `p.mode === '插入'`。0.3.1 不读 `mode` 以后，agent 看到的可用快捷活动，会和界面、`start_break` 实际接受的不一样。改成看 `place === '弹层'`，同步 `docs/application/README.md`。

## 建议

- **N1 `Transaction.plan(day)` 是异步懒读，同步的 InTx 用不了**：`startFreeInTx`、`startPresetInTx` 这些是同步函数，仓库读文件是异步的。建议今天那份在建事务时预读（同 `cards`），明天和更早的才懒读，并注明只有 async 的 InTx 可以调 `plan(day)`。
- **N2 翻卡后开始的起点**：0.3.0 的 `home.draw` 先开待确认（`homeService.ts:76`），所以「抽卡 → 开始」之间的时间算进卡。0.3.1 抽卡只读，起点就成了点〔开始〕的那一刻。如果要保留原来的算法，就在打开翻卡时 `beginPending`，关掉翻卡时 `cancelPending`，不保留的话就写一句说明。
- **N3 `current_card` 的不变式**：抽卡不再写 `current_card` 以后，它只可能是 null，或者是进行中的卡（包括插入中原来那张）。`keepGoingInTx` 要同时清掉 `current_card`（`releaseCard` 不会清）；`cancelPendingInTx:59` 里「当前卡是待做」的分支只剩处理 0.3.0 旧数据的作用。建议写进 ADR 第 2 条。
- **N4 插入中从小窗完成原来那张**：`complete` → `stopRefInTx`（`timerService.ts:48-52`）发现回到目标就是这张卡，就开 `待机`，插入的事也跟着停了。G7 小窗插入状态那一条，写明插入中小窗给不给〔完成〕。
- **N5 历史动作名**：`newDay()` 是一个 `run`，动作是 `system.dayChange`（`bootstrap.ts:84-85`）。ADR 第 11 条列的 `system.carry` 不会单独出现，除非把带过去拆成单独一个 `run`。二选一写清楚。〔开始〕附「来源抽卡」：`HistorySource` 没有这个字段，可以用 `page: '抽卡'`。
- **N6 MCP 在「停了还在等」时**：`stop_timer` 在这个状态下应该什么都不做（`reason: 'already_stopped'`）还是结束原任务？`allowed` 表里这个状态和「插入中」是不是同一套？建议在 G4 的 MCP 那一条补上，并加进兼容测试。
