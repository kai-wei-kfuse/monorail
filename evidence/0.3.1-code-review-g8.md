## 应改

### S1 `update_time_entry` 改时间时不提示覆盖，规则和日历不一样，而且回报的 `overlaps` 里会有被删掉的记录
- 工具描述和 README 写的是「规则同单轨日历」。但日历改时间时走的是 `timeEditService.update → updateRangeInTx → editEntry → place(..., 'overlay')`（`edit.ts:59-63`、`place.ts:12`）：`overlay` 模式下**非待机的记录原样保留，可以并行**，只会切掉被盖住的待机。所以日历改时间并不会「让出」别的记录。
- `updateTimeEntryCheckedInTx`（`homeService.ts:341-347`）走的也是这条路，结果和日历一致：两条非待机记录并行。注释却写着「新时段盖住的别的记录（日历同一套：被盖住的部分让出来）」，和代码不符。返回的 `overlaps` 来自 `tracking.overlaps`，只列非待机的记录，所以它的意思其实是「和这些记录并行」，不是「这些被覆盖了」。这和 `add_time_entry` 是同一个语义，没有问题；要改的是注释和工具描述，免得 agent 以为被盖住的记录已经被改掉了。
- 另外，正在计时的那一条改开始时间时，`end` 传的是 `tx.at`，`overlaps` 算的是 `[新开始, 现在]` 这一段，这是对的。
- 改法：把注释，以及 MCP 和 README 里的描述，改成「新时段和这些已有记录重叠（并行保留，不改它们；被盖住的待机会让出来）」。测试 `updateTimeEntry.test.ts:15` 已经断言了 `overlaps`，再补一句：重叠的那条记录本身没有变。

### S2 `update_time_entry` 能把待机、系统记录改成普通活动，日历也是这样，但要写清楚
- `patchMetadataInTx` 只挡「来自卡的描述和项目」，不挡待机、休息、睡眠、离线这些条目。agent 可以用 `update_time_entry` 改离线那一段的描述和项目，这正是离线追问的回答在做的事，也是日历允许的，所以可以接受。
- 不过 `validateUserProject` 不允许把项目改**成**系统项目（`RESERVED_PROJECT`），这个规则是对的。反过来，把一条「待机」改成「工作」，会让这段从待机变成普通活动；如果它就是开着的那一条待机，开着的就变成了「工作」，首页从待机变成计时中。日历的弹层对正在计时的待机条目是否开放改项目，我没有核对。
- 改法：二选一。一是对开着的待机条目拒绝改项目和描述（报 `ENTRY_IS_IDLE`，提示改用 `start_timer`），这样更安全；二是允许，同时在 README 写明「改开着的待机条目的项目，等于从那一刻起在做这件事」。我建议拒绝，并补一条测试。
