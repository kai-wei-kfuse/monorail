## 阻塞

### B1 主窗口的〔继续〕还接在 `timer.resume`（回到任务）上，插入的事暂停后点〔继续〕，回到的是卡
- `homeService.continueTimer` 已经写好，也有测试（`insert.test.ts:88-98` 首页那一路直接调的是 `continueTimer`），但 `src/app/actions.ts:68` 只导出了 `resume: timer.resume`，没有导出 `continueTimer`。首页的〔继续〕按钮（`FreeCard.tsx:63`、`FusedCard.tsx:56,63,111`）调的都是 `actions.resume`。
- 后果：用户在主窗口暂停插入的事（`home.pause` 已经正确分流成「待机 / 插入」）以后，点〔继续〕走的是 `homeService.resumeInTx`，结果回到了原来那张卡，插入的事续不上。这正是第 3 轮 B1 想修的问题，现在服务层修好了，主窗口没接上。小窗没问题（`resume` 命令走的是 `continueInTx`）。
- 改法：`actions.ts` 加 `continueTimer`。首页、计时条上所有「继续」按钮改调它；〔回来〕〔回到任务〕（`AwayDrawer.tsx:70`、`MainApp.tsx:234` 的快捷活动弹层「回来」）继续用 `resume`。如果打算在 G7 换插入卡时一起改，请在 G4 交接里写明「主窗口〔继续〕未接」，并加一个测试：插入的事暂停时，`actions.resume` 必须是回到任务，`actions.continueTimer` 才是继续。不然 G4 现在的状态会被当成已经完成。

### B2 换日时「插入中先结束原任务」没有实现，有一处注释和代码对不上
- ADR 第 6 条和方案 G2 写的是：换日时，如果还在插入中，并且原来那条开始于今天活动日起点之前，就先结束原任务。`planService.ts:96-97` 的注释写着「由调用方（homeService）在本函数之前处理」，可 `dayChange.ts:10-14` 的顺序只有 `expireInTx → rolloverInTx → refreshInTx`，`grep endOriginalInTx` 也只有界面动作在调。所以这一步实际上没有做。
- 连带的问题：`rolloverInTx` 判断「换日时还在计的卡」看的是 `openInTx(tx).card_id`（`planService.ts:111-113`）。插入中开着的条目是插入那条，`card_id` 为 null，所以原来那张卡既不会被结束原任务，也不会被当成在计的卡直接加进今天。它只能靠「昨天板子上没达成」被带过来、等确认；如果它昨天不在板子上，就什么都不发生，第二天还停在插入状态，回去照样能回。数据不会坏，但和 ADR 写的不一致。
- 改法：在 `dayChangeInTx` 里，`rolloverInTx` 之前加一步：`insertStateInTx(tx)` 不为空、且 `resume_entry_id` 指向的那条开始于今天活动日起点之前，就调 `endOriginalInTx(tx)`，然后 `alignInTx(tx)`。要注意方向：`dayChange` 调 `homeService` 的 InTx。`CLAUDE.md` 已经写了「scheduler → homeService 的 InTx」，`dayChange` 相当于 scheduler 这一路，可以在 `CLAUDE.md` 那一行顺手补上 `dayChange`。再补一条单测：前一晚插入中、第二天 `newDay()` 以后，原卡回到待做、插入那条变成普通条目，并被当成昨天没做完的项带过来、等确认。

## 应改

### S1 `rolloverInTx` 加进今天的「在计的卡」，量算法和 ADR 不一致，0 也会被抬成 5
- `planService.ts:117-118`：`rest = max(5, timebox − floor(总已计))`。ADR 第 6 条写的是在计的卡「直接加进今天」，没定量；`carryItems` 和 `defaultTodayMinutes` 的量是「剩下的时长」，并向上取到 5 分钟。两种算法不同：一张已经计满、甚至超出的卡，这里会得到 5 分钟，`carryItems` 遇到 `rest === 0` 会直接跳过。建议统一调 `defaultTodayMinutes`，`rest === 0` 时就不加。
- 同一段里还有一行 `if (!plan.items.some(item => item.carried)) plan.carried_confirmed = true;`：来源里有带过来的项、而在计的卡正好也在其中时，`existing.carried = false`，于是就不用再确认这张了。这样处理是对的，但只有在在计的卡这个分支里才会执行。建议把它挪到函数末尾，统一按「还有没有带过来的项」来设 `carried_confirmed`，以后再改的时候少一个坑。

### S2 `drawFromPlan` 在提交队列外读设置，`skipCard` 和抽卡对「今天」的算法不同
- `dealService.ts` 的 `drawFromPlan(ctx, at)`：「今天」按调用方传进来的 `at` 算，界面上是点击的时刻。`skipCard` 的写事务里用的是 `tx.todayPlan`，「今天」按 `commandAt` 算。正常情况下两者相同；翻卡正好跨过换日时间时，抽的是昨天的板子，跳过写进的是今天的板子。影响很小，可以在 `skipCardInTx` 里校验 `cardId` 在今天的板子上，不在就什么都不做。
- `drawFromPlan` 每次都 `cards.list()` 和 `tasks.list()` 去读盘，而快照里已经有提交后的 `cards`、`tasks`、`state` 了（`ctx.snapshot()`）。改用快照，就不用每抽一次读一遍全部卡文件。只读排队的语义不变（照样在 `readSerial` 里读快照）。板子文件也可以从 `snapshot.plan` 拿，但 `PlanSlice` 是投影，没有 `seen`，所以板子还是读盘最简单。

### S3 MCP 在「插入的事暂停了」这一状态下的测试不全
- 逻辑我核对过，是对的：`pauseTimerCheckedInTx`（`homeService.ts:281-285`）在插入的事暂停时返回 `already_paused`；`resumeTimerCheckedInTx` 走 `continueInsertInTx`；`stopTimerCheckedInTx`（第 303 行）开着的是「待机 / 插入」，`kind === '插入'`，被 `checkNormalPreconditions` 拒成 `IN_AWAY_ACTIVITY`。三者都和 ADR 第 3 条的方法表一致。
- 缺的是测试：`applicationController.test.ts` 只覆盖了「插入中」。请补「插入的事暂停了」这一行：`pause_timer` 返回 noop `already_paused`、`resume_timer` 继续插入的事、`stop_timer` 报 `IN_AWAY_ACTIVITY`、`start_task_item` 报 `IN_AWAY_ACTIVITY`、`allowed` 里有 `resume_timer` 没有 `pause_timer`。方案 G4 要求的 `cli/cli.test.ts` 两种状态的用例，这次 diff 里也没有。

### S4 `today_plan` 只在 `taskMode` 打开时给，但 `away_paused` 的 schema 是 optional
- `shared/application.ts:114`：`away_paused: z.boolean().optional()`，可 `buildTimerContext` 每次都会给。用 optional 是为了让旧客户端解析时不报错，这个理由成立；但服务端输出时应该始终带上这个字段，测试也要断言它一直在，这样 agent 能放心依赖。现在 `applicationController.test.ts:223` 只在 away 时断言了。建议加一条 idle 时 `away_paused === false` 的断言。
- `today_plan` 的条件是 `view.settings.taskMode && view.plan`。`snap.plan` 在应用启动后的第一次提交之前不存在，这时 `get_context` 会给 null，和「今天没排」分不出来。可以改成 `plan` 不存在时报 `SNAPSHOT_UNAVAILABLE`，和别的快照字段一致；或者在 README 里写明 null 有两种意思。

### S5 插入中「继续这一条」继续的是原来那张卡时，没有检查插入状态之外的情况
- `continueEntryInTx`（`homeService.ts:143-153`）：只有在插入状态、且回到目标正好是这张卡时，才当成〔回到任务〕。在**卡暂停中**（`待机 / 暂停`，不算插入状态）去点这张卡的「继续这一条」，会走 `startCardFromPendingInTx`，结果是重新开始同一张卡。效果和〔继续〕差不多，但起点用的是待确认起点、还会清掉待确认，和〔继续〕的语义不完全一样，也没有测试。建议在卡暂停中、目标正好是回到目标那张卡时，也走 `resumeInTx`，并补一条用例。

## 建议

- **N1 入口白名单再加一道**：在 `insertEntrypoints.test.ts` 里加一条，查 `services/`、`app/` 里所有直接调 `startCardInTx` / `card.start(` 的地方，要求都经过 `requireNotInserting`，或者在白名单里。`cardService.start`（`cardService.ts:68`，现在只有 `verification/main.ts` 在用）绕过了插入检查：它不在 eslint 能看到的生产路径上，但也是个口子，建议在它里面也调用插入检查，或者直接删掉、让验证入口改用 `homeService.startCard`。
- **N2 明天那份改成懒读**：`commit.ts` 每个事务都会读明天那份，只为投影用。ADR 第 1 条写的是「明天懒读」。如果担心心跳、小窗这类高频事务的读盘开销，可以把明天那份的投影缓存在 ctx 上，只在明天那份被写过、或者换日以后才重读。现在的做法功能正确，可以留到 R5 性能用例的时候再看。
- **N3 `planChanges` 里「换一张」的 `seen` 被重置成 `[这张]` 时**：新一轮开始时，原来 `seen` 里的卡被清掉，这次的改动里不会记录；只记新加的那张，可以接受。但 `before.seen` 里有、`after.seen` 里没有的那些，历史里看不到「开了新一轮」。如果想让用户看懂，可以加一条 `type: 'state'`、`field: '换一张'`、`after: '新一轮'` 的记录。不加也行。
- **N4 `drawAndStart`（`HomePage.tsx`）抽到就直接开始**：这是 G7 之前的临时接法，`kind === 'plan' / 'confirmCarry' / 'done' / 'blocked'` 都会静默什么都不做，用户点了〔抽卡〕没有反应。如果 G4 以后会先出一个 Beta 给自己试，建议至少在这几种情况下推一条 notice。如果确定 G7 之前不会给人用，在交接里写一句就行。
- **N5 `PlanRepo.days()` 吞掉所有错误**：`fs.list('plans').catch(() => [])` 会把「目录不存在」以外的读错误也吞掉，带过去就会静默跳过。建议只在目录不存在时返回空列表，其余错误照常抛出。
