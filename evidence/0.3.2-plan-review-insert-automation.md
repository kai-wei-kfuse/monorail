# 0.3.2 方案审核（跨窗显式插入入口与内存草稿，ADR 0024）

审核人 coder-3 · 2026-11-07 · 对象：[ADR 0024](../docs/adr/0024-explicit-insert-across-windows.md)（Proposed，v1），对照 [0.3.2.md](../docs/stages/0.3.2.md) v0.16 第 3–4 条与现有代码（`master` `95fd8f3`）。

只读交叉审核：未修改 ADR、执行方案、需求文档、业务代码或版本文件。

## 结论

- **阻塞：0 条**。ADR 0024 采用「主窗唯一内存草稿协调器 + `readSerial` 建/撤草稿 + `run` 统一 `commitInsertDraftInTx` + `EntrySource = 'explicitInsert'` + `(epoch, viewSeq)` 快照排序」的整体设计与现有单写者、单提交队列架构完全契合，且不增加持久化字段或 MCP/CLI 方法数（保持 ADR 0023 的 35 方法不变）。
- **应改：5 条（S1–S5）**。涉及 `commit.ts` 中 `ctx.publish` 与草稿消费/令牌校验的执行时序、同毫秒/边界 `draft.at` 下 `startInTx` 误删原条目导致 `resume_entry_id` 悬空、暂停态原事 `original` 取值与 `MiniSnapshot` 协议字段、跨窗切页/隐藏的撤回边界与镜像窗控件禁用，以及 `viewSeq` 同步采样与纯草稿变更的双端推送。
- **建议：3 条（N1–N3）**。

---

## 应改（Should-Fix）

### S1 `commitInsertDraft` 在 `execute()` 内的 `ctx.publish` 时序会自触发「原来的事已变化」，且需精确区分事务未提交失败与 `postCommit` 告警

- **位置**：`src/services/commit.ts:97, 149-154, 333-375`、`src/services/miniController.ts:40`，对照 ADR 0024 §3 第 2–4 段。
- **现状问题**：
  1. 在 `commit.ts` 的 `execute()` 中，`await ctx.repos.transact(ctx.id(), tx.writes)`（第 333 行）落盘成功后，会在 `run()` 的 Promise 返回给调用方**之前**，先在 `postCommit('projection')` 中同步调用 `ctx.publish(snapshot)`（第 352 行），而 `ctx.publish` 会**同步触发所有 `ctx.onSnapshot` 监听器**（第 97 行，包括 `connectMini` 的 `push()`）。
  2. ADR 0024 §3 第 2 段规定：「任何提交后投影若发现令牌变化……则清草稿并推明确『原来的事已变化，插入未记下』」。当 `commitInsertDraft` 自身成功提交时，新快照里的 `open_entry` 已经变成新建的 `'插入'` 条目，`timerStateToken` 必然不同于 `draft.expectedTimer`。如果协调器等到 `await run(...)` resolve 之后才消费草稿，那么在 `ctx.publish(snapshot)` 触发 `onSnapshot` 的那一刻，协调器里的 `draft` 仍处于 `phase === 'committing'`：
     - 若 `onSnapshot` 令牌检查不识别「正是当前 `committing` 草稿自身落盘引起的令牌变化」，会把本次成功提交误报为「原来的事已变化，插入未记下」；
     - 同时 `connectMini` 会在 `onSnapshot` 时推一帧（仍带旧草稿或错误提示），`await run()` 返回后再推一帧，导致同一次提交被拆成两帧推送。
  3. 此外，`run()`（`commit.ts:150-152`）在 `transact()` 已落盘成功、但 `postCommit`（`projection / reminders / logging`）产生 `warnings` 时会抛 `Error('数据已提交，后续处理失败：…')`。若外层 `catch` 不区分「`transact` 前失败」与「`transact` 后 `warnings` 抛错」，会在落盘成功后把草稿误恢复为 `editing`。
- **应改**：
  - 在 `commitInsertDraft` 中：
    1. 当 `work(tx)` 执行完毕、进入 `postCommit` 触发 `ctx.publish` 时（或通过事务完成标记），在 `onSnapshot` 监听器生成 `MiniSnapshot` **之前**即把处于 `committing` 的当前草稿正常消费清空（`draft = null`），使新 `inserting` 快照与 `draft = null` 在同一次 `ctx.publish`（同一个 `viewSeq`）中原子推出，且不触发「原来的事已变化」提示。
    2. 若 `run()` 抛错：仅当事务未提交（`work(tx)` 抛错，或 `ctx.repos.transact` 抛错置位 `queue.failure`）时才按未提交处理（若当前 `timerStateToken` 与原目标仍有效则恢复 `draft.phase = 'editing'` 并保留文本；若令牌已变则清草稿并提示「原来的事已变化，插入未记下」）；若已提交而仅因 `数据已提交，后续处理失败` 抛错，草稿必须保持已消费状态，绝不恢复为 `editing` 重试。

### S2 原事为运行中普通条目时，若 `draft.at` 与 `open.started_at` 同毫秒（或 `tx.at = commitAt` 下触发 `claim`），`startInTx` / `place` 会抹除原条目导致 `resume_entry_id` 悬空

- **位置**：`src/services/tracking/timerService.ts:12-18, 47-51, 55`、`src/domain/timeline/place.ts:14, 23-32`、`src/services/cardService.ts:35-41`，对照 ADR 0024 §4 第 2–3 段。
- **现状问题**：
  1. 当原事是正在计时的普通条目（`open.kind === '普通' && !isIdle(open)`，含做卡进行中或自由记录进行中）时，`insertInTx`（`timerService.ts:49`）先把 `tx.state.resume_entry_id` 设为 `open.id`，再调 `startInTx(tx, template, from, '插入')`。
  2. 在 `startInTx`（`timerService.ts:13-18`）与 `place`（`place.ts:14`）中：
     - 若 `Date.parse(draft.at) <= Date.parse(open.started_at)`（例如刚点开始同一毫秒内点〔＋ 插入事件〕、跨窗毫秒级时钟偏差，或单测固定时钟），`startInTx` 第 14 行 `Date.parse(entry.started_at) === Date.parse(tx.at) ? [] : ...` 以及 `place.ts:14` `if (a < start)` 会将时长为 0 的原条目 `open` **从 `tx.entries` 中直接删除**（此前 `pauseInsertInTx` 第 55 行已专门为此加过同毫秒保护）；
     - 一旦 `open` 被删，`tx.state.resume_entry_id` 就变成指向不存在条目的悬空 ID，`insertStateInTx(tx)`（`timerService.ts:27-28`）因找不到 `resume` 返回 `null`，紧接着 `alignInTx(tx)`（`cardService.ts:36-40`）认为当前没有活跃卡引用，直接把正在做的卡释放回 `待做` 并清空 `current_card`！
  3. 另一方面，若 `commitInsertDraft` 用回车时刻 `commitAt` 作为 `tx.at`、用 `from = draft.at` 调 `startInTx`，当 `Date.parse(draft.at) === Date.parse(open.started_at)` 时，`claim(tx.entries, from, tx.at)`（`place.ts:30`：`if (!isIdle(entry) && a < end && b > start && a >= start) claimed = Math.max(claimed, b)`）会把尚未关闭的 `open` 当成阻挡段，把插入起点静默推迟到回车时刻 `tx.at`，违背 ADR 0024 §4「起点始终是按钮点击时捕获的 `draft.at`」。
- **应改**：
  - 明确 `draft.at` 与 `tx.at` 的边界规则：
    1. 当原事为 `open.kind === '普通'`（正在计时的卡或自由记录）时，插入起点 `draft.at` 必须**严格晚于** `open.started_at`（`Date.parse(draft.at) > Date.parse(open.started_at)`；若点击时刻与 `open.started_at` 同毫秒，可在 `beginInsertDraft` / `commitInsertDraftInTx` 中将 `draft.at` 夹紧为 `new Date(Date.parse(open.started_at) + 1).toISOString()`），保证原条目被截断为 `[open.started_at, draft.at]` 而不被删掉，`resume_entry_id` 始终有效。
    2. 当原事为 `open.kind === '暂停'`（开着的是 `待机 / 暂停`，而 `resume_entry_id` 已指向暂停前那条已结束的原条目）时，只需 `Date.parse(draft.at) >= Date.parse(open.started_at)`（即使 `draft.at === open.started_at` 抹掉 0ms 的 `待机 / 暂停` 段，底层的 `resume` 条目早已闭合，不受影响）。
    3. `commitInsertDraft` 调 `run(ctx, ..., draft.at)`（或让 `startOtherInTx` 显式接收 `from = draft.at`）时，校验 `Date.parse(draft.at)` 不早于 `open.started_at` 且不晚于提交时刻 `ctx.now()`。

### S3 暂停态原事的 `original` 身份/标题必须取自 `resume_entry_id`，且需补齐 `MiniSnapshot` / `windowBus` / `historyActions` 的契约细节

- **位置**：`src/services/homeProjection.ts:24-38, 71-76`、`src/services/miniProjection.ts:20-31`、`src/platform/windowBus.ts:10-59, 70, 75, 100`、`src/services/homeService.ts:245-288`、`src/shared/history.ts:47-59`，对照 ADR 0024 §1–§4。
- **现状问题**：
  1. **暂停态原事的目标取值**：当卡暂停或自由记录暂停时，`state.open_entry` 是 `待机 / 暂停`（`description: '待机'`, `project: '待机'`, `card_id: null`），真正被中断的原事是 `state.resume_entry_id` 指向的闭合条目 `resume`。若 `InsertDraft.original` 直接取 `open_entry` 的 `id` 和 `description`，在自由记录暂停点〔＋ 插入事件〕时，`original.title` 会变成 `"待机"`，主窗 `InsertCard` 的 `over.elapsedMs` 也会算成待机时长而非暂停前自由记录的已用时长。
  2. **`MiniSnapshot` 与 `windowBus` 现有类型缺口**：
     - `MiniSnapshot`（`windowBus.ts:32-51`、`miniProjection.ts:20-31`）目前没有 `viewSeq`、`timerStateToken`、`canInsert`、`insertDraft`；小窗无法拿到发起 `beginInsertDraft` 所需的 `expectedTimer`；
     - `MiniWindowBus.ready()` 与 `MainWindowBus.onReady()`（`windowBus.ts:57, 70, 75, 100`）目前无参数，未传递 `ownerSession`；
     - `dispatchMiniCommand`（`homeService.ts:245-288`）目前把所有小窗命令都包在 `run(ctx, ...)` 写事务里，并对带 `revision` 的命令强校验 `command.revision !== tx.revision`。
  3. **操作历史动作与主体定位**：`historyCapture.ts:56` 在 `locate: 'none'` 时取 `all.find(c => c.type === 'entry')`。而插入事件会同时改动「被截断的原条目（起点更早，排在 `all` 第一个）」和「新建的插入条目（排在第二个）」。若不指定新建插入条目为主体，历史记录的 `subject` 会绑到被截断的原条目或待机条目上。
- **应改**：
  - `InsertDraft.original` 明确区分当前打开条目与原事目标：当 `open.kind === '暂停'` 时，原事目标取 `resume`（`state.resume_entry_id`），标题取 `card ? card.content : resume.description`，主窗 `InsertCard` 的 `over` 与 `homeProjection.ts:30-35` 保持同源计算；仅当目标原事名称被编辑时刷新 `original.title`。
  - `MiniSnapshot` 增加 `viewSeq: number`、`timerStateToken: string`、`canInsert: boolean`、`insertDraft: { id: string; owner: 'main' | 'mini'; ownerSession: string; at: string; phase: 'editing' | 'committing'; originalTitle: string; isCard: boolean } | null`；`ready(ownerSession: string)` / `onReady(handler: (ownerSession?: string) => void)` 传递会话 ID（主窗在 `onReady` 中通过 `readSerial` 仅回收 `owner === 'mini' && ownerSession !== nextSession && phase === 'editing'` 的旧草稿）。
  - `beginInsertDraft` / `cancelInsertDraft` 在 `miniController` 中走协调器的 `readSerial` 分支，不进 `dispatchMiniCommand` 的 `run()`；`commitInsertDraft` 不带 `revision` 字段（仅校验 `epoch`、`draftId`、`ownerSession`、`expectedTimer` 与有效原事），并在 `historyActions` 中登记动作（`subject: 'entry', locate: 'result'`，事务返回新建插入条目的 `id`）。

### S4 主窗切页/卸载与小窗隐藏的自动撤回需按 `owner` 隔离，且非 owner 镜像窗必须禁用写控件与读数点击

- **位置**：`src/app/MainApp.tsx:239, 257`、`src/pages/home/HomePage.tsx:226-303`、`src/pages/home/InsertCard.tsx:42, 146-176`、`src/app/MiniApp.tsx:74-79, 215, 229, 250-256`，对照 ADR 0024 §1 第 21/27 行、§2 第 42/48/50 行、§4 第 70 行。
- **现状问题**：
  1. **主窗切页会卸载 `HomePage`**：`MainApp.tsx:257` 仅在 `page === 'home'` 时挂载 `<HomePage>`。ADR 0024 §2 规定「main owner 离开首页、隐藏窗口或组件卸载即撤回」同时规定「主窗窗口内切页不终止 mini 草稿」。若 `HomePage` 的卸载 cleanup 或主窗隐藏事件无条件调通用 `cancelInsertDraft`，用户在主窗切到日历/列表页查看信息时会把小窗正在写的 `owner === 'mini'` 草稿误撤掉。
  2. **小窗隐藏不能走 `leaveEdit` 的自动提交**：`MiniApp.tsx:77, 215` 在收到 `mini-visibility: { visible: false }` 时调用 `leaveEdit.current()` -> `closeEdit(true)`（有字就发 `editOpen` 写盘）。而显式插入草稿要求「mini owner 隐藏/关闭/重载即撤回；普通输入失焦不提交、不撤回」。
  3. **镜像态与草稿态的未落盘防呆**：
     - `InsertCard.tsx`（第 147, 174 行）目前在 `draft === undefined` 时会渲染 `〔暂停〕/〔继续〕` 和 `〔结束原任务〕`。当 `draft.owner === 'mini'` 时，主窗 `InsertCard` 处于镜像态（条目尚未落盘），若直接传 `draft={undefined}` 会漏出 `〔暂停〕` 和 `〔结束原任务〕` 按钮（点下会因无插入条目报错）；
     - `MiniApp.tsx`（第 229, 250, 255 行）在草稿期间（无论 `owner === 'mini'` 还是 `owner === 'main'` 镜像），若不禁用读数 `<TimeField>`，点击读数会去改底层原条目的时长；当 `owner === 'main'`（小窗显示镜像）时，点击标题 `onTitle` 或分类按钮也会误开普通编辑。
- **应改**：
  - 协调器提供两类撤回入口：
    1. **生命周期自动回收** `cancelDraftByOwner(owner: 'main' | 'mini', ownerSession?: string)`：仅当当前草稿 `draft.owner === owner`（且 `phase === 'editing'`）时撤回。主窗切页/`HomePage` 卸载/主窗隐藏只传 `'main'`；小窗隐藏/关闭/`onReady` 新会话只传 `'mini'`。
    2. **用户显式撤回** `cancelDraft(draftId: string)`：用户在主窗或小窗显式点击〔撤回 / 回到原事 / Esc〕时调用，只要 `draft.id === draftId && draft.phase === 'editing'` 即可撤回（允许非 owner 从镜像窗撤回）。
  - `InsertCard` 支持 `mirror` 模式（当 `draft.owner === 'mini'` 时，标题区显示「正在小窗写插入事件…」，隐藏项目选择、`〔暂停〕/〔继续〕` 与 `〔结束原任务〕`，仅保留〔回到任务 / 回到原来的事〕撤回）。
  - `MiniApp` 在 `insertDraft !== null` 期间统一禁用 `<TimeField>` 读数编辑（`canEditTime = false`）与自动完成弹层 `Suggest`；当 `insertDraft.owner === 'main'`（小窗为镜像）时，禁用标题点击与分类下拉，右侧动作仅显示撤回 `↩`（及 520×88 的关闭 `×`）。

### S5 `viewSeq` 必须在捕获 `(snapshot, draft)` 视图的同一同步时刻分配并严格单调比较，且纯草稿变化需主动通知主窗与小窗

- **位置**：`src/platform/windowBus.ts:85-98`、`src/services/miniController.ts:13, 38-41`，对照 ADR 0024 §2 第 3 段、§3 第 1 段。
- **现状问题**：
  1. `acceptMiniSnapshot`（`windowBus.ts:85-89`）目前按 `next.revision >= seen.revision` 过滤。由于纯草稿建立/撤回走 `readSerial`、不改变 `revision`，若 `viewSeq` 不是在同步读取 `(ctx.snapshot(), coordinator.draft())` 的同一刻递增，或者 `acceptMiniSnapshot` 对带 `viewSeq` 的快照未按严格递增过滤，异步 `emitTo` 乱序到达时仍可能让旧草稿快照覆盖新撤回快照。
  2. `readSerial` 不会触发 `ctx.publish(snapshot)`，因此不会触发 `ctx.onSnapshot` 和 `appStore` 更新。若协调器不主动触发通知，小窗发起 `beginInsertDraft / cancelInsertDraft` 后主窗 `HomePage` 不会重绘，主窗本地发起/撤回草稿后小窗也不会立刻收到推送。
- **应改**：
  - `connectMini` 的 `push()` 在同步读取 `const snapshot = ctx.snapshot(), draft = coordinator.current()` 时立即分配 `const viewSeq = ++seq`，再调用 `await bus.push(projectMini(snapshot, ctx.mainEpoch, viewSeq, draft))`；`acceptMiniSnapshot` 在同一 `epoch` 内对带 `viewSeq` 的快照采用 `next.viewSeq > seen.viewSeq` 判据。
  - 协调器暴露 `onChange(listener)`，在草稿建立、撤回、标题同步、提交消费或因令牌变化失效时，同步更新主窗草稿状态（驱动 `HomePage` 重渲染）并触发 `connectMini` 的 `push()`。

## 建议（Suggestions）

### N1 在 `homeService.commitInsertDraftInTx` 中统一执行 `parseEntryText` 行内项目/标签解析

- **位置**：`src/shared/tags.ts:4`、`src/pages/home/InsertCard.tsx:119-125`、`src/pages/home/HomePage.tsx:300`、`src/app/MiniApp.tsx:205-210`，对照 ADR 0024 §1 第 27 行、§4 第 66/70 行。
- 0.3.1 的 `HomePage.tsx:300` 提交草稿时直接传了 `tags: []` 且未調 `parseEntryText` 解析行内 `@项目` 与 `#标签`。建议在 `commitInsertDraftInTx(tx, { text, project })` 内统一调用 `parseEntryText(text, tx.settings.lists.projects.map(p => p.name))`（行内 `@项目` 优先于选择器 `project`；去掉 `#标签 / @项目` 后若 `description` 为空则回退原词或拒绝空正文），避免在 `InsertCard` 与 `MiniApp` 两处重复实现解析规则。

### N2 主窗四处卡头入口与小窗最小按钮统一由纯函数 `canInsert` + `!insertDraft` 门控

- **位置**：`src/pages/home/FusedCard.tsx:60, 101`、`src/pages/home/HomePage.tsx:263`、`src/pages/home/FreeCard.tsx:37`、`src/app/shell/MiniWindow.tsx:39-45`。
- 0.3.1 仅在 `FusedCard.tsx:60`（做卡分支）渲染了 `〔＋ 插入事件〕`（且在 `card.status === '待做'` 或 `pending !== null` 时未隐藏、回退到了 `writeOther`），而分开布局的 `TaskCard`、`FreeCard` 与融合布局的自由记录分支均无此按钮。实现时应由服务层同一个纯函数 `canInsert`（结合 `!insertDraft`）统一控制主窗四种视图（融合做卡、融合自由记录、分开做卡、分开自由记录）的 `c-rest` 按钮与小窗（520×88 / 320×46）的 `22×26px` 加号按钮。

### N3 小窗草稿态下切换分类后的焦点保持与 `Esc` 分层处理

- **位置**：`src/app/MiniApp.tsx:25-31, 80-87`。
- 小窗草稿态点开分类列表 `CatList` 选择分类后，应将焦点归还草稿输入框以便直接按 `Enter` 提交；当 `catOpen === true` 时按 `Esc` 先关闭分类下拉，当 `catOpen === false` 时按 `Esc` 触发 `cancelInsertDraft`，避免收起分类下拉时误撤回整张草稿。

## 重点审查项核对表

| 审查重点 | 核对结论 |
|---|---|
| 1. 唯一内存草稿 | **可行（配合 S3 / S4）**。协调器挂在主窗 `Ctx` 生命周期下，不写 `state.yaml`、不进 `Snapshot`；通过区分 `cancelDraftByOwner` 与显式 `cancelDraft`，保证主窗切页不杀小窗草稿、小窗隐藏撤回草稿。 |
| 2. `readSerial` / `run` 队列竞争 | **可行（配合 S1）**。`readSerial` 与 `run` 共享同一 `queue.tail` FIFO 链，天然串行且不嵌套；需按 S1 在 `postCommit` 的 `ctx.publish` 前消费 `committing` 草稿，防止自触发令牌变化告警。 |
| 3. `viewSeq` 排序 | **可行（配合 S5）**。每次 `push` 在同步采样 `(snapshot, draft)` 时分配单调递增 `viewSeq`，小窗按 `(epoch, viewSeq)` 严格单调接收，并由协调器 `onChange` 驱动纯草稿变化的实时推送。 |
| 4. 提交后失败处理 | **需修正 S1 / S2**。区分 `transact` 前抛错（恢复 `editing` 或因令牌变化清草稿）与 `transact` 后 `postCommit` 告警（保持草稿已消费，绝不恢复为可重试）；并防止运行中条目同毫秒截断被 `startInTx` 删掉。 |
| 5. 旧普通入口语义 | **已保持不变**。新增专用 `EntrySource = 'explicitInsert'` 仅由 `commitInsertDraftInTx` 固定传入；普通 `mini`、`timerBox`、`favorite`、`recent`、`continue` 在自由记录下仍走切换，待机点输入仍走 `beginPending`。 |

## 补充审核：ADR 0025（背包开始计时复用旧抽卡擦除）及与 ADR 0024 共用的提交后结构化结果

审核对象：[ADR 0025](../docs/adr/0025-bag-start-wipe.md)（Proposed，v1）、[ADR 0024 v1.1](../docs/adr/0024-explicit-insert-across-windows.md)、[0.3.2 开发执行方案 v1.4](../docs/stages/0.3.2-execution-plan.md)（P3a / P3b）。

### 结论

- **阻塞：0 条**。
- **ADR 0024 S2 收敛确认**：主线程决定对同毫秒/早于当前条目起点的 `beginInsertDraft`（`Date.parse(at) <= Date.parse(open.started_at)`）明确拒绝并提示下一刻重按，不静默 `+1ms`，既保护了原事不被 `startInTx` 当 0ms 抹掉、又保留了真实点击起点语义，完全合理。同时 ADR 0024 v1.1 将主窗草稿表单提升至 `MainApp`（切页/最小化/托盘隐藏保留，显式撤回或小窗 `×` 关闭撤回），消除了主窗切页卸载 `<HomePage>` 丢失草稿的风险。
- **ADR 0025 & 跨 ADR 提交后结构化结果应改：3 条（S6–S8）**。

### S6 `commit.ts` 的 `run()` 应抛出结构化 `PostCommitError`（携带 `warnings: CommitWarning[]` 与 `data`），供 ADR 0024 / 0025 共用而不解析中文字符串

- **位置**：`src/services/commit.ts:134, 149-154, 338-375`，对照 ADR 0024 §3 第 4 段、ADR 0025 §流程与不变量 第 2 段。
- **现状问题**：
  - 当前 `run()`（`commit.ts:150-152`）在 `result.warnings.length > 0` 时直接 `throw new Error(\`数据已提交，后续处理失败：...\`)`，丢失了结构化的 `result.warnings`（`phase: 'settings' | 'projection' | 'reminders' | 'logging'`）、`result.data` 与 `result.committed_at`。
  - 调用方若想区分「提交前失败（`transact` 未成）」与「提交后失败（`transact` 已成，但 `projection` 或 `reminders` 告警）」，或者区分「`projection` 已成功发布（仅 `reminders/logging` 失败）」与「`projection` 自身失败（store 仍停留在旧快照）」，目前只能靠匹配中文错误前缀。
- **应改**：
  - 在 `src/services/commit.ts` 导出结构化错误类 `PostCommitError<T = unknown> extends Error`（含 `readonly committed = true as const; readonly data: T; readonly committed_at: string; readonly warnings: readonly CommitWarning[]; readonly projectionFailed: boolean`）及类型守卫 `isPostCommitError(error)`。
  - **ADR 0024 (`commitInsertDraft`) 联动**：捕获到 `isPostCommitError(err)` 时，因 `err.committed === true`，协调器必须消费草稿（不恢复 `editing`），向用户报告 `err`；
  - **ADR 0025 (`startFromBag`) 联动**：
    - `!isPostCommitError(err)`（提交前失败）：保留 `BagDrawer` / `FlipDeal` 上下文供用户重试，不播 `Wipe`，报告原错误；
    - `isPostCommitError(err)`（已提交但后置失败）：先报告 `err`（提示数据已提交但后续处理失败），关闭 `FlipDeal` / `BagDrawer` 防止重复点〔开始〕；若 `err.projectionFailed === true`（最新投影未发布），则跳过 `Wipe` 动画直接结束。

### S7 `HomePage` 在「开始前无旧任务卡（`previousView === null`）」或融合布局 `FusedCard` 下复用 `frozen` / `Wipe` 的挂载边界

- **位置**：`src/pages/home/HomePage.tsx:128-130, 219-220, 255-285`、`src/pages/home/FusedCard.tsx:26, 53`，对照 ADR 0025 §流程与不变量 第 4 条。
- **现状问题**：
  1. 当前 `HomePage.tsx:130` 写的是 `const live = cardView(home, now), view = frozen ?? live;`。由于 `startFromBag` 是在 `startCard` **提交并发布新快照成功之后**才把 `{ id, cardId, at, previousView }` 传给 `HomePage`，此时 `home.mode` 已是 `'task'` 且 `live` 已是**新卡**。如果开始前首页处于空白卡（`blank`）、引导卡（`guide`）或自由记录卡（`free`），此时 `previousView === null`；若直接 `setFrozen(null)`，`view = frozen ?? live` 会在 `Wipe` 前 300ms 从左往右盖满之前就直接露出底下的**新卡**，无法实现 ADR 0025 第 4 条「没有旧卡时用空白原卡区，不伪造旧任务」。
  2. 融合布局下（`HomePage.tsx:274`），`<FusedCard key={home.card?.id ?? 'none'} card={home.mode === 'task' && home.card ? home.card : null} cardView={home.mode === 'task' ? view : null} fx={task?.fx} />` 的 `card` 传的是当前 `home.card`（新卡），而 `cardView` 传的是 `view`（`frozen` 旧卡）。且当 `frozen` 代表「无旧卡的空白原卡区」时，`task.fx` 挂在 `TaskCard` 上，若渲染空白 `CardFrame` 也需把 `fx={wipeEl}` 挂入该 `CardFrame`。
- **应改**：
  - 将 `HomePage` 的冻结状态定义为判别联合：`type FrozenStage = { kind: 'card'; view: TaskCardView } | { kind: 'blank' } | null`：
    - 当 `previousView !== null` 时设 `{ kind: 'card', view: previousView }`，在 `onCovered` 前保持渲染旧卡 `TaskCard`（融合布局下 `FusedCard` 的 `card` 元数据也与 `frozen.view` 对齐），并在外层 `CardFrame` 挂载 `fx={<Wipe en="START TASK" cn="开始计时" ... />}`；
    - 当 `previousView === null` 时设 `{ kind: 'blank' }`，在 `onCovered` 前渲染带 `fx={<Wipe ... />}` 的空白原卡区 `CardFrame`，`onCovered` 触发时清空 `frozen = null` 露出底下的新卡。

### S8 简化动效（`motionLevel() === 'reduced'`）下 `playAfterWipe` 需补齐 220ms 淡入

- **位置**：`src/ui/effects/Wipe.tsx:18`、`src/pages/home/intro.ts:39-42`、`src/ui/effects/animate.ts:31-40`，对照 ADR 0025 §视觉规格 第 3 段。
- **现状问题**：
  - ADR 0025 §视觉规格规定：「简化：保留现有 FlipDeal 简化流程，开始成功后 220ms 淡入新卡，不出现大色块」。
  - 但现有 `Wipe.tsx:18` 在 `motionLevel() !== 'full'` 时立即同步调用 `onCovered()` 与 `onDone()`，随后 `HomePage.tsx:220` 调用 `playAfterWipe(stage.current)`；而 `playAfterWipe`（`intro.ts:39-42`）内部只调了 `revealLines` 和 `popBars`（底层走 `play()`，在 `motionLevel() === 'reduced'` 下直接返回 `null`），因此 `'reduced'` 下没有任何 220ms 淡入。
- **应改**：
  - 在 `playAfterWipe`（`src/pages/home/intro.ts:39`）中增加 `if (motionLevel() === 'reduced') { fadeIn($(card, 'card'), 220); return; }`（同 `playResumeIntro` 第 34 行做法），使简化动效下不出现大色块且新卡按 220ms 淡入，关闭动效（`'off'`）下不执行任何动画。
