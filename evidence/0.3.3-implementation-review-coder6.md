## 实质阻塞

### A1 / P1：find_items 将不同提交的元数据与正文拼在一起

位置：`src/app/applicationController.ts:681`，尤其 `682`、`693`–`695`；同文件 `312`–`337` 的已提交快照约定；串行读入口 `src/services/commit.ts:203`。

当前先用 `readCommittedView(ctx)` 取快照，再直接 `await ctx.repos.records.getDetails(r.id)`，没有把整个查询接入 `readSerial`。新的全文读已不再是原先纯快照查询，写入可以在 await 时提交。

实测复现：创建“标题A #旧 / 正文A”，暂停 find 的详情读取，另发 update 改成“标题B #新 / 正文B”。写入在查询仍被暂停时已经提交；查询最终返回：

```json
{"text":"标题A #旧\n正文B","tags":["旧"]}
```

这不是任一已提交记录，关键词/标签与返回内容也可能不一致。独立用例 `0.3.3-coder6-api-review.test.ts` 的 R1 明确失败；日志包含 `committedWhileReadHeld=true`。

要求：整个详情读取、快照选择、匹配和结果组装保持同一串行提交视图；不要在控制器添加另一把锁或只修输出字符串。

### A2 / P1：缺失详情被静默当作空正文

位置：`src/app/applicationController.ts:693`–`695` 的 `detail?.body ?? ''`。完成/撤销旧全文也存在同类写法，见 `1310`–`1334`，需按同一规则核对。

独立 R2 将已在快照中的记录详情读取注入为 null；查询成功返回“标题A #旧”，而不是显式错误。合法空正文和文件/读取目标缺失不能合并。这里会悄悄缩短已存在的长记录，不符合旧全文兼容与显式失败要求。

要求：已选定记录的详情缺失明确报错并指出目标；异常读取不得生成空正文成功结果。以真实空正文、缺失记录、读取失败分别验证。

### A3 / P1：控制器重做创建与转换规则，形成第二个业务来源

位置：`src/app/applicationController.ts:887`–`957`、`986`–`1073`；现有共享服务 `src/services/backpackService.ts:61`–`66` 与 `src/services/ideaService.ts:308`–`347`。

create_task 没有复用 createTaskInTx，而是复制 taskWithItems、saveTask/saveCard、refresh 流程。convert 虽最终调用 convertIdeaInTx，却提前再检查修订、已转状态、目标资格、项目、任务与子项容量，随后服务重新检查相同规则。

这是已审结构要求的直接偏离，不应为了丰富 latest_context 留两份判断。要求创建/转换的领域决策与原子编排留在共享 InTx 服务；控制器适配规范输入、映射结构化服务失败与 DTO，不通过再加前置分支修复。保留新协议的严格空数组/空事项拒绝，不能搬旧 taskWithItems 的回退到公开协议。

### A4 / P2：CLI 在读取失败后伪造 record_revision

位置：`cli/execute.ts:225`–`231`，特别是：

```ts
catch {
  return { operationId: explicitOpId, recordRevision: 'ir3:conflict-check' };
}
```

已有回执的方法与本次方法不同时，冲突已经确定。当前却再读详情，任何错误被吞掉后构造假令牌并发送 update/convert。独立 R3 注入详情连接失败，观察到 `get_operation_result → get_idea_details → update_idea(record_revision=ir3:conflict-check)`。

最终返回 OPERATION_CONFLICT 没有造成业务写入，但不能用这个正确错误码掩盖吞掉读取错误、伪造技术字段与额外派发的路径。要求按已知回执直接明确报告方法冲突；移除假令牌及无必要的读取/写请求。

### A5 / P2：MCP 创建任务说明写死错误容量与不存在的设置路径

位置：`mcp/server.ts:402`；实际设置 `src/shared/settings.ts:4`–`6`。

说明称“主线活跃子事项最多5个”、读取 `settings.capacity.mainTasks/sideTasks`，实际 mainItems 默认5但可调1–10，设置键位于顶层。新工具是给 agent 的执行说明，不能和运行规则形成两种容量。

要求描述遵循当前 mainItems/mainTasks/sideTasks，可注明默认值，不把默认写成硬上限或编造字段路径。同步帮助和设置说明时核对内容，不只核对41个名称。

## 验收证据范围与缺口

### E1：P6 JSON 的映射/中断“已验证”常量缺少本套件断言

`evidence/0.3.3-p6-verification.test.ts:451`–`486` 构造六个夹具，正常调用一次 migrateV3，验证备份哈希、最终 schema3 和 mainTasks2。未逐个断言六类标题/详情结果，也没有在本套件注入 journal 中断或执行恢复。

但 `680`–`681` 写入 `adr0026All6MappingCasesVerified: true` 和 `interruptedJournalStateFirstRecoveryVerified: true`。记录/迁移模块单测存在，不自动等于此处的真实磁盘 P6 覆盖。应补实际断言/失败注入及运行证据，或将 JSON 缩窄到本次真正测试的内容。

P6 位于 evidence，`vite.config.ts:11` 仅收 `src/**/*.test.ts`；103文件/772项不包含该套件。交接只写了文件名，需给显式配置和精确运行命令。现有 JSON 不能单独证明所有声明。本席未据此认定 P6 从未运行，也未覆盖原 artifacts 重跑性能套件。

### E2：规模样本字节标注与“冷启动”口径不准确

`evidence/0.3.3-p6-verification.test.ts:507`–`509` 用 JS 字符串长度切片，并以 sc.bodyBytes 标注 UTF-8 字节。按当前生成式独立计算：

| 标称正文字节 | 实际 UTF-8 正文字节 |
|---|---|
| 2048 | 2432 |
| 65536 | 77824 |
| 256 | 304 |

`539`–`552` 先创建上下文并执行 run，之后 `554`–`563` 才量 records.list 的“coldStart”，记录仓库已经被初始化事务读取。此指标不能称第一次冷加载。

要求用实际 UTF-8 字节生成/记录样本、明确首次加载与暖缓存测量条件，保留实际延迟，不追加无依据的产品上限。更深的读缓存、原生 fs 与性能判断由 coder 继续独立核验。

### E3：真实 Named Pipe 有价值，但不等于生产 Rust/Tauri 全链

P6 `170`–`199` 用 Node net.createServer 转调真实 ApplicationController/repo；`225`–`229` MCP 使用 SDK InMemoryTransport；CLI `203`–`222` 通过 runCli 注入客户端与部分文件读取器。它覆盖了真实 Named Pipe + 生产适配器/控制器 + Node 磁盘仓库的集成，保留这个有效边界。

它没有经过实际 Rust mcp_bridge、已安装 WebView2、原生写门/窗口，部分 --details-file / --items-file 输入由内存字典提供。fixture 的 atomicWrite 实际 writeFileSync（`79`–`85`），也不能证明 Tauri 原子替换/编码行为。交接明确未测的原生窗口交互和安装包回退仍未关闭，不能将此集成概括为原生验收已完成。
