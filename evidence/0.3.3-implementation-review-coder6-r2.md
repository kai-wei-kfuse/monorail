## 新阻塞 B1 / P1：窗口回执混入windowDoc破坏共享输出

位置：`src/app/ideaWindowController.ts:335`–`353`、`447`–`464`。save用command=update_idea，却将完整windowDoc和idea/noop一起放入runOperation的data；draft-create同样用create_idea写 `{idea, windowDoc}`。公开契约只允许 `{idea,noop}` 或 `{idea}`，详情在规范input中已保留。

本席W1运行生产connectIdeaWindows → updateIdeaInTx → runOperation/Journal，写出窗口保存回执，再调用生产CLI和MCP适配器同ID同参数重放。get_operation_result真实返回committed，data包含windowDoc；两个适配器重放均失败，CLI退出3、MCP isError=true，实际错误是：

```text
EXECUTION_FAILED / not_executed
Unrecognized key: "windowDoc" at data
```

观测错误码不是主审推测的INVALID_RESPONSE：ApplicationController内部严格输出解析先抛错并映射EXECUTION_FAILED。无论名称如何，已提交操作不能因错误输出形状被描述为未执行并引导新ID重试。

要求：窗口与公开方法使用同一严格共享data，在提交前验证，不把完整详情再复制进receipt.data。窗口独有reply另行构造；原操作正文可依规范input/摘要处理，附件/完成者/完成时间等缺失信息必须明确处理，不能读当前记录冒充原结果或用null掩盖未知。

## 新阻塞 B2 / P1：草稿技术身份改变同一create_idea的规范请求

位置：`src/app/ideaWindowController.ts:83`–`91`、`449`；公开create规范在`applicationController.ts`的create_idea分支。

窗口draft-create规范input含draft_id、task_id、attachments；公开create只有title/details_markdown/needs。W2专门使用**无附件、无所属任务**的草稿，同标题、正文、needs和operation_id调用CLI/MCP create，仍返回OPERATION_CONFLICT：额外draft_id、null task_id和空attachments已经令指纹不同。

这不是用户改变业务参数。要求在同一概念处定义规范输入，技术草稿身份与公开业务意图分开；默认空值也必须同源。窗口附加业务字段（如真正新附件）不能简单当技术字段丢掉，需明确公开可表达/只回查的边界并保持原ID换业务参数冲突。不得给同一个method保留两套不兼容的请求/回执格式。
