## 结论

- **阻塞：0 条**。新增 18 个方法（5 读 + 13 写，合计 35 方法：10 读 + 25 写）完整覆盖 A（今日/明日任务板）、B（做卡流与插入收尾）、C（整张任务完成/重新打开、想法重新打开）、D（多维回看与操作历史查询）；单层 `readSerial` + 抽出共享 `InTx` + 统一 `runOperation` 回执与操作历史的设计与现有架构完全吻合。

## 应改（Should-Fix）

### S1 条件式 `expected_state` 在跨入口/同 ID 重放时会触发 `cli/execute.ts` 误抛 `RECEIPT_INCOMPLETE`

- **位置**：`cli/execute.ts:84-123`（`resolveWriteMeta`），对照 ADR 0023 §2 第 5–7 条、执行方案 §3.3「跨 CLI/MCP 重放」。
- **现状问题**：
  - ADR 0023 §2 第 5 条规定 `complete_task` / `reopen_task` 的 `expected_state` 为可选（仅在停止目标任务或 `makeRoom` 任务的当前卡时服务端才要求校验），同时写「CLI 沿用 `needsExpectedState=true` 获取并传入令牌」。
  - 但 `resolveWriteMeta`（`cli/execute.ts:101-121`）在 `needsExpectedState === true` 且 `lookup.status === 'committed'`、`lookup.command === method` 时，若历史回执 `request.arguments.expected_state` 为空，会直接抛 `RECEIPT_INCOMPLETE`。
  - 如果首次调用由 MCP 在无关计时状态下**未传** `expected_state` 成功提交，随后用同一 `operation_id` 经 CLI 重放（或由带 `--operation-id` 的调用重试），CLI 会因回执无 `expected_state` 误报 `RECEIPT_INCOMPLETE`；反之若去拉取当前 `expected_state` 填入，又会因 `commit.ts:241`（`existing.input !== input`）报 `OPERATION_CONFLICT`。
- **应改**：
  - 在 P6 与 ADR 0023 §2 写明：对 `expected_state` 可选的方法（`complete_task` / `reopen_task`），当 `resolveWriteMeta` 命中同 `method` 的 `committed` 回执且命令行未显式传 `--expected-state` 时，**按回执实际的 `expected_state` 原样恢复**（回执有字符串则恢复该字符串，回执未带则保持 `undefined`），不抛 `RECEIPT_INCOMPLETE`。
  - 同时在 `applicationController.ts` 中构造 `runOperation` 的 `normalized` 输入时，所有 13 个新写方法必须保持与 `application.ts` 输入契约一致的字段名（未传 `expected_state` 时不写入空串或多余键），确保 `get_operation_result` 返回的 `request.arguments` 与原请求严格可比。

### S2 抽取 `complete` / `keepGoing` 的 `InTx` 时必须补齐 `insertStateInTx` 拦截，防止 `stopRefInTx` 静默截断插入计时

- **位置**：`src/services/cardService.ts:103-114, 128-133`、`src/services/tracking/timerService.ts:90-94`，对照 ADR 0023 §4 第 1 条、执行方案 P4。
- **现状问题**：
  - `cardService.split`（`cardService.ts:143`）已有 `if (insertStateInTx(tx)) throw new Error('IN_AWAY_ACTIVITY：正在插入别的事，先回到任务再缩小');`。
  - 但 `cardService.complete`（`cardService.ts:103-114`）与 `keepGoingCard`（`cardService.ts:128-133`）只调了 `requireCurrent(tx, card)`（仅检查 `tx.state.current_card !== card.id || tx.state.rest`），**没有检查 `insertStateInTx(tx)`**（GUI 在插入中靠 `InsertCard` 盖住卡片和小窗隐藏完成按钮来防呆）。
  - 一旦在插入状态（`inserting` 或 `insertPaused`，此时 `current_card` 仍是底层原卡）调用未加拦截的 `complete` / `keepGoing`，底层 `stopRefInTx`（`timerService.ts:90-94`）因 `resume?.card_id === ref && open?.kind !== '普通'` 会清空 `resume_entry_id` 并调 `startSystemInTx(tx, '待机')`，直接把正在计时的插入事件静默截断成待机。
- **应改**：
  - P4 抽取 `completeCardItemInTx` / `keepGoingCardItemInTx`（及 `splitCardItemInTx`）时，必须在事务内统一校验 `insertStateInTx(tx)`（抛 `IN_AWAY_ACTIVITY`）、`tx.state.rest !== null`（抛 `IN_DEGRADE_REST`）、`tx.state.pending_id !== null`（抛 `PENDING_CONFIRMATION`）以及 `!tx.settings.taskMode`（抛 `TASK_MODE_OFF`）。
  - 注意：**卡暂停中**（`open.kind === '暂停'`，`insertStateInTx(tx) === null`，`current_card === cardId`）在 GUI 首页允许直接点〔完成〕/〔接着做〕/〔缩小〕，且 `checkNormalPreconditions`（`homeService.ts:294-300`）本来就允许 `暂停` 态通过；单测应覆盖「卡暂停中允许 complete/keep/split，插入中/插入暂停中拒绝 `IN_AWAY_ACTIVITY`」。

### S3 `planService.skipCardInTx` 的候选集与 `pickFromPlan` 在「今天先不排 / 待确认带入」下不一致

- **位置**：`src/services/planService.ts:76-83, 142-145`、`src/domain/picker/pick.ts:43-53, 68-78`，对照 ADR 0023 §3 第 5 条、执行方案 P4。
- **现状问题**：
  - `planService.skipCard`（`planService.ts:142-145`）传给 `skipCardInTx` 的 `drawable` 只调了 `drawableOnPlan`（只遍历 `plan.items`，`pick.ts:46`）。
  - 当 `plan.items` 为空且 `skip_until_planned === true`（今天先不排，从全背包抽）时，`pickFromPlan`（`pick.ts:71`）的候选是全背包 `isCandidate(card, tasks) && card.id !== activeCard`，但 `drawableOnPlan` 返回 `[]`。这导致：
    1. `skipCardInTx` 第 78 行 `if (!plan.items.some(...) && !plan.skip_until_planned)` 在 `skip_until_planned === true` 时对任何 `cardId`（甚至不存在或已完成的卡）都放行；
    2. 第 80 行 `left` 永远是 `[]`，`plan.seen` 每次都被重置成 `[cardId]`，无法跨多张背包卡累积 `seen`。
  - 此外，当 `!plan.carried_confirmed && plan.items.some(item => item.carried)` 时，今日板子处于待确认带入状态（`pickFromPlan` 返回 `confirmCarry`），此时也不应允许写 `seen`。
- **应改**：
  - 在 `domain/picker/pick.ts` 抽出与 `pickFromPlan` 同源的当前可抽候选计算函数（区分「待确认带入无候选」「`plan.items` 非空取 `drawableOnPlan`」「`plan.items` 为空且 `skip_until_planned` 取全背包 `isCandidate`」），由 `pickFromPlan`、`planService.skipCardInTx` 与 `skip_task_item` 共用。
  - `skip_task_item` 检查目标 `card_id` 必须属于当前可抽候选集，否则明确拒绝（如 `CARD_NOT_DRAWABLE` 或 `CARRY_CONFIRMATION_REQUIRED`）。

### S4 只读查询队列 `readSerial` 缺少 `snapshotFailure` / `signal` 检查，且 `drawFromPlan` 缺少 `taskMode` 门控、`get_task_plan` 需按 `asOf` 现算分钟

- **位置**：`src/services/commit.ts:166-174, 338`、`src/services/dealService.ts:28-39`、`src/services/planProjection.ts:22, 37`，对照 ADR 0023 §3 第 1/3/4 条、§5 第 1 条、执行方案 P4/P5。
- **现状问题**：
  1. `readSerial`（`commit.ts:166-174`）只检查 `if (queue.failure)`，**未检查 `queue.snapshotFailure`**（`commit.ts:338`：当 journal 已落盘但 `postCommit` 投影失败时，`ctx.snapshot()` 仍停留在上一次旧快照），且未像 `readOperation`（`commit.ts:209, 213`）那样支持 `AbortSignal` 入队前与出队后取消。
  2. `dealService.drawFromPlan`（`dealService.ts:28-39`）已是 `readSerial` 包装（controller 切勿在外层再套一层 `readSerial` 否则永久死锁），但内部**未检查 `ctx.settings.taskMode`**（GUI 靠隐藏抽卡按钮防呆）。
  3. `Snapshot.plan`（`commit.ts:350`、`planProjection.ts:22, 37`）里的 `minutesToday`、`achieved` 与 `drawable` 只算到上次提交时刻 `tx.at`（GUI 靠 `runningSince` 每秒补算）。若 `get_task_plan` 直接返回 `Snapshot.plan`，在卡片持续计时未发生新提交期间会返回过时的 `minutes_today` 与 `achieved: false`，与 `draw_task_item` 按 `ctx.now()` 现算的结果矛盾。
- **应改**：
  - P4/P5 明确：`readSerial`（或各只读方法在 `readSerial` 回调开头）统一检查 `signal?.aborted` 与 `assertQueueHealthy(ctx)`（含 `snapshotFailure` 与未就绪 `APP_NOT_READY`），保证单层排队、不嵌套调用其他 `readSerial` 根函数。
  - `draw_task_item` 在 `taskMode === false` 时明确拒绝 `TASK_MODE_OFF`（或返回结构化状态，与 ADR 0021 §10 一致）。
  - `get_task_plan` 在 `readSerial` 内通过 `ctx.repos.plans.read(targetDay)`（无文件时内存返回 `emptyPlan(targetDay)`，不落盘建文件，见 `planRepo.ts:30-31`）并以本次 `asOf = ctx.now()` 现算 `minutes_today`、`achieved` 与 `drawable`。

### S5 `get_recap` 对未知 `bucket` 与 `custom` 日期在现有 domain 层会静默回退，需在 API 边界显式拦截

- **位置**：`src/domain/review/recap.ts:129`、`src/domain/timeline/recap.ts:9, 57-60`、`src/shared/recap.ts:61`，对照 ADR 0023 §5 第 2–3 条、执行方案 P5。
- **现状问题**：
  1. `computeRecap`（`domain/review/recap.ts:129`）写的是 `const bucket = query.bucket ? bucketIndex.get(query.bucket) ?? null : null;`——当传入不属于当前解析周期的 `bucket` ID 时，会**静默回退为整周期汇总**而非报错。
  2. `resolvePeriod('custom')`（`domain/timeline/recap.ts:58`）在 `from` / `to` 缺省时静默回退为 `today`；且 `fmt`（`recap.ts:9`）用 `new Date(y, m - 1, d)`，若只用正则 `/^\d{4}-\d{2}-\d{2}$/` 校验，`2026-02-31` 会静默进位到 3 月。
  3. `RecapResult`（`src/shared/recap.ts:101-122`）当前无 `asOf` 字段（`range.effectiveTo` 在 `lastWeek` 等历史周期下等于 `range.to` 而非计算时刻），缓存命中时拿不到原计算时刻。
- **应改**：
  - `RecapResult` 增加 `asOf: string`（由 `computeRecap` 原样记录传入的 `asOf`），`get_recap` 输出 `computed_at: result.asOf`；且对缓存结果只读序列化，不就地修改缓存对象。
  - `get_recap` 输入契约用 `z.iso.date()` 校验真实日历日；`period === 'custom'` 时必填 `from` 与 `to`，`period !== 'custom'` 时禁止传 `from` / `to`。
  - 若请求带了 `bucket`，核对 `result.buckets.some(b => b.id === bucket)`，不匹配时明确报 `INVALID_BUCKET`。
  - `RecapBucket.byKey` 输出 schema 复用 `src/shared/application.ts:159` 的 `createDurationMapSchema()`。

## 建议（Suggestions）

### N1 同步 `buildTimerContext.allowed_actions` 与 `historyActions` 的新动作条目

- **位置**：`src/app/applicationController.ts:94-126`、`src/shared/history.ts:98-102`。
- `timerContextSchema.allowed_actions` 是 `z.array(z.string())`（非枚举，不影响旧客户端 strict 解析）。建议在 `buildTimerContext` 中同步加入 B 类动作：
  - `mode === 'away'`（插入中/插入暂停）：加入 `'end_original_task'`；
  - `mode === 'running'` 或 `'paused'` 且 `activeCard !== null`：加入 `'complete_task_item'`、`'keep_going_task_item'`、`'split_task_item'`。
- `historyActions` 补齐 13 个 `auto.<method>`：注意 `auto.end_original_task` 的底层回到目标可能是自由记录而非卡片（ADR 0023 §1 已指出），`intent.subject` 应仅在 `resume?.card_id` 非空时传 `{ type: 'card', id: resume.card_id }`。

### N2 CLI 的 A 类写命令统一只收显式 `--day <YYYY-MM-DD>`

- **位置**：`cli/commands.ts`、`cli/execute.ts`，对照 ADR 0023 §1 表与 §3 第 1 条。
- 只读 `monorail plan show --day today|tomorrow` 接受相对词并返回解析后的 `day: YYYY-MM-DD`；A 类写命令（`plan add/remove/edit/carry/skip-today/skip`）在 CLI 侧建议只接受 `--day <YYYY-MM-DD>`（用 `z.iso.date()` 校验），不接受 `--day today|tomorrow`，从根源消除跨日带 `--operation-id` 重试时 CLI 重新解析相对日期导致的冲突。

### N3 `list_operation_history` 的默认日期计算与筛选口径

- **位置**：`src/services/historyService.ts:20-24`、`src/data/historyRepo.ts:56-65`。
- 省略 `from_day` / `to_day` 时的 `toDay = today(ctx, at)` 应放进 `readSerial` 回调内部计算；显式传入时校验 `from_day <= to_day`。
- 明确 `source` 筛选枚举：建议支持 `'manual' | 'system' | 'mcp' | 'cli' | 'automation'`，或提供与 GUI「仅自动化」一致的 `'all_automation'`（匹配 `mcp | cli | automation`，复用 `historyService.isAutomation`）。

### N4 Rust `is_write_method` 与 `applicationContracts` 的自动对齐测试

- **位置**：`src-tauri/src/mcp_bridge.rs:62-67`、`mcp/compatibility.test.ts`。
- `is_write_method` 加入 5 个新只读方法（`get_task_plan`、`draw_task_item`、`get_task_details`、`get_recap`、`list_operation_history`）后，除 Rust 侧单测外，建议在前端/MCP 测试中读取或对照 10 个 `readOnly: true` 方法名，防止后续增改方法时漏改 Rust 侧名单。

## 定向复核结论（2026-11-07 · 针对 ADR 0023 修订1 & 执行方案 v1.2）

- **复核结论：通过（0 阻塞 / 0 新增应改）**。`S1–S5` 与 `N1–N4` 均已完整、准确写入 [ADR 0023 修订1](../docs/adr/0023-032-automation-coverage.md) 及 [0.3.2 开发执行方案 v1.2](../docs/stages/0.3.2-execution-plan.md)（P4–P6 及 §3 回归验证）。
- **定向核对明细**：
  1. **S1（`optional` 状态令牌重放与 `normalized`）**：ADR 0023 §2 第 8–9 条、执行方案 P6 已明确 `resolveWriteMeta` 区分 `none / required / optional`；`complete_task` / `reopen_task` 命中同方法回执且未显式传令牌时，按回执原样还原字符串或保持省略，不抛 `RECEIPT_INCOMPLETE`、不补当前令牌；`normalized` 与契约字段同名且缺省不填 `null`/空串/多余键，并覆盖跨 MCP/CLI 双向同 ID 重放测试。
  2. **S2（`complete / keep / split` 插入态拦截与卡自身暂停放行）**：ADR 0023 §4 第 1 条、执行方案 P4 已明确三项共享 `InTx` 统一校验 `taskMode`、`rest`、`pending`、`requireCurrent` 与 `insertStateInTx`（插入中/插入暂停报 `IN_AWAY_ACTIVITY`），同时明确卡自身暂停中（`kind === '暂停'`）仍允许执行。
  3. **S3（全背包/带入确认同源候选与 3 卡 `seen` 轮转）**：ADR 0023 §3 第 6 条、执行方案 P4 已明确从 `pickFromPlan` 抽出同源候选计算供 `pick` / `skipCardInTx` / `skip_task_item` 共用，覆盖板子项、空板 `skip_until_planned` 全背包候选、待确认 `carry`（`CARRY_CONFIRMATION_REQUIRED`）与非候选拒绝（`CARD_NOT_DRAWABLE`），并锁定至少 3 张全背包卡的 `seen` 累积与重开新轮测试。
