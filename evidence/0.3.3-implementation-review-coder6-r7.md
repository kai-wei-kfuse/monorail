## G1/G2：generation 仍可缺失或错误

生产 `createDraftCheckTracker` 的 payload.generation 仍 optional；非法数值折算 gen=null 后继续按 ID 接受，合法小数还用 Math.floor 降为整数。同 ID restore 没有核对 activeGeneration。

实际回归：

- 已持有 `(opaque-current, generation=2)` 时，缺 generation 的新 check 被接受为 opaque-next，覆盖 active；预期不推进。
- 同一 requestId 但缺 generation 的 restore 返回 true，解除锁定；预期只有同一 `(requestId,generation)` 的有效恢复能解锁。
- 测试还包含 NaN/Infinity/0/负数/小数/超 JS 安全整数，以及同 ID 错代、同代错 ID。当前循环在首个缺失值就失败，因此不把其后每个值都冒称独立已验证；修复后会完整走完。

要求与主审一致：新协议没有旧兼容，generation 必须是正安全整数；check/restore 一并核验，不保仅 ID 回退，不截断小数。安全整数是 JavaScript 传输精度约束，不是新增产品检查次数上限。

测试在 [前端回归文件](0.3.3-coder6-maintenance-window-review-r6.test.ts)末尾追加3项，现共10项；[配置](0.3.3-coder6-maintenance-window-review-r6.config.ts)仍显式收 evidence 文件，不用 npm test 路径冒充定向执行。

## O1/O2：实际调用者仍取消别人的轮次

新增 [归属测试](0.3.3-coder6-maintenance-owner-review-r7.test.ts)与[配置](0.3.3-coder6-maintenance-owner-review-r7.config.ts)，执行真实 SettingsScreen.onChangeDir 回调和真实 installUpdate，不仅测试 native.cancel(undefined)。

### O1 设置页准入失败后取消全局 other-operation

生产 tracker 先收到另一操作的有效检查，global active 为 other-operation。本次设置页检查直接拒绝，未签发自己的 ticket。实际执行 SettingsScreen 的换目录回调后：

```json
{"SETTINGS_UNOWNED_CANCEL":[["other-operation"]]}
```

对应设置页 catch 用 reqId ?? nativeIdeaWindows.getActiveCheckRequestId() 猜取消归属；MainApp 退出 catch 还会从 tracker/global active 推 cancelId，主审已亲读确认同类问题。没有本次 ticket 的准入拒绝不能取消已存在轮次。

### O2 安装服务 prepare 失败仍调用 cancelInstall

真实 installUpdate 在 prepareInstall 立即拒绝、未持有 native ticket 时，仍调用 cancelInstall，仅传错误文本：

```json
{"INSTALL_UNOWNED_CANCEL":[["已有别人的维护轮次，本次 prepare 未取得 ticket"]]}
```

Rust cancel_install 又直接取 Gate 的全局 active，而非本次调用 ticket，组成实际取消别人轮次的路径。不能只让 Gate.cancel(None) 拒绝，再由上层读全局 ID 绕过。

要求：本次 check 在 dirty/后续错误时显式携回自己的 ticket；准入失败没有 ticket，就不取消已有维护。MainApp、Settings、updateService/Rust 安装使用同一真实 ticket，不留全局 active 猜属或第二份归属状态。收到最终结构化结果/错误 ticket 类型后，本席再补“持有自己的 dirty ticket 正确取消并恢复”的正向回归。

归属测试用受控 React hooks/IPC 边界运行生产设置页回调，用 MemoryFs 上的真实 Ctx 运行安装服务；不是 React DOM 挂载、原生安装器或 NSIS 实测。回调结束/报告由真实 Promise 路径观察，没有轮询次数上限或伪超时成功。
