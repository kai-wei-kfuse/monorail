## 首轮 [P1] 创建待确认失败后，本地 manualPending 仍将界面视为已创建会话（已关闭）

位置：`src/pages/home/useEntry.tsx:22,27,31,69-79`，以及 `HomePage.tsx:159` 的 beginPending 适配。

`next()` 在事务确认前调用 `setManualPending(true)`，`deciding = pending !== null || manualPending` 随即解除底层冻结。真正的 beginPending 经队列写入后才发布 store；错误会由 app/actions.guard 上报并返回 undefined，TimerActions 适配没有把成功或失败交回 hook。

如果该事务失败，pending ID、entry ID 和 away ID 均未改变，依赖这些 ID 的 effect 不会再次执行，manualPending 保持 true。结果是 store.pending 为空，底层输入却已经可写、状态为待确认；融合卡的“放弃”又要求真正 pending 非空，因此连明确的放弃按钮都没有。此状态不能作为一个已经建立的业务会话。

复现使用真实 React hook 与 DOM 事件，在 beginPending 边界注入“已报告错误且返回 undefined、store 不发布”的失败结果，和现有 guard 对事务失败的输出一致；不是在真实用户目录制造 IO 错误。实际输出：

```json
{
  "committedPending": null,
  "uiDeciding": true,
  "uiFrozen": false,
  "inputReadOnly": false,
  "beginPendingCalls": 2
}
```

**修复要求：** 消除重复的业务状态来源，让已提交 pending 投影决定待确认语义；本地可保留输入草稿与焦点意图，但不能把未成功的事务显示成有效 pending。不要再叠加一个失败标记、额外超时或静默回退来绕过问题。同时合并 next 与随后的 focus 对 beginPending 的重复派发。验证成功、延迟提交、失败以及已聚焦只读框后点“＋”的路径。

## 首轮 [P2] pending 与 away 并存时，自由输入分支隐藏了暂停/停止（已关闭）

位置：`src/pages/home/TimerBar.tsx:129-134`、`src/pages/home/FusedCard.tsx:104-106`；FreeCard 的 pending 动作分支也只保留放弃。

已批准 ADR 的 pending 并存契约明确允许点击底层“暂停”关闭当前临时活动并保留 pending。然而 TimerBar 的 pending 分支与暂停分支互斥，停止按钮又要求 `!deciding`；融合自由输入分支在 `E.deciding` 时只显示抽卡与放弃。

触发：自由记录进行中 → 插入临时活动 → 点击“＋”并成功创建 pending。此时抽屉仍在，但两种布局的底层都没有暂停/停止入口。主审对实际组件作真实 React 服务端渲染后检查 DOM，结果均为：

```json
{
  "fused": { "pause": false, "stop": false },
  "split": { "pause": false, "stop": false }
}
```

**修复要求：** 在 pending 与 away 并存时，保留作用于当前 open 临时活动的暂停/停止，以及 pending 自己的放弃动作。点击暂停/停止后正确收起抽屉并保留已提交 pending ID、起点与输入；不向冻结的 resumeEntry 发写入命令。覆盖融合与分开布局的实际点击事件与提交后状态。

## 第二轮复审：普通编辑失焦被草稿保留规则拦截（P2，已关闭）

依据 Runner 消息 `01M6B9VSBDA4GX6XGHK85FMAR4`，已读取新版 useEntry、三个首页分支、AwayDrawer、状态测试和浏览器报告，并复跑原始复现：两布局暂停/停止均存在；失败的 beginPending 只派发一次，store.pending 为空时 UI 保持 deciding=false、isFrozen=true、readOnly=true。原始复现退出码 0，见 [原问题复核](0.2.5-away-rereview-original-repro.log)。manualPending 已删除。抽屉改名也已修正为提交新 text，浏览器报告补充了项目/标签与读数确认/取消记录。

### 新回归及根因

`src/pages/home/useEntry.tsx:74` 对任何带 `data-entry-keep` 的目标都直接返回，未限定 pending。与此同时 `TimerBar.tsx:66,133` 与 `FusedCard.tsx:109` 给普通计时的停止/暂停按钮也加上该属性。结果是为保留待确认草稿增加的规则，也阻止了普通运行条目的失焦保存。

触发步骤：无 pending、无临时活动，普通自由记录「学 408」进行中 → 点击名称进入编辑 → 输入「复习 408」→ 点击暂停或停止。预期沿用现有“离开输入组即保存”的规则，先 `editOpen(base.id, { description: '复习 408' })`，再 pause/stop；实际只派发了 pause/stop，新名称没有提交。本地 focused 状态也未在该早退中清除，会让输入继续显示未落盘文字。

主审扩展 `away-review-repro.mjs`，以真实 React 状态更新及 DOM 焦点事件复现两条路径。普通输入改名通过公开输入 handler 设置，随后真实聚焦/点击带标记的控制按钮；只观察对外命令次序，不模拟 hook 实现。输出：

```json
{
  "pause": { "hasPending": false, "hasAway": false, "commandOrder": [{ "command": "pause" }], "editCommittedBeforeControl": false },
  "stop": { "hasPending": false, "hasAway": false, "commandOrder": [{ "command": "stop" }], "editCommittedBeforeControl": false }
}
```

**修复要求：** 将保留 pending 草稿的失焦例外限定于确实存在已提交待确认会话的流程。普通条目编辑继续正常提交并退出编辑；保留 pending+away 以及抽屉收起后仍有 pending 时的草稿行为。优先收窄现有条件，不新增另一套保存或状态恢复分支。补充两布局普通改名后暂停/停止的命令次序与实际持久化回归，同时保留首轮两项修复。
