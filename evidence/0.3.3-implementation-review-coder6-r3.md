## C1 / P1：update将明确task_id:null当成省略

位置：`src/services/ideaService.ts:164`–`192`，`CanonicalUpdateIdeaOperationInput.task_id?: string` 与下面的逻辑：

```ts
const trimmedTaskId = input.task_id?.trim() || null;
...(trimmedTaskId !== null ? { task_id: trimmedTaskId } : {})
```

它同时丢弃undefined和明确null。创建时两者均表示默认不关联，可以归一；更新时含义不同：省略保持关联、明确null清空。`updateIdeaInTx`本来按字段是否提供判断是否修改task_id，但共享规范化提前删除了这个意图。

这是当前可操作的用户路径：`QuickBarFields.tsx:53`–`57` 的“不属于项目”选项映射到null；`QuickBarApp.tsx:239`–`253` 将draft.taskId传入已绑定记录的save。

### W3 实测：选择清空后记录仍有关联

建立有关联的想法，发送生产windowController save，明确taskId=null，其它内容保持。结果：

```json
{"sentTaskId":null,"storedTaskId":"related-task","reply":{"kind":"saved"}}
```

用户收到保存成功，但记录未解除任务关联。

### W4 实测：同ID的“清空”与“省略”被错误重放

第一份请求明确taskId=null，第二份同operation_id请求省略taskId。实际第二份返回saved/replayed=true，而不是OPERATION_CONFLICT。因为两份不同业务意图被规范化为同一输入。

要求：在唯一的更新规范化函数中保留字段存在性及明确null，类型允许`task_id?: string | null`；创建默认空值处理保持。不要只在服务中另加清空绕过却继续丢失回执指纹，不改变既定record_revision算法，不删合法清关联路径。
