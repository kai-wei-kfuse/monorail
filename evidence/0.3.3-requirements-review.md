## 3. 现状（只读核对）

### 3.1 想法是不是只能一行

| 入口 | 实际能力 |
|---|---|
| 想法池空态文案 | 「在快速记录条里写一行」 |
| 想法池列表 | 整段 `text` 用 `<b>` 展示，无编辑入口，无详情 |
| 快速记录条 | Enter 保存；**Shift+Enter 可换行，最多 10 行**；仍是同一段 `text`，无标题/详情分离；可附文件（`attachments/`） |
| `save_idea`（MCP/CLI） | 契约写明「支持多行和 #标签」；测例含换行。保存后仍只有 `text` |
| `editIdea` | `ideaService.ts` 已有，改 `text`/`needs` | **未注册** `application.ts`，MCP/CLI 不能改已有想法 |
| 附件 | 记录已有 `attachments[]`，快速记录条可拖入；想法池不展示附件预览 |

结论：契约已允许多行，GUI 主路径仍按「一行标题」用。没有「先标题、再可选详情」的结构。没有 Markdown 编辑/预览。`package.json` 无 markdown / DOMPurify / sanitize；源码无 `dangerouslySetInnerHTML`。挡原始 HTML 和危险链接是 0.3.3 新做的，不是接现成过滤器。

### 3.2 待办是不是只能一行

| 入口 | 实际能力 |
|---|---|
| `capture_todo` | 单字段 `text`/`content`，支持 #标签 |
| 卡片编辑器 | `TextArea` 最多 4 行，是卡的「内容」，用来判断做没做完，不是 Markdown 备忘 |
| 任务详情/首页卡 | 一行展示（`plainText`），双击改内容 |

结论：待办卡已能多行短内容，语义是**可完成的事项名**，不是想法那种长备忘。用户原话把想法和待办并提，但路径 1 的「标题 / 详情 / 链接稍后看」只明确写在想法上。

### 3.3 标题/详情若拆开，会碰到的现有语义

| 场景 | 现在用什么 | 0.3.3 若不规定就会歪 |
|---|---|---|
| 想法池列表、已完成列表 | `text` 全文 | 长详情会撑爆列表。应只显示标题 |
| 筛选/查找 `find_items` | 匹配 `text`、`needs`、标签，**不读 md body**（body 现在基本空） | 详情里的链接/关键词默认搜不到。要规定：查标题必中；查详情是否纳入 |
| 转任务 `ConvertIdea` | 任务名/拆项默认 `ideaText.split('\\n')[0]` | 已按「第一行当标题」；详情不应自动变成子项正文，除非用户要拆 |
| 完成想法 | 只改 pool/completed_at，保留 `text` | 详情应随想法一起保留，完成列表仍只显示标题 |
| 首页当前这件事 | 计时活动名或卡内容 | 想法详情不应出现在首页计时卡上 |

### 3.4 主线「只能一个」的用户可见规则

两套上限，不要混：

| 设置 | 界面文案 | 默认 | 可调范围 | 用户看见什么 |
|---|---|---|---|---|
| `mainTasks` | 「主线任务最多几个」：同时押注的主线任务数 | **1** | 1–**3** | 背包「主线任务 n / mainMax」；满了不能再新建主线，已有的不会被挤出 |
| `mainItems` | 主线事项数 | 5 | 1–10 | 每个主线里待做子项上限；满了提示「主线任务最多同时有 N 个待做子任务」 |

默认同时只能有 **1 条**主线任务，所以会感觉「只能一个」。设置里最多加到 3，不是无限。子项上限是另一件事。

### 3.5 存储结构与「数据会不会太多」（已按 coder-7 / 主审纠正）

每条记录仍是 `records/{uuid}.md`：YAML frontmatter（含 `text`）+ markdown body。附件在 `attachments/`。不必另起笔记库。

**不能假定 body 空着当详情用。** `commit.ts:287-288`：`text` 一变，就把 body 写成新的 `text`；`text` 没变则保留原文。`editIdea` 改 `text` 后，原先更长的 body 会被覆盖成新 text（`ideaService.test.ts:94-105`：只改 needs 时保留「完整长正文」；改 text 后 body 变成「新的全文」）。因此：

- 现网多数文件的 body 往往等于 `text`（副本，不是独立详情）。
- 也可能存在外部编辑或测试夹具留下的、比 `text` 更长的 body；直接把 body 当 details 会吃掉或覆盖这些内容。
- 方案必须写清：旧数据如何映射（body==text 视为无独立详情；body 与 text 不同如何展示/迁移）、保存后再编辑、以及降级到旧版本再升级时会不会把详情冲掉。

数据量：

1. **条数**有池上限（默认 10，设置 3–50），到期进冷库但文件还在。历史性能测过一次 2000 条想法。
2. **字数无上限**。长文无论在 `text` 还是 body，`MdRepo.list()` 启动仍会读每个 md 全文。列表 UI 只显示标题 ≠ 内存已减。
3. 把长文继续放在 `text` 里，想法池、`find_items`、转任务第一行都会一起变重。

存储评估细节归 coder-7。产品要求：单一来源的标题/详情、旧数据不丢、不能只靠 UI 隐藏来宣称变轻。

## 6. 验收故事（确认需求后给原型，不代替方案）

1. 只写标题「看到一个安装教程」保存 → 想法池出现这一行，无详情也不挡保存。
2. 点该想法写详情，贴一个 URL 和几句 Markdown → 再打开仍在；列表仍只显示标题。
3. 用 MCP/CLI 按 id 改详情或另存带详情的想法 → 主窗口想法池一致；不打开聊天页。
4. 将该想法转任务 → 任务名来自标题，详情不自动变成子项。
5. 完成该想法 → 已完成列表仍是标题；详情还在，可再打开。
6. 背包能同时存在多于 1 个主线任务（具体条数以澄清 2 为准）；满格仍显式选择，不自动挤走旧主线。
7. 用户认为主路径好看、不用猜「标题框会不会开始计时」。
8. 从一条想法「新窗口打开」→ 另开一个大窗口显示该想法笔记；关掉大窗口不影响主窗口。同一记录再开则聚焦已有窗（有草稿不重载覆盖）。不同记录可否并开由原型给用户看，不定成「只能开一篇」，也不做成笔记管理器。

## 8. 对 coder-3 勘察的产品筛选（2026-11-08）

采纳：快速记录条回车只存标题、可选展开详情；想法池能点开看和改详情。磁盘不能用「1000×2KB≈2MB」结案，要分开看文件体积、提交时全量 list/克隆、历史和回执。历史不要新加静默截断，沿用现有摘要规则。想法池直接新建、待办详情、详情转卡，都还不是已定需求。

coder-3 四条原型场景（`原型/v033-idea-detail-mainline/`）产品对齐：① 标题回车即存、详情另框；② 列表标题+轻标记；③ 再打开默认阅读、转任务只用标题；④ 多主线并列。Tab 保持焦点导航。Shift+Enter 在 0.3.2 是同框换行，改为展开属行为变化，原型里提示即可，不定正式快捷键。未定的待办详情/主线上限不进用户主面开关（避免再出现 S1 实验室面板）；候选写在独立说明页。链接徽章只显示文中已有 URL 的域名并打开，不抓网页。Markdown 按渲染阅读，拒绝原始 HTML 与危险 URL；0.3.2 没有可复用渲染器，原型自带的不算正式实现，方案要把选库和消毒写成新工作。文档路径：coder-6 独占 `docs/stages/0.3.3-execution-plan.md`、`docs/stages/changes/0.3.3-title-details-main-tasks.md`、`docs/adr/0026-record-title-and-markdown-details.md`、`docs/adr/0027-multiple-main-tasks.md`；仓库现到 0025，0026/0027 未占用。

不采纳或未定：详情同步带入 Card content；在用户回复前给 `capture_todo` / `get_task_details` 加 detail；把 mainTasks 直接改成无限。标题+body 拆分必须先处理旧数据（body 现随 text 覆盖），不能当空字段占用。
