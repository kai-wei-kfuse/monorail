审核人 pro-b-4 · 2026-11-06 · 对象：提交 `8c571db` 的 ADR 0021 修订 3（第 1、2、3、4、5、6、11、13 条与「第 2 轮」表）、执行方案 v1.2（G3、G4、G6、G6b、G7、G9 改动处与第 5 节）、计划 v0.31（已定 56–59）。前两轮报告见 `evidence/0.3.1-plan-review-round1.md`、`round2.md`。

本轮只读，没有改代码和方案，没有构建和跑测试。代码位置以当前 HEAD 为准（`src/` 与 tag `v0.3.0` 相同）。

## 结论

第 2 轮的 3 条阻塞、6 条应改、6 条建议都已处理，落点和正文一致，我认为都关掉了。

用户新定的两处需求，大方向可行，「数据一样，只改显示和追问」站得住。但插入暂停有 **1 条阻塞**：现有的暂停 / 继续入口没有改道，照现在的代码走，插入的事一暂停就变成「卡暂停」，〔继续〕回到的是卡。另有应改 5 条、建议 5 条。阻塞和应改都只需改方案文字。改完以后，G1 可以开工；G4、G6b 开工前请把这几处写进方案。不需要再全文复核。

## 第 5 节 3 个问题的回答

### 1. 第 2 轮表的处理：都关掉了
- B1：`refreshInTx` 保留 `first_used_day` 和 `reviewUpdates`，单测补了「新目录写了 `first_used_day`、建了本周回顾行」。
- B2：`rolled_over` 让带过去每天只做一次；在计的卡加进板子、插入中结束原任务，只在开着的条目（插入时看原来那条）开始于今天起点之前才做；三条单测都列了。
- B3：`insertInTx` 加了 `from`，插入和替换两个分支都 `clearPending`，单测每个入口两行。
- S1–S6、N1–N6：落点都和表一致。

### 2. 〔继续〕靠「紧挨在待机前面结束的那条插入」：日常够用，但有两个缺口
- 正常路径可靠：暂停走 `startInTx`（`timerService.ts:8-19`），会把插入那条在 `tx.at` 结束，再在 `tx.at` 开待机，两边时间严格相等。
- 缺口 1：插入刚开始就暂停（同一毫秒），`startInTx` 会把插入那条**删掉**而不是截断（`timerService.ts:13`，`started_at === tx.at` 时返回 `[]`），〔继续〕就找不到前一段。
- 缺口 2：在日历里把前一段的结束时间往前拖，待机不会跟着往前长，中间留出空隙，`ended_at === 待机.started_at` 就不成立了。
- 两种情况方案 R10 都会把〔继续〕灰掉，不坏数据。更稳的找法见建议 N1。

### 3. 宽松 / 紧凑模式
- **「数据一样」站得住**：任何时刻有且只有一条在计时，启动校验（`bootstrap.ts:30-31`）不变，0.3.0 照常打开，切换模式不用转换数据。
- **离线结算在宽松模式下记成待机**：有一个副作用，去重会失效，见应改 S3。
- **空闲追问放在「开始下一件事的事务里」**：要挂的入口太多，建议改成在提交时统一判断一次，见应改 S2。

## 阻塞

### B1 插入暂停 / 继续：现有的暂停 / 继续入口没有改道，小窗的 `resume` 命令有两种意思
- 现在插入中点〔暂停〕走的是 `tracking.pauseInTx`（`timerService.ts:24-29`）：只有开着的条目是 `普通` 时才改 `resume_entry_id`；插入那条是 `插入`，所以回到目标仍然指向卡，接着开一条 `待机 / 暂停`。按 ADR 第 3 条的状态表，这就是「卡暂停中」，不是「插入的事暂停了」。之后点〔继续〕走 `homeService.resumeInTx`（`homeService.ts:83-89`），回到的是**卡**。也就是第 1 轮 B1 的问题又回来了。
- 调这两个函数的入口有：
  - 首页 `home.pause`（`homeService.ts:79`）。现在插入中的〔暂停〕按钮就是它（`FreeCard.tsx:61`）。
  - 小窗命令 `pause` / `resume`（`homeService.ts:171-172`，`windowBus.ts:13-14`）。
  - MCP `pause_timer` → `tracking.pauseInTx`（`homeService.ts:250`）。
  - MCP `resume_timer` → `homeService.resumeInTx`（`homeService.ts:261`）。
- 方案 G4 只是新增了 `pauseInsertInTx` / `continueInsertInTx` 和两个根动作，没写这些现有入口怎么分流。ADR 第 3 条的 MCP 方法表写了想要的效果（插入中 `pause_timer` 暂停插入的事，插入暂停了 `resume_timer` 继续插入的事），可这两个方法现在调的正是上面两个函数。
- 小窗：G7 写的是〔↩ 回到 …〕发现有的 `resume` 命令，「插入的事暂停时小窗的〔暂停〕变〔继续〕」。这个〔继续〕发什么命令没写。如果也发 `resume`，就是回到任务，不是继续插入的事。
- 改法（照第 1 轮 S4「判断放进 InTx 内部」的原则）：
  1. `tracking.pauseInTx` 开头用 `insertState` 判断：插入中就转去 `pauseInsertInTx`，插入的事已经暂停了就什么都不做。这样首页、小窗、MCP 不用逐个改。
  2. 「继续」和「回到任务」分成两个操作。`homeService.resumeInTx` 只做回到任务（〔回到任务〕、`return_from_break`）。新增一个 `continueInTx`：插入的事暂停时继续插入的事，否则按现有的 `resumeInTx` 处理。首页的〔继续〕和 MCP `resume_timer` 改调它。
  3. 小窗 `windowBus` 加一个命令（例如 `continueInsert`），或者把现有 `resume` 的意思定成「继续」，〔↩ 回到 …〕另用一个 `backToTask`，二选一写进 G7。
  4. 首页、计时条在插入中的〔停止〕按钮（`TimerBar.tsx:137`、`FusedCard.tsx:45`、`FreeCard.tsx:61`）随已定 57 一起去掉，写进 G7。`home.stop` 在插入状态下要有明确的行为，见建议 N2。
  5. 单测：每个入口在「插入中」和「插入的事暂停了」两种状态下各一行，断言开着的条目是 `待机 / 插入`，`resume_entry_id` 不变。

## 应改

### S1 回答空闲追问时要把条目的 `kind` 改回 `普通`；`timeEditService.patch` 这个名字不存在
- 要改的那段可能是 `待机 / 暂停`（卡暂停）或者 `待机 / 插入`（插入的事暂停）。现有的 `patchMetadataInTx` / `editInTx`（`timeEditService.ts:34-38,83-85`）只改描述、项目、标签。只改项目会留下「`学习 / 暂停`」这样的条目：`暂停` 本来只用在待机上，回看、首页投影里 `kind === '暂停'` 的分支（`homeProjection.ts:40`）会把它当成暂停处理。
- 改法：回答时同时把 `kind` 改成 `普通`。如果那段是插入的事暂停时的待机，改成 `插入`，回看就会算成「临时离开」。这要用到和 `promoteInsertInTx` 同一种「改 `kind`」的 tracking 接口，建议做成一个通用的内部函数，两处共用。ADR 第 13 条和 G6b 里的 `timeEditService.patch`，改成实际的函数名。

### S2 空闲追问在提交时统一判断，不要挂在每个「开始」入口里
- 「开始下一件事」的入口很多：`startFreeInTx`、`startPresetInTx`、`startCardInTx`、`continueEntryInTx`、插入 / 替换、`continueInsertInTx`、`resumeInTx`、MCP `start_timer` / `start_task_item` / `start_break` / `resume_timer`、日历的「继续这一条」。逐个加，容易漏，R3 的 grep 白名单也难维护。
- 改法：在 `commit.ts` 生成快照之前做一次比较。事务开始时开着的是待机（`普通`、`暂停` 或 `插入` 都算），提交后开着的不是待机，而且这段待机**在本次事务结束时的实际长度**大于 `idleAskMinutes`，就推一条 `idleAsk`。用实际长度，是因为用户可能用待确认起点把一部分待机划给了新的事。MCP 发起的开始也会被覆盖。
- 通知会经过 `buildPendingActions`（`applicationController.ts:168-174`）交给 agent，`describeNotice` 要加 `idleAsk` 这一种，写进 G6b。
- 插入的事暂停后再继续算不算「空闲」，要写一句（建议算，因为它也是待机）。

### S3 宽松模式的离线结算：去重靠的是 `source: '离线追问'`
- `settleOfflineInTx`（`homeService.ts:102-108`）靠「已经有一条 `source === '离线追问'`、开始时间相同的条目」来防止同一段离线被结算两次：休眠恢复事件可能重复到达，启动时还会按 `previous_last_alive` 再结算一次（`scheduler.ts:57-58`）。
- 宽松模式下这段如果记成普通的待机，就会被结算第二次。按现在的做法，第二次会再插一条待机，或者把原来那条再截断一次。
- 改法：宽松模式下这一段记成 `project: '待机'`、`source: '离线追问'`。去重照旧，`buildPendingActions` 只看 `project === '离线'`（`applicationController.ts:176`），不会误报成待处理。ADR 第 13 条表里这一行补上 `source`。

### S4 宽松模式还要改长时间提醒和小窗
- **长时间提醒**：`planReminders`（`domain/reminders.ts:20-22`）对任何开着的条目都排「还在做吗」，待机也一样。宽松模式下首页写「没在计时」，几小时后却弹「「待机」已经持续 N 小时」。ADR 第 13 条表里「长时间提醒照旧」这一格，要改成宽松模式下待机不排这条提醒。紧凑模式是否保留现状，由方案作者决定。
- **小窗**：计划 v0.30 写的是「首页、日历、列表、回看、小窗都要跟着改」，G6b 和 ADR 第 13 条都没列小窗（`MiniApp.tsx:145` 现在按 `project !== '待机'` 决定显示什么），快速记录条的上下文（`quickbarContext`）也没列。请补上，并说明宽松模式下小窗空闲时的样子，和首页一起截图给用户看。

### S5 插入状态和宽松模式同时出现时，界面以哪个为准
- 插入的事暂停了，开着的是待机。G6b 写的是「宽松模式下开着的是待机时输出 `idle: true`，首页写『没在计时』」。可这时首页应该是插入卡，显示「已暂停 · 还在等你回去」。卡暂停中也一样，应该显示卡在暂停。
- 改法：`homeProjection` 的 `idle` 只在**不在插入状态、也没有回到目标**时才按宽松模式处理。也就是说，只有真正什么都没在做时才写「没在计时」。G6b 的单测补这两种组合。

## 建议

- **N1 找〔继续〕的前一段**：改成「`resume_entry_id` 那条结束以后、最后结束的那条 `插入`」。条件是它的 `ended_at ≤ 待机.started_at`，且中间没有别的非待机条目。这样日历里拖出空隙也能找到。同一毫秒内开始又暂停的情况，可以让 `pauseInsertInTx` 在这种时候什么都不做。
- **N2 插入状态下的 `home.stop`**：现在的 `stopInTx` 会清掉回到目标，等于悄悄结束原任务（`timerService.ts:31-36`）。界面上的〔停止〕去掉以后，建议 `stopInTx` 在插入状态下直接抛 `IN_AWAY_ACTIVITY`，和 MCP 方法表里 `stop_timer` 的拒绝一致，避免以后有人从别的入口接回来。
- **N3 MCP 看不出插入的事有没有暂停**：两种插入状态在 `get_context` 里都是 `mode: 'away'`（`applicationController.ts:96`），agent 只能从 `allowed`、`open_entry.project === '待机'` 推断。可以加一个只读字段（例如 `timer.away_paused: boolean`）。`timerContextSchema` 是 `strictObject`（`application.ts:101`），加字段也算输出约定的扩展，和 `today_plan` 一起写进兼容测试。不加的话，就在 `docs/application/README.md` 写明怎么判断。
- **N4 `skipCard(card.id, resetRound)` 不要用界面传进来的 `resetRound`**：从翻卡到点〔换一张〕，中间状态可能变了（例如小窗完成了一张卡）。建议在写事务里重新算一次：加上这张以后，如果剩下的候选全都在 `seen` 里，就写成 `[这张]`。
- **N5 `rolled_over` 文件会每天新建**：任务模式关掉、或者从来不用板子的用户，每个活动日启动时也会写一份只有 `rolled_over: true` 的 `plans/<今天>.yaml`。数据没问题，180 天清理也会覆盖。如果想少写盘，可以在任务模式关掉时跳过带过去，写在 ADR 第 6 条。
