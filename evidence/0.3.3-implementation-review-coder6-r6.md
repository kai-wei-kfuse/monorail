## 五个失败用例

### F1 从未见过的迟到旧 check 覆盖新轮

tracker 已接受新轮 dc-round-2，随后收到从未见过的旧轮 dc-round-1，实际返回 dc-round-1 并取代 active。当前实现仅用 ackedRequestIds 记见过的 ID，没有服务签发的先后关系；合法 restore dc-round-2 随后无法解锁。

要求沿主审决定增加同会话单调轮次或服务签发 generation，不解析自由字符串 ID 猜顺序。测试 requestId 是不透明字符串；generation 字段为将来的单调属性占位，最终字段名可按真实协议适配，不能改成允许旧 check。

### F2 restore 先于 check 时没有关闭该轮

restore dc-round-1 先到，当前 active=null 时直接忽略；后来的 check dc-round-1 被接受，已结束轮次重新加锁。要求恢复事件关闭其对应轮次，使后来旧 check 不能重锁；仍不能用旧 restore 解锁新轮。

### F3 前端无 token 取消仍送到 Rust

nativeIdeaWindows.cancelMaintenanceCheck(undefined) 实际 invoke cancel_maintenance_check，requestId=null，并成功返回。不是拒绝。MainApp 初修退出 catch 也无 ID 取消：一次并发准入被拒后可能取消另一项已经开始的维护。

### F4 Rust 并发 begin 覆盖当前轮

真实 Gate 正处于 dc-original，再调用 begin_check(dc-second, ...) 后，active/pending 变为 dc-second，首轮 channel sender 被替换。测试要求首轮状态和 receiver 保留，实际失败。

要求沿既有维护准入明确拒绝并发；不能另造第二把业务锁。check_all_drafts 与 perform_app_exit/安装必须使用同一轮生命周期，不能每次重复 begin 换号。

### F5 Rust 无 token 取消可解除别人的轮次

cancel_check(None) 在 dc-current 正进行时成功清除 installing/pending/active。带错 token 已拒绝，缺 token 却仍是旁路。要求取消只作用于调用者实际持有的本轮 ID，并将准入失败与已拥有该轮后的失败分开处理。
