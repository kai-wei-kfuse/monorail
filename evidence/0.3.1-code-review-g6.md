## 应改

### S1 宽松模式的显示只做了一半：`looseIdle` 算出来了，但没有界面在读

  - **首页**：没在做事时写「没在计时」、读数不走、标题栏状态灯变灰（G6b 第 3 条）。现在宽松模式的首页还是「待机」，读数照走。
  - **小窗、快速记录条**（第 3 轮 S4）：`MiniApp.tsx:145,152` 还按 `project !== '待机'` 判断，标题写「待机」；`quickbarContext` 没改。
  - **回看**：「待机不计，『含待机 / 睡眠』开关只剩睡眠」（G6b 第 4 条）。`recapService`、`domain/review/recap.ts` 没改。
  - **日历页的〔显示待机〕开关**（`CalendarPage.tsx:80`）：宽松模式下还显示，可点了不起作用（`showIdle` 被强制设成 false）。要么隐藏，要么显示成灰的并写明原因。

### S2 缩小对话框的下限、今天的量取自上一次提交，卡在计时的时候会过期，服务端会拒绝
- G5 N1 / N2 的修法是把 `split: { todayGoal, minToday }` 放进 `homeProjection`（`homeProjection.ts:23-27,43`），对话框只读这两个值。可 `projectHome` 只在提交时算（只有 `commit.ts:345` 调用），心跳不会重算。
- 卡在计时、中间又没有别的提交时，`minToday` 停在上一次提交的时刻。比如 9:00 开始这张卡，9:25 点〔缩小〕：投影里今天已计是 0，`minToday` 是 5；服务端 `split` 按 9:25 算，今天已计 25 分钟，下限是 25。用户在滑块上选 10、15、20，都会被拒，报「今天做的不能少于今天已经计的时间」。G5 之前，页面是拿 `now` 现算的，没有这个问题。
- 改法：投影给「上一次提交时的今天已计」和「开着那条的开始时刻」，对话框打开时加上已经过去的时间再套 `minTodayMinutes`。或者打开对话框时调一个只读函数，现算一次（照 `checkComplete` 的做法，`cardService.ts`）。`todayGoal` 的回落值（剩下的时长）也一样会过期，用同一种办法一起修。补一条测试：开始卡 25 分钟内没有别的提交，打开缩小时下限是 25。

## 建议

- **N1 宽松模式下隐藏的「离线追问最小间隔」其实还在起作用**：`settleOfflineInTx`（`homeService.ts:124-125`）不管哪种模式，都先按 `offlineAskMinMinutes` 决定这段离线结不结算：短于这个时长就算在原来的活动上，长于它才记成待机。宽松模式下设置页把这一项藏起来了（`onlyIn: 'strict'`），用户却还受它影响。可以接受，但请把描述写成两种模式通用（例如「关机或休眠短于这个时长，算在原来的活动上」），这一项不要藏。
- **N2 空闲追问的通知数据里有 `activities`，回答时可能还在用旧列表**：`idleAsk` 的 `activities` 是推通知那一刻的快捷活动列表，和 `offlineAsk` 一样，可以接受。但 `answerIdle` 用 `template(tx, activity)`：传的是预设 id 时取预设，否则按名字，项目默认「生活」。用户手写的活动名会全部记成「生活」，和离线追问一致，在 G7 截图给用户时顺带说一句就行。
- **N3 `Gallery.tsx:120` 的设置导航还写着「出卡 DEAL」「降级 DEGRADE」**：这是开发用的画廊，不进生产包，但 G7 要用它截图对照，建议同步成「任务」「任务模式」。设置 01 的 id 还是 `deal`，02 的 id 从 `degrade` 改成了 `quest`。我 grep 过，没有别处按 id 跳转到这两节，所以没问题。
- **N4 拆分的 `order` 取中点，反复拆会越来越密**：`(card.order + next) / 2` 每拆一次，间隔减半，大约 50 次以后就会碰到浮点精度。实际用不到这么多次，`reorderQueue` 也会把序号重排成整数。写一句注释就行，不用改。

## 已核对、没问题的

- 设置：四个新键都标了 `defaultWhenMissing`，`SETTING_LABELS` 加了；02 改成任务模式，编号不变；01 去掉了「快到期」，描述也改了；04 加了计时模式和空闲追问（只在紧凑模式下显示）；05 去掉了休息池和「切换 / 插入」的说法；06 加了回去区域；`mainItems` 和回顾日的描述同步了。按计时模式过滤设置行的写法（`onlyIn`）简单可靠。
- 离线结算：宽松模式下记成 `project: 待机`、`source: 离线追问`，去重照旧；不推 `offlineAsk`；`buildPendingActions` 只看 `project === '离线'`，不会误报。有重复结算只记一次的测试。
- 长时间提醒：宽松模式下，开着的是待机时不排「还在做吗」，有测试。
- 空闲追问：在 `commit.ts` 统一判断，只在紧凑模式下做。比较的是「事务开始时开着的待机」在提交后的实际长度，用户用待确认起点划走的那一部分会自动扣掉，严格大于阈值才问（刚好等于、短于都不问，有测试）。MCP 发起的开始也会触发，`describeNotice` 加了 `idleAsk`。
- 回答空闲追问：`answerIdle` 先确认那一段还是待机、已经结束，然后用 `retypeEntryInTx` 同时改描述、项目、标签和类型。插入的事暂停的那段改成 `插入`，其余改成 `普通`。卡暂停那段回答以后，不会留下「学习 / 暂停」这样的条目，有测试。
- `looseIdle` 的判断本身是对的：不在插入、没有回到目标、开着的是待机，有测试。
